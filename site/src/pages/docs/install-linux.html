Install on Linux

The Linux build is one tarball of about 1.2 MB: the desktop app, the stockfw command line with its manual page and shell completion, a boot service, a menu entry, the README, the changelog, the licence texts and an install script. GTK comes from your distribution.

Before you start

  • An x86-64 distribution with GTK 3. Debian, Kali, Ubuntu and WSL2 are what it is tested on.
  • liblzma 5 and OpenSSL 3 (liblzma.so.5 and libcrypto.so.3), which read the signed location database. A distribution that ships only OpenSSL 1.1, such as Debian 11 or Ubuntu 20.04, is refused by the installer before anything is copied, because the app and the boot service could not start there.
  • iptables and ip6tables, and nft and curl if you want threat-intel blocklists or country blocking. On current distributions iptables is the nftables-backed version, which is fine: StockFW’s rules land in nftables through it.
  • Root, for reading the kernel log and for changing rules. Everything else works as your own user.

Install

$ sha256sum -c SHA256SUMS.txt --ignore-missing
StockFW-{{release}}-linux-x86_64.tar.gz: OK
$ tar xzf StockFW-{{release}}-linux-x86_64.tar.gz
$ cd StockFW-{{release}}-linux-x86_64
$ sudo ./install.sh

The script checks that every library the binary links against is present, by soname rather than by package name, because Debian and Ubuntu renamed libgtk-3-0 to libgtk-3-0t64 and a package check would wrongly fail a working system. If something is missing, it names the library and stops:

$ sudo apt install libgtk-3-0 libgdk-pixbuf-2.0-0 liblzma5 libssl3   # Debian, Kali, Ubuntu
$ sudo dnf install gtk3 xz-libs openssl-libs                           # Fedora
$ sudo pacman -S gtk3 xz openssl                                       # Arch

iptables, nft and curl are checked separately and only warned about: without iptables the app still runs, reads, simulates and shows the policy, and only applying needs it; without nft or curl the threat-intel lists cannot be turned on, and the Threat Intel page says so.

What gets installed

PathWhat
/usr/local/bin/StockFWThe desktop application.
/usr/local/bin/stockfwThe command line and local dashboard. The two names differ only in case; they are staged apart in the tarball so a case-insensitive filesystem cannot merge them.
/usr/local/share/man/man1/stockfw.1The manual page, man stockfw, written by the tool itself from its command tables.
/usr/local/share/man/man7/stockfw-topics.7The desktop app’s help topics as one manual page, man stockfw-topics; the same text as stockfw help topics.
/usr/local/share/bash-completion/completions/stockfw, /usr/local/share/zsh/site-functions/_stockfwCompletion for bash and zsh: commands, options, values and your own rule references. See the command line page.
/usr/local/share/applications/stockfw.desktopThe menu entry (Settings › StockFW). It starts the unprivileged app.
/usr/local/share/icons/hicolor/{48x48,128x128,256x256}/apps/stockfw.pngIcons.
/etc/systemd/system/stockfw.serviceThe boot service, enabled by the installer: it runs stockfw start before the network comes up and loads the last applied policy, so the rules are back after a restart. See At boot.
/usr/local/share/doc/stockfw/LICENSE.txt, CHANGELOG.mdThe licence summary with both licence texts, and the changelog.
/usr/local/bin/stockfw-uninstallRemoves all of the above.

Run it

$ StockFW                          # as yourself: policy, simulator, Trust; no events, no apply
$ sudo /usr/local/bin/StockFW      # as root: the full tool

As your own user, the app can show and edit a policy, run the simulator and inspect programs, but the kernel log is unreadable without root, so the Events page says that monitoring is unavailable rather than showing an empty list, and Apply refuses with a message rather than half-applying.

Why the full path after sudo

sudo does not search your PATH. It uses Defaults secure_path from /etc/sudoers, which on Fedora, RHEL and some Kali systems is /usr/sbin:/usr/bin:/sbin:/bin and does not include /usr/local/bin (Ubuntu’s default does). There, sudo StockFW reports “command not found” while plain StockFW works. The installer reads secure_path in both the quoted form Debian writes and the unquoted form RHEL and Fedora write, and warns in its summary when the path is missing.

It deliberately does not edit sudoers. Adding /usr/local/bin to secure_path would widen the search path for every command anyone runs under sudo on that machine, which is a worse trade than typing a path.

Why there is no polkit policy or setuid helper

StockFW expects to already be root when it changes the firewall and never re-executes itself through sudo. A desktop program that can silently rewrite the whole firewall is a worse security posture than one that asks for root openly, so the installer ships neither a polkit rule nor a setuid wrapper. Grant privilege by launching with sudo, or through your desktop environment’s own mechanism.

At boot

iptables rules live in the kernel only, so a reboot empties them. The installer puts in and enables stockfw.service, which runs stockfw start once, before any network interface comes up, so the machine is never on the network unfiltered between boot and sign-in. It starts the last policy that was applied as root (/etc/stockfw/applied.csv): a policy that was saved but never applied, or held by Audit-only or the Lock, waits for the next Apply, and on a machine where nobody has applied a policy yet the service does nothing. There is no stop action on purpose: stopping the unit or shutting down never takes the rules away; sudo stockfw stop does. A deny rule that names a host by name cannot be looked up before the network is up, so it is left out at boot, journalctl -u stockfw says which, and it goes in with the next apply. The policy edited in StockFW started without sudo lives in ~/.stockfw and is not what the service loads; see the next section.

Two homes: yours and root’s

The policy lives in a directory that depends on who is running the program:

  • as your user: ~/.stockfw/, with preferences and logs in ~/.config/stockfw/;
  • as root: /etc/stockfw/, with preferences and logs in /root/.config/stockfw/.

A rule you add as yourself is therefore not the rule sudo stockfw apply applies. Pick one identity for policy work and stay with it: the simplest is to run both the app and every stockfw policy command through sudo, so everything lives in /etc/stockfw. For scripts and tests, STOCKFW_RULES_DIR=/some/dir points both programs at one directory regardless of who runs them.

Where StockFW keeps its files

File (as root)Holds
/etc/stockfw/inbound/…, outbound/…The policy, one file per rule kind. See Files and formats.
/etc/stockfw/applied.csvThe last policy the engine accepted: what Apply measures against and rolls back to.
/root/.config/stockfw/stockfw.confPreferences.
/root/.config/stockfw/audit.logOne line per apply, attest, forget and Sentinel action. Append-only.
/root/.config/stockfw/trust.csv, behavior.csv, autoblocksThe Trust baseline, the Copilot’s learned behaviour, Sentinel’s staged blocks.

In the kernel, StockFW owns the chains INBOUND, OUTBOUND, STOCKFW-DNAT and STOCKFW-SNAT, hooked from INPUT, OUTPUT, PREROUTING and POSTROUTING. On each apply only those chains are replaced; rules that Docker, libvirt or ufw keep in the same tables are not touched.

Events on Linux

The policy logs what it drops, rejects and, with Log allowed connections on, newly allows, and the Events page reads those lines from the kernel ring buffer (/dev/kmsg) directly, so it works on WSL, in containers and on systems without rsyslog or journald. Root is required.

Update

Unpack the new tarball and run its install.sh again. Your policy, preferences and event history are outside /usr/local and are kept; the boot service is replaced.

Uninstall

$ sudo /usr/local/bin/stockfw-uninstall

Removes exactly what the installer created: the binaries, the boot service (disabled and deleted), the menu entry, the icons, the licence and the changelog, and your own start-at-sign-in entry. A running StockFW is asked to quit first so it saves its settings. It leaves your policy in /etc/stockfw or ~/.stockfw, your preferences and event history, and any rules currently loaded in the kernel: press Stop firewall or run sudo stockfw stop first if you want those gone.
