Install on Linux

The Linux build is a small tarball: the desktop app, the stockfw command line, a menu entry and an install script. GTK comes from your distribution, so the download is under 200 KB.

Before you start

  • An x86-64 distribution with GTK 3. Debian, Kali, Ubuntu and WSL2 are what it is tested on.
  • iptables and ip6tables, and nft if you want threat-intel blocklists. On current distributions both are the nftables-backed versions, which is fine: StockFW’s rules land in nftables through them.
  • Root, for reading the kernel log and for changing rules. Everything else works as your own user.

Install

$ sha256sum -c SHA256SUMS.txt --ignore-missing
StockFW-{{release}}-linux-x86_64.tar.gz: OK
$ tar xzf StockFW-{{release}}-linux-x86_64.tar.gz
$ cd StockFW-{{release}}-linux-x86_64
$ sudo ./install.sh

The script checks that every library the binary links against is present, by soname rather than by package name, because Debian and Ubuntu renamed libgtk-3-0 to libgtk-3-0t64 and a package check would wrongly fail a working system. If something is missing, it names the library and stops:

$ sudo apt install libgtk-3-0 libgdk-pixbuf-2.0-0   # Debian, Kali, Ubuntu
$ sudo dnf install gtk3                              # Fedora
$ sudo pacman -S gtk3                                # Arch

iptables is checked separately and only warned about: without it the app still runs, reads, simulates and shows the policy; only applying needs it.

What gets installed

PathWhat
/usr/local/bin/StockFWThe desktop application.
/usr/local/bin/stockfwThe command line and local dashboard. The two names differ only in case; they are staged apart in the tarball so a case-insensitive filesystem cannot merge them.
/usr/local/share/applications/stockfw.desktopThe menu entry (Settings › StockFW). It starts the unprivileged app.
/usr/local/share/icons/hicolor/{48x48,128x128,256x256}/apps/stockfw.pngIcons.
/usr/local/share/doc/stockfw/LICENSE.txtLicence text.
/usr/local/bin/stockfw-uninstallRemoves all of the above.

Run it

$ StockFW                          # as yourself: policy, simulator, Trust; no events, no apply
$ sudo /usr/local/bin/StockFW      # as root: the full tool

As your own user, the app can show and edit a policy, run the simulator and inspect programs, but the kernel log is unreadable without root, so the Events page says that monitoring is unavailable rather than showing an empty list, and Apply refuses with a message rather than half-applying.

Why the full path after sudo

sudo does not search your PATH. It uses Defaults secure_path from /etc/sudoers, which on Debian and Kali is /usr/sbin:/usr/bin:/sbin:/bin and does not include /usr/local/bin. So sudo StockFW reports “command not found” while plain StockFW works. The installer detects this and warns in its summary.

It deliberately does not edit sudoers. Adding /usr/local/bin to secure_path would widen the search path for every command anyone runs under sudo on that machine, which is a worse trade than typing a path.

Why there is no polkit policy or setuid helper

StockFW expects to already be root when it changes the firewall and never re-executes itself through sudo. A desktop program that can silently rewrite the whole firewall is a worse security posture than one that asks for root openly, so the installer ships neither a polkit rule nor a setuid wrapper. Grant privilege by launching with sudo, or through your desktop environment’s own mechanism.

Two homes: yours and root’s

The policy lives in a directory that depends on who is running the program:

  • as your user: ~/.stockfw/, with preferences and logs in ~/.config/stockfw/;
  • as root: /etc/stockfw/, with preferences and logs in /root/.config/stockfw/.

A rule you add as yourself is therefore not the rule sudo stockfw apply applies. Pick one identity for policy work and stay with it: the simplest is to run both the app and every stockfw policy command through sudo, so everything lives in /etc/stockfw. For scripts and tests, STOCKFW_RULES_DIR=/some/dir points both programs at one directory regardless of who runs them.

Where StockFW keeps its files

File (as root)Holds
/etc/stockfw/inbound/…, outbound/…The policy, one file per rule kind. See Files and formats.
/etc/stockfw/applied.csvThe last policy the engine accepted: what Apply measures against and rolls back to.
/root/.config/stockfw/stockfw.confPreferences.
/root/.config/stockfw/audit.logOne line per apply, attest, forget and Sentinel action. Append-only.
/root/.config/stockfw/trust.csv, behavior.csv, autoblocksThe Trust baseline, the Copilot’s learned behaviour, Sentinel’s staged blocks.

In the kernel, StockFW owns the chains INBOUND, OUTBOUND, STOCKFW-DNAT and STOCKFW-SNAT, hooked from INPUT, OUTPUT, PREROUTING and POSTROUTING. On each apply only those chains are replaced; rules that Docker, libvirt or ufw keep in the same tables are not touched.

Events on Linux

The policy logs what it drops, rejects and, with Log allowed connections on, newly allows, and the Events page reads those lines from the kernel ring buffer (/dev/kmsg) directly, so it works on WSL, in containers and on systems without rsyslog or journald. Root is required.

Update

Unpack the new tarball and run its install.sh again. Your policy and preferences are outside /usr/local and are kept.

Uninstall

$ sudo /usr/local/bin/stockfw-uninstall

Removes the binaries, the menu entry, the icons and the licence. It leaves your policy in /etc/stockfw or ~/.stockfw, and any rules currently loaded in the kernel: press Stop firewall or run sudo stockfw stop first if you want those gone.
