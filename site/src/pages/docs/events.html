Events

Every connection the firewall allowed or blocked, as it happens. StockFW does not capture packets; it reads the verdicts your operating system already records and shows them unchanged, so each row can be checked against the system’s own log.

[[shot:events|The Events page: a count of 12 events, a search box, the Monitor switch, Clear and Refresh, a filter bar with direction, verdict, protocol, port, address, From and To, Reset and Export CSV, and a table of time, direction, interfaces, port, source, destination, protocol and service with blocked rows in red.|Blocked rows are red and carry the [BLOCKED] marker that every other part of the app keys on. The filter bar narrows the list by direction, verdict, protocol, port, address and time.]]

Where the events come from

[[win]]
The Security event log, events 5156 (the Windows Filtering Platform permitted a connection) and 5157 (it blocked one). StockFW runs wevtutil from the system folder every five seconds and reads every record after the last one it delivered, up to 10,000 a poll, newest first and shown oldest first, so a burst arrives whole. Past that cap the newest 10,000 are read and the gap is counted, as an upper bound, next to the event count (“up to N skipped”). Each record carries the program path, both addresses, the ports, the protocol and the direction, so the Events page on Windows names the program; the In and Out columns hold this computer’s address and the other side’s. The audit policy that makes Windows write these events is switched on the first time the elevated app runs; see Enable monitoring.
[[linux]]
The kernel log. StockFW’s own rules log what they drop and reject with the prefixes STOCKFW-DROP and STOCKFW-REJECT, and, when Log allowed connections is on, the first packet of each newly allowed connection with STOCKFW-ALLOW, rate-limited to ten a second. A block by a threat-intel list or a country or network rule logs with STOCKFW-TI and the list’s id, so the row names the list as its rule. The page reads those lines from the kernel ring buffer (/dev/kmsg) directly, which needs root and works on WSL, in containers and on minimal systems, and it never skips a line; lines without a StockFW prefix are ignored, so unrelated kernel messages never appear. The kernel log carries no program name, so there is no Program column on Linux; the Overview’s connection table names programs instead. [[gap]]

The columns

Time (the event’s own time, in local HH:MM:SS), direction (in or out), the interfaces in and out (on Windows, this computer’s address and the other side’s), the local port, source and destination addresses, protocol, and the service name looked up from the port, with [BLOCKED] appended on a blocked row and, after it, the rule that blocked it when a list did. On Windows there is also the program. Every column sorts, and rows are inserted newest first by their time stamp, so an event that arrives late still lands in the right place. [[verified:ui-hitview-smoke]]

How many it keeps

The list holds 100,000 events by default and up to 1,000,000 (Preferences › Events › Events kept in the list), and stays responsive at that size: the rows live in a ring buffer outside the toolkit, each string is kept once (about 75 bytes an event, so 100,000 is about 7 MB), the view copies no rows, and a live event under any sort order moves at most one small block. The oldest event goes first. The same row twice in a row is one event. [[verified:ui-hitview-smoke]]

Search, filters, export

  • Search narrows the list as you type: a case-insensitive match against any column the list shows, the blocking list’s name included. The count reads “3 of 1,200 events” while a filter is active, so an empty result is never mistaken for an idle firewall. [[verified:test_filter_match]]
  • The filter bar adds direction, verdict (blocked, allowed or both), protocol, a port or a range (1000-2000), an address or a CIDR block (10.0.0.0/8, fd00::/8), and a time range (From and To). Every filter must match. Reset clears them all. The command line has the same filters: stockfw events --since 1d --port 22 --dir in.
  • Export CSV writes the rows that match the current filters to a file only your account can read (RFC 4180; a cell a spreadsheet would run as a formula is written as text).
  • Monitor starts and stops reading the log. When it cannot start, because you are not root on Linux or the audit policy is off on Windows, the page says so and how to fix it instead of showing nothing.
  • Clear empties the list and forgets which rows it has seen; the history on disk, if you keep one, is not touched. Refresh reads again now.

An empty list always explains itself: waiting for the first event, monitoring off, or nothing matches the filter.

History on disk

Keep event history on Preferences › Events is off until you turn it on. On, every event the list accepts is also appended to a file: one file per day under ~/.local/share/stockfw/events on Linux and %LOCALAPPDATA%\stockfw\events on Windows, readable by your account only, flushed once a second and at once when the session ends, each line with a checksum so a line cut short by a crash is skipped rather than misread. Files older than 30 days, or beyond 200 MB in all (both adjustable on the same page), are deleted oldest first; Delete history asks first and deletes only history files. When StockFW starts, the newest events are read back into the list on a worker thread, so the window is up before the history is in, and a burst that arrives while it loads still reaches the file whole. Only one copy of StockFW writes a given history; a second copy on the same account says so and saves nothing until the first is gone. stockfw events --history searches the saved files without root. [[verified:test-eventstore.sh]]

Repeated events and noise

Two settings on Preferences › Events shape the list. Hide repeated events drops a row when the same source, port and verdict arrived a moment ago, so a port scan becomes a few rows rather than thousands. Skip events that are not for the firewall filters records the firewall subsystem did not produce. The Copilot is fed before these display filters, so hiding repeats never hides a scan from the detections.

De-duplication happens three times for three reasons: the reader refuses to deliver the same record twice, the list refuses to insert the same row twice (so a monitor that is stopped and restarted does not repeat itself), and the preference above hides visually identical connections. [[verified:ui-hitview-smoke]]

Right-click: from an event to a rule

The menu offers only what that row can express, so it can never promise a rule the policy cannot hold:

  • Outbound rows: Block destination (all traffic), Allow destination (all traffic), and Block this service to the destination, where the service is taken from the row’s port. On a row a threat-intel list blocked, Allow becomes Add exception, because an allow rule would not beat the list.
  • Inbound rows: Trust source (inbound allow), or Remove trust for this source when a trust rule for it already exists. There is no inbound-deny rule kind, because inbound is denied by default; removing the trust is what blocks the source again.
[[shot:events-menu|The Events page with the right-click menu open on a blocked inbound VNC row from 203.0.113.50, offering “Trust 203.0.113.50 (inbound allow)”.|On an inbound row the only offer is to trust the source. Blocking it is already the default.]]

Choosing an entry opens a dialog that prints the exact rule, as it will be written to the policy file. Where the rule kind has an opposite-direction twin, the dialog also carries the Direction setting: one direction by default, or Bi-directional, which stages the twin as part of the same change. After Yes, the rule is saved (and taken back out if the save fails), the Policy page reloads, and the change is pushed through the apply gate. The result dialog distinguishes live from staged, not live yet: administrator privileges are required. [[verified:test_eventrule_builders]]

Allowing a destination also lifts any block Sentinel staged for it, before the allow is pushed, so the two reach the firewall together; on Windows a block rule outranks an allow, so without this your Allow would have changed nothing on the wire. [[verified:fs-copilot-smoke]]

What else reads the events

The Activity page counts exactly the rows this page lists, after its duplicate check, each at its own time. The Copilot reads every row for its checks and Sentinel’s detectors. The Overview’s counters and recent-blocks card are the same stream, summarised. All of it runs whether the window is shown or hidden in the tray.
