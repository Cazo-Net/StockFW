Files and formats

StockFW keeps everything as plain text you can read, copy, diff and back up. There is no database and no registry blob. This page is the format reference; nothing here is needed to use the app.

Where

PlatformPolicy and journalPreferences, logs, baselines
Windows%LOCALAPPDATA%\stockfw\%APPDATA%\stockfw\
Linux, as your user~/.stockfw/~/.config/stockfw/
Linux, as root/etc/stockfw//root/.config/stockfw/

STOCKFW_RULES_DIR overrides the first column; XDG_CONFIG_HOME the second on Linux; and STOCKFW_AUDIT_FILE, STOCKFW_TRUST_FILE and STOCKFW_AUTOBLOCK_FILE point single files elsewhere.

The policy

One file per rule kind, no extension, under inbound/ and outbound/. A file that does not exist is an empty kind.

FileColumns
inbound/allow-fromhost, comment
inbound/allow-serviceservice, port, for, comment
inbound/forwardservice, firewall port, to, port, comment
outbound/allow-to, outbound/allow-from, outbound/deny-to, outbound/deny-fromhost, comment
outbound/allow-service, outbound/deny-serviceservice, port, for, comment
 
SSH, 22, 192.168.1.0/24, admin LAN
HTTPS, 443, Anyone, web server
Web, 8080, 192.168.1.30, 80, lab box

Comma-separated, one rule per line, a space after each comma on write and optional on read. The comment is the last field and may be empty. A field may not contain a comma or a line break, and the app refuses to save one that does, because it would become another field. Ports are digits only (a range is 1024:2048); a host is an address, a CIDR network, Anyone, or a host name that does not start with a hyphen. A line that does not parse is skipped at load and counted (“2 malformed policy rules were skipped”); saving writes back only the rules that parsed, and never rewrites a bad line into something else. [[verified:test_policy_load_validation_f1]]

Round trip is exact: what you save is what loads. You may edit these files by hand with the app closed; the Policy page shows the result, and nothing reaches the firewall until Apply.

The applied journal

applied.csv next to the policy: the last policy the engine accepted. Apply measures its impact against this file, not against the saved policy, and rolls back to it when the engine refuses.

# StockFW applied policy journal v1
inbound-allow-service, "SSH, 22, 192.168.1.0/24, admin LAN"
outbound-deny-to, "198.51.100.66, known bad host"

One row per applied rule: the kind, then the rule’s own line as one quoted field. A row that cannot be trusted fails the whole load, and an apply then refuses rather than roll back to something unverifiable; the dialog says so. The file is rewritten after every successful apply. If it is missing, the next apply counts every rule as added, which is also what happens on a fresh install. [[verified:test_apply_gate]]

Preferences

stockfw.conf, an ini file with two groups. Keys keep the names the original program used, so a setting is easy to find:

[client]
first_run=false
enable_tray_icon=true
minimize_to_tray=true
filter/redundant=false
filter/not_for_firewall=true
policy_auto_apply=true
policy_audit_only=false
start_firewall_on_gui=false

[firewall]
ext_if=eth0
int_if=
nat=false
icmp/enable=true
icmp/echo_request=true
deny_packets=true
block_external_broadcast=false
block_non_routables=true
restrictive_outbound=false
log_allowed=true

A missing key takes its default. The Preferences page describes each setting.

The audit log

audit.log, append-only, one line per thing StockFW did to the firewall or the baselines:

2026-11-02T16:40:12Z | policy applied | source=Policy page mode=live +1 added (1 allow, 0 block), -0 removed (0 allow, 0 block), =8 unchanged
2026-11-02T16:41:03Z | policy held, firewall untouched | source=cli mode=audit-only +0 added ... =9 unchanged
2026-11-02T16:44:50Z | event rule added | outbound-deny-to 203.0.113.9 (Events page) live
2026-11-02T16:51:19Z | sentinel auto-block | outbound-deny-to 198.51.100.77 beacon 6 contacts, mean 30 s
2026-11-02T17:01:19Z | sentinel rule removed | outbound-deny-to 198.51.100.77: expired after 10 minutes
2026-11-02T17:05:02Z | trust-attest | /usr/bin/nc.openbsd sha256=…

The three fields are the time in UTC, the action, and the detail, separated by | . Actions include policy applied, policy applied, with notes, policy apply failed, policy apply refused, policy apply: no change, policy held, firewall untouched, event rule added, event rule added (bi-directional twin), event trust removed, the sentinel … family and trust-attest / trust-forget. Line breaks and the separator inside a detail are escaped, so a tool’s error text can never read as a second, forged entry. The app only ever appends; rotation is yours. [[verified:test_apply_gate]]

The Trust baseline

trust.csv: quoted CSV, eight fields per row, one row per attested path.

"C:\Program Files\Mozilla Firefox\firefox.exe","9f3b…c1","68425616","1761840000","valid","Mozilla Corporation","1762085102","1762091840"

Path, SHA-256, size, modification time (unix seconds), signature state (valid, invalid, unsigned, na, unknown), publisher, first seen, last seen. A row with a different number of fields is skipped, never the file. [[verified:test_trust_engine]]

The behaviour baseline

behavior.csv: what the Copilot has learned, one fact per row, keyed by program.

firefox,meta,1342,98304,2211840,1762080000,1762091830
firefox,rate,1762091400,7,6250,41,0
firefox,port,443,1288
firefox,port,80,41
firefox,dest,104.16.4.34,212
firefox,hour,14,301
curl,partial,1

Row kinds: meta (totals and first/last seen), rate (the connection-frequency state), port, dest and hour (counts), and partial (the profile was capped and can no longer claim novelty). Rows of an unknown kind are ignored, so an older version can read a newer file. Delete the file to start learning from scratch.

Sentinel’s staging record

autoblocks: what Sentinel has staged and when, rewritten on every stage and every retirement.

S,1762094279,7,198.51.100.77, Sentinel: beacon 6 contacts

Four fields: S, the staging time in unix seconds, the rule kind’s number, and the rule’s own CSV line last, so its commas survive the split. At start-up, rows older than ten minutes are taken out of the policy with an audit line; fresh rows are re-armed with their original time. Deleting this file loses the tracking of staged rows, not the rows themselves, which the destination gates and the next Apply then govern. [[verified:fs-copilot-smoke]]

In the engine

  • [[win]] Rules named StockFW-… are policy rules; StockFW … (with a space) are Preferences rules. StockFW owns everything with those prefixes and nothing else. wf.msc or netsh advfirewall firewall show rule name=all lists them.
  • [[linux]] Chains INBOUND, OUTBOUND, STOCKFW-DNAT and STOCKFW-SNAT, hooked from INPUT, OUTPUT, FORWARD (router mode), PREROUTING and POSTROUTING; log prefixes STOCKFW-DROP, STOCKFW-REJECT and STOCKFW-ALLOW. The nftables table inet stockfw_intel for threat intel, with the log prefix STOCKFW-TI. nft list ruleset shows all of it.

Backing up

Copy the two directories. Restoring the policy directory onto another machine and pressing Apply reproduces the firewall there; the journal will count every rule as added, which is correct. The baselines and the audit log are per machine and worth keeping for their history, not for restoring.
