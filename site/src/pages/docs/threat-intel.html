Threat-intel blocklists

A policy says what you allow. A blocklist says what the wider community has seen attacking, hosting botnet controllers or spraying brute-force logins, as address ranges that are refused on sight. 1.0.7 brings well-known feeds into StockFW, off until you turn each one on, with the same discipline as the rest of the app: nothing silent, nothing that cannot be undone, and the kernel’s real state shown rather than the configuration.

Where this stands

The address-range engine and the path from a list file to an nftables set are built and tested [[built]]. Feeds, downloads, consent, the Threat Intel page, stockfw intel and list-attributed events are being written for the Linux release of 1.0.7 [[soon]]. Windows enforcement follows once the Windows build has been checked on a real machine [[planned]]. Until then every Windows surface says blocklists are not available there yet. The design, with its review findings, is docs/1.0.7-threat-intel-design.md in the repository.

The feeds

Every feed is off until you switch it on and accept its terms. A feed is fetched from its own publisher or not at all: no mirrors, no aggregator of StockFW’s own. Each entry carries the host it contacts, its information and terms pages, the licence where it has been verified (otherwise “See the provider’s terms”), whether it is for non-commercial use only, its format, its default direction and how often it updates.

A custom feed is any URL that passes the URL rule, with a name, a format and a direction; typing the URL is your consent for that host. A local list is a CSV or plain file you import yourself, with no network involved.

Direction means what it means for Windows’ stateful rules: in stops them connecting to you, out stops you connecting to them, both does both. Replies to connections you opened are never affected by an in list.

Consent

The first time you turn a feed on, a dialog says which host will be contacted and how often, what that host learns (your public address and the string StockFW/version), the licence and a link to the terms, and that lists contain mistakes and how to make an exception. Only after Accept does anything download. Updates run hourly in the desktop app and from stockfw intel update for cron or a timer; a failed or refused update never removes the previous copy.

What a feed is checked for

A downloaded file is text from the internet and is treated as hostile until it has passed every guard: a 64 MB size cap before it is read; strict parsing (addresses, CIDRs and a-b ranges, never names); no single IPv4 interval wider than a /8 and no IPv6 interval wider than a /16; no more than an eighth of the IPv4 space in one list; a list that is empty or mostly unparseable is refused and the set keeps what it had; and a sudden shrink is judged against the previous size. Content dates are read where a format has one, and a list older than seven update intervals is marked stale. [[verified:test-intel.c]]

What can never be blocked

Before anything reaches the kernel, the engine subtracts from every set, and lists in its notes what it subtracted:

  • loopback, link-local, multicast, the private ranges, carrier NAT, the reserved and documentation ranges, and the NAT64 prefixes;
  • your own exceptions;
  • this computer’s own addresses, its connected prefixes and its default gateways;
  • the DNS servers in use, read from /etc/resolv.conf and, when those are loopback stubs, from systemd-resolved’s and NetworkManager’s real lists;
  • the peer of your SSH session and every established inbound SSH connection, so a list cannot lock you out of the machine you are configuring it on;
  • the feeds’ own hosts, so a list cannot block its own updates.

Then, for sets that block outbound, each IPv4 interval is also added to the IPv6 set inside 64:ff9b::/96, so NAT64 does not bypass the list. Over all sets there are at most 300,000 intervals; above that the build fails and names the largest sets.

How it reaches the kernel

[[linux]] One nftables table, inet stockfw_intel, owned by StockFW and replaced in a single nft -f - transaction, so it applies whole or not at all and a failed apply leaves the previous table in force. The script goes to nft on standard input through GSubprocess; no shell ever sees an address. Three base chains at priority filter - 10 run before the iptables policy, so a listed address is refused even if a policy rule would have allowed it. Inbound drops are silent to the outside; outbound blocks reject with administratively prohibited, so a local program fails at once instead of hanging. Each blocking rule logs with the prefix STOCKFW-TI list, rate-limited, and carries a counter. [[verified:test-nftset.sh]]

The policy and the lists never touch each other’s tables. Applying, reloading or clearing the policy leaves the threat-intel table alone. The user-facing Stop firewall suspends the lists as well, and Start resumes them, because “stop the firewall” should mean what it says. On Linux nothing survives a reboot, policy or lists, until Start is pressed; the page and the FAQ say so.

What the kernel is really doing

The table carries a digest of the rule set that produced it. Every surface compares the live table with what StockFW last applied and shows one of these states, never just the configuration:

StateMeaning
offThe master switch is off, or no list is enabled.
enforcedThe live table is the one StockFW last applied.
not loadedSomething should be enforced but the table is missing: a reboot, or someone ran nft flush ruleset.
differsA table is there, but not the one StockFW applied.
suspendedYou stopped the firewall, so the lists are off on purpose.
unsupported, needs root, unknownCannot enforce here, cannot read the kernel, cannot tell.

Counters survive updates: before a set is replaced, its live count is added to the list’s carried total, so “blocked 1,204 since 3 November” stays true.

Where it shows up

  • Threat Intel page: the state in words, the master switch, each feed with its licence, direction, entry count, content age, status and blocks; Update now and Apply; local lists; exceptions; a lookup box; the notes from the last build.
  • Events: a block by a list shows the list’s name as its rule. For such an address the right-click Allow becomes Add exception, because an allow rule would not beat the list.
  • Overview: one line with the state and how many lists are enforced.
  • What-if: an address the policy allows but a list blocks is answered “Blocked by threat intel: list”.
  • Command line: stockfw intel status | feeds | enable | disable | update | apply | clear | import | remove | except | unexcept | exceptions | lookup | on | off, each with --json; stockfw status gains an intel object.
  • Audit log: every apply, update, consent, exception and suspend is a line.

Files

[[linux]] /var/lib/stockfw/intel/, owned by root, mode 0700: intel.conf (switches, feeds, custom feeds, local lists, exceptions), one .list and one .state per list, and applied.state for what the kernel was last given. Files are opened without following symlinks, read with a size cap, and written to a fresh name then renamed. A stored list is re-checked against the guards when loaded, so a tampered file is an error, not a block.
