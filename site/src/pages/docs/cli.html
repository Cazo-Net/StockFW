Command line

stockfw is the desktop app without the display: the same policy files, the same simulator, the same apply gate. A rule added here is the rule the Policy page shows, and an apply here writes the same audit line. [[linux]] There is no Windows command line; on Windows, use the app.

Usage: stockfw [--json] [--no-color] [-q] <command> [arguments]

StockFW from the command line: the same policy, simulator and apply
gate as the desktop app, without a display.

Commands:
  status                     Firewall state, policy and monitoring at a glance
  policy list|add|remove     Read and edit the traffic policy
  apply [--dry-run]          Push the saved policy to the firewall (root)
  start | stop               Start or stop the firewall (root)
  simulate "<traffic>"       What-if: would this traffic be allowed or blocked?
  events [-n N] [-f]         Recent firewall events; -f follows live (root)
  connections                Active TCP connections and their programs
  interfaces [--watch]       Network adapters with traffic counters and rates
  dashboard [--port N]       Serve the local web dashboard and open it
  help [command]             Help for one command
  version                    Print the version

Global options:
  --json        Machine-readable output (one JSON document; NDJSON for -f)
  --no-color    Plain output (also honoured: NO_COLOR, TERM=dumb, pipes)
  -q, --quiet   Only errors and the essential result
  -h, --help    This help;  -V, --version  the version

Exit status:
  0  success          2  usage error           5  simulate: BLOCKED
  1  failure          3  needs root privileges
                                               6  simulate: DEPENDS

Policy files live in ~/.stockfw (or /etc/stockfw when run as root) --
the same files the desktop app edits.  Nothing here talks to the
network: the dashboard listens on 127.0.0.1 only.

Before you start: whose policy?

As your own user the policy lives in ~/.stockfw; as root, in /etc/stockfw. A rule added without sudo is not the rule sudo stockfw apply pushes. Pick one identity and keep to it; the simplest is sudo for everything, so the app, the command line and the firewall all read /etc/stockfw. For a script that must not depend on who runs it, set STOCKFW_RULES_DIR. sudo on Debian and Kali does not search /usr/local/bin, so write sudo /usr/local/bin/stockfw or add an alias. See Install on Linux.

policy list, add, remove

$ sudo stockfw policy add inbound-allow-service SSH 22 192.168.1.0/24 --comment "admin LAN"
+ inbound-allow-service SSH 22 192.168.1.0/24
Saved in /etc/stockfw.  Not live yet: run `sudo stockfw apply'.

$ sudo stockfw policy add outbound-allow-to 192.0.2.10 --both --comment "backup server"
+ outbound-allow-to 192.0.2.10
+ inbound-allow-from 192.0.2.10
Saved in /etc/stockfw.  Not live yet: run `sudo stockfw apply'.

$ sudo stockfw policy list

    1  Web  port 8080 -> 192.168.1.30:80  [IPv4 only]  # lab box

    1  192.0.2.10  [IPv4 only]  # backup server
outbound-deny-to (1)
    1  198.51.100.66  [IPv4 only]  # known bad host

$ sudo stockfw policy remove outbound-deny-to 1
- outbound-deny-to 198.51.100.66
Saved.  Not live yet: run `sudo stockfw apply'.

The kinds and their fields are those of the Policy page: inbound-allow-from HOST, inbound-allow-service SERVICE PORT FOR, inbound-forward SERVICE FIREWALL-PORT TO PORT, outbound-allow-to HOST, outbound-allow-from HOST, outbound-allow-service SERVICE PORT FOR, outbound-deny-to HOST, outbound-deny-from HOST, outbound-deny-service SERVICE PORT FOR. FOR is a host, a network or Anyone. --both adds the opposite-direction twin of an allow rule as one change. N in remove is the number printed by list. --kind KIND narrows the list.

Validation fails closed, with the same rules as the app:

$ stockfw policy add inbound-allow-service SSH 80abc Anyone
stockfw: error: not a valid inbound-allow-service rule: check the host, port or range
stockfw: hint: hosts are addresses, networks (10.0.0.0/8) or "Anyone"; ports are 1-65535 or a range 1024:2048
$ echo $?
2

policy list --json gives every rule with its kind, number, fields, comment, covers (["ipv4"], ["ipv6"] or both) and covers_why, the sentence the Policy page shows as a tooltip:

{"kind":"inbound-allow-service","number":1,"service":"SSH","port":"22",
 "target":"192.168.1.0/24","to":null,"to_port":null,"comment":"admin LAN",
 "covers":["ipv4"],
 "covers_why":"192.168.1.0/24 is an IPv4 range, so the rule covers IPv4 only. Add a second rule for the IPv6 range if there is one."}

apply, start, stop

$ sudo stockfw apply --dry-run
Would apply: +1 added (1 allow, 0 block), -0 removed (0 allow, 0 block), =8 unchanged
Nothing was changed (dry run).

$ sudo stockfw apply
Applied (only the changes): +1 added (1 allow, 0 block), -0 removed (0 allow, 0 block), =8 unchanged

$ sudo stockfw apply
Nothing to change: the policy already matches the firewall.

apply goes through the gate described on the Policy page: only what changed is touched, a refused apply is rolled back to the last applied policy and the rollback is verified, and every attempt is one audit line with the source cli. When Audit-only or Lock is on in the app, apply records the change and leaves the firewall alone: “Held: audit-only mode is on. The firewall was left untouched.” Notes from the engine (“IPv6 is not filtered: ip6tables is not installed”) are printed after the result. start builds the firewall from the saved policy and starts it; stop removes StockFW’s own chains and nothing else. All three need root and exit 3 without it.

5

Exit 0 means ALLOWED, 5 BLOCKED and 6 DEPENDS, so a script can branch without parsing; 2 means the line could not be read. The plain output is the window in text: the verdict in a sentence, how the line was read with a confidence, then for each direction the trace (- skipped, * a note, => the deciding step) and the checked fixes in brackets. The JSON carries the same, with read_as, and under answers every direction’s trace, cases and actions, each action with the exact policy row it would write. The sentence grammar is on the simulator page. Simulating reads the saved policy and needs no root; reading whether the firewall is running does, so --assume-running answers for the firewall as it would run.

if ! stockfw simulate "inbound https from 0.0.0.0/0" >/dev/null; then
    echo "port 443 would be closed; refusing to deploy" >&2
    exit 1
fi

[{"time":"2026-11-02T16:41:09Z","direction":"out","source":"192.168.1.20","destination":"203.0.113.7","port":"23","protocol":"TCP","service":"Telnet","in":"","out":"eth0","blocked":true}]

The last N events (default 20) that StockFW’s rules logged, read from the kernel log, which remains the archive. -f follows until Ctrl-C and, with --json, prints one object per line. --blocked shows only blocks. Reading the kernel log needs root or the adm group. Allowed rows appear when the policy logs the first packet of each new allowed connection, which Log allowed connections in Preferences turns on.

The same connection table and adapter counters the Overview shows, with direction decided by what is listening. interfaces --watch refreshes every second. Programs owned by other users are readable only as root; the cell reads ? otherwise.

dashboard

stockfw dashboard [--port N] [--no-open] serves the local dashboard and opens it in your browser. There is deliberately no --bind.

Output conventions

  • --json prints one JSON document per command, or one object per line for events -f and interfaces --watch. Keys are stable across releases; new keys may be added.
  • Colour is off when the output is not a terminal, when NO_COLOR is set or TERM=dumb, or with --no-color.
  • Errors go to standard error as stockfw: error: …, usually followed by stockfw: hint: … saying what to do.
  • -q keeps only the essential line.

Environment variables

VariableEffect
STOCKFW_RULES_DIRWhere the policy and applied.csv live, regardless of who runs the program. The app honours it too.
STOCKFW_AUDIT_FILEThe audit log, instead of audit.log next to the preferences.
STOCKFW_TRUST_FILEThe Trust baseline, instead of trust.csv.
STOCKFW_AUTOBLOCK_FILESentinel’s staging record.
STOCKFW_LOG_FILERead events from this file instead of the kernel ring buffer (for tests and relocated logs).
STOCKFW_ASSUME_IPV61 loads the IPv6 payload on a kernel without an IPv6 stack (tests).
XDG_CONFIG_HOMEWhere stockfw/stockfw.conf and the logs go, as usual.
NO_COLORPlain output.

intel

stockfw intel manages threat-intel blocklists and country and network-owner sets: status, feeds, enable, disable, update, apply, clear, import, remove, except, unexcept, exceptions, lookup, on and off, each with --json. enable shows the feed’s terms and records your consent before anything is downloaded. status gains an intel object, and simulate answers “Blocked by threat intel: list” for an address a list covers. Changing the sets needs root, like every other change to the kernel.
