Command line

stockfw is the desktop app without the display: the same policy files, the same simulator, the same apply gate. A rule added here is the rule the Policy page shows, and an apply here writes the same audit line. [[linux]] There is no Windows command line; on Windows, use the app.

Usage: stockfw [--json] [--no-color] [-q] <command> [arguments]

StockFW from the command line: the same policy, simulator and apply
gate as the desktop app, without a display.

Commands:
  status                     Firewall state, policy and monitoring at a glance
  policy list|add|remove     Read and edit the traffic policy
  apply [--dry-run]          Push the saved policy to the firewall (root)
  start | stop               Start or stop the firewall (root)
  simulate "<traffic>"       What-if: would this traffic be allowed or blocked?
  copilot health             Check the policy for overlaps, conflicts, risky allows
  events [-n N] [-f]         Recent firewall events; --history for saved ones
  connections                Active TCP connections and their programs
  interfaces [--watch]       Network adapters with traffic counters and rates
  intel <action>             Threat-intel blocklists (stockfw help intel)
  dashboard [--port N]       Serve the local web dashboard and open it
  help [command]             Help for one command
  version                    Print the version

Global options:
  --json        Machine-readable output (one JSON document; NDJSON for -f)
  --no-color    Plain output (also honoured: NO_COLOR, TERM=dumb, pipes)
  -q, --quiet   Only errors and the essential result
  -h, --help    This help;  -V, --version  the version

Exit status:
  0  success          2  usage error           5  simulate: BLOCKED;
  1  failure          3  needs root privileges    intel lookup: blocked
                                               6  simulate: DEPENDS
                                               7  copilot health: findings

Policy files live in ~/.stockfw (or /etc/stockfw when run as root) --
the same files the desktop app edits.  Nothing here talks to the
network, except `stockfw intel update' downloading the blocklists and
the location database you turned on; the dashboard listens on
127.0.0.1 only.

Before you start: whose policy?

As your own user the policy lives in ~/.stockfw; as root, in /etc/stockfw. A rule added without sudo is not the rule sudo stockfw apply pushes. Pick one identity and keep to it; the simplest is sudo for everything, so the app, the command line and the firewall all read /etc/stockfw. For a script that must not depend on who runs it, set STOCKFW_RULES_DIR. sudo on Debian and Kali does not search /usr/local/bin, so write sudo /usr/local/bin/stockfw or add an alias. See Install on Linux.

policy list, add, remove

$ sudo stockfw policy add inbound-allow-service SSH 22 192.168.1.0/24 --comment "admin LAN"
+ inbound-allow-service SSH 22 192.168.1.0/24
Saved in /etc/stockfw.  Not live yet: run `sudo stockfw apply'.

$ sudo stockfw policy add outbound-allow-to 192.0.2.10 --both --comment "backup server"
+ outbound-allow-to 192.0.2.10
+ inbound-allow-from 192.0.2.10
Saved in /etc/stockfw.  Not live yet: run `sudo stockfw apply'.

$ sudo stockfw policy remove outbound-deny-to 1
- outbound-deny-to 198.51.100.66
Saved.  Not live yet: run `sudo stockfw apply'.

The kinds and their fields are those of the Policy page: inbound-allow-from HOST, inbound-allow-service SERVICE PORT FOR, inbound-forward SERVICE FIREWALL-PORT TO PORT, outbound-allow-to HOST, outbound-allow-from HOST, outbound-allow-service SERVICE PORT FOR, outbound-deny-to HOST, outbound-deny-from HOST, outbound-deny-service SERVICE PORT FOR. FOR is a host, a network or Anyone. --both adds the opposite-direction twin of an allow rule as one change. N in remove is the number printed by list. --kind KIND narrows the list.

Validation fails closed, with the same rules as the app:

$ stockfw policy add inbound-allow-service SSH 80abc Anyone
stockfw: error: not a valid inbound-allow-service rule: check the host, port or range
stockfw: hint: hosts are addresses, networks (10.0.0.0/8) or "Anyone"; ports are 1-65535 or a range 1024:2048
$ echo $?
2

policy list --json gives every rule with its kind, number, fields, comment, covers (["ipv4"], ["ipv6"] or both) and covers_why, the sentence the Policy page shows as a tooltip:

{"kind":"inbound-allow-service","number":1,"service":"SSH","port":"22",
 "target":"192.168.1.0/24","to":null,"to_port":null,"comment":"admin LAN",
 "covers":["ipv4"],
 "covers_why":"192.168.1.0/24 is an IPv4 range, so the rule covers IPv4 only. Add a second rule for the IPv6 range if there is one."}

apply, start, stop

$ sudo stockfw apply --dry-run
Would apply: +1 added (1 allow, 0 block), -0 removed (0 allow, 0 block), =8 unchanged
Nothing was changed (dry run).

$ sudo stockfw apply
Applied (only the changes): +1 added (1 allow, 0 block), -0 removed (0 allow, 0 block), =8 unchanged

$ sudo stockfw apply
Nothing to change: the policy already matches the firewall.

apply goes through the gate described on the Policy page: only what changed is touched, a refused apply is rolled back to the last applied policy and the rollback is verified, and every attempt is one audit line with the source cli. When Audit-only or Lock is on in the app, apply records the change and leaves the firewall alone: “Held: audit-only mode is on. The firewall was left untouched.” Notes from the engine (“IPv6 is not filtered: ip6tables is not installed”) are printed after the result. start builds the firewall from the saved policy and starts it; stop removes StockFW’s own chains and nothing else. All three need root and exit 3 without it.

Exit 0 means ALLOWED, 5 BLOCKED and 6 DEPENDS, so a script can branch without parsing; 2 means the line could not be read. The plain output is the window in text: the verdict in a sentence, how the line was read with a confidence, then for each direction the trace (- skipped, * a note, => the deciding step) and the checked fixes in brackets. The JSON carries the same, with read_as, and under answers every direction’s trace, cases and actions, each action with the exact policy row it would write. The sentence grammar is on the simulator page. Simulating reads the saved policy and needs no root; reading whether the firewall is running does, so --assume-running answers for the firewall as it would run.

if ! stockfw simulate "inbound https from 0.0.0.0/0" >/dev/null; then
    echo "port 443 would be closed; refusing to deploy" >&2
    exit 1
fi

[{"time":"2026-11-02T16:41:09Z","direction":"out","source":"192.168.1.20","destination":"203.0.113.7","port":"23","protocol":"TCP","service":"Telnet","in":"","out":"eth0","blocked":true}]

The last N events (default 20, up to 1,000,000) that StockFW’s rules logged, oldest first, read from the kernel log. -f follows until Ctrl-C and, with --json, prints one object per line. Reading the kernel log needs root or the adm group. Allowed rows appear when the policy logs the first packet of each new allowed connection, which Log allowed connections in Preferences turns on.

--history reads the history the desktop app saves instead, from ~/.local/share/stockfw/events, so no root is needed; under sudo that is root’s history, and --history-dir DIR reads another folder. The filters are the ones the Events page has, and all of them must match:

$ stockfw events --history --since 1d --port 22 --dir in
$ stockfw events --history -n 1000 --addr 203.0.113.0/24 --json

  --since T, --until T  15m, 2h, 3d, 1w, now, 2026-11-01, "2026-11-01 14:30", or ISO with Z;
                        --until with a date takes in that whole day
  --grep TEXT           a column of the Events list contains TEXT, any case
  --dir in|out          the direction
  --proto P             TCP, UDP, ICMP...
  --port P              443, 1000-2000 or 1000:2000
  --addr A              source or destination in A: an address, a CIDR block or a-b
  --blocked, --allowed  the verdict

With no saved history the command says so and points at the Preferences switch that turns it on.

copilot health

$ stockfw copilot health
9 rules checked, 1 finding

[info] 1 outbound allow rule has no effect in this mode
  rule:  outbound_allow_to #1: 192.0.2.10, backup server
  why:   Outbound traffic is allowed by default (restrictive outbound is off in the Firewall preferences), so outbound allow rows change nothing until it is turned on. This is expected for the default policy.
  no fix offered: the rows are right as they are, and take effect when restrictive outbound is turned on.
A check only: nothing was written. Fixes are made on the Copilot page.
$ echo $?
7

The policy health check of the Copilot page, on the saved policy: duplicates, shadowed rows, allows a deny makes unreachable, outbound allows that do nothing in the current mode, broad or risky inbound allows from anyone, and deny rules that reach no address family. It writes nothing; fixes are made on the Copilot page. Exit 0 means no findings, 7 findings, and 2 a policy that could not be read in full. With --json each finding carries kind, severity, title, rule (with index from 0 and the row’s csv), why, evidence, whatif, and either fix with its before and after rows and the What-If checks that verified it, or no_fix_reason. dashboard

stockfw dashboard [--port N] [--no-open] serves the local dashboard and opens it in your browser. There is deliberately no --bind.

Output conventions

  • --json prints one JSON document per command, or one object per line for events -f and interfaces --watch. Keys are stable across releases; new keys may be added.
  • Colour is off when the output is not a terminal, when NO_COLOR is set or TERM=dumb, or with --no-color.
  • Errors go to standard error as stockfw: error: …, usually followed by stockfw: hint: … saying what to do.
  • -q keeps only the essential line.

intel

stockfw intel [status]                     State, and the lists turned on
stockfw intel feeds                        Every feed: on/off, licence, credit, entries, last update
stockfw intel terms FEED                   What turning FEED on means
stockfw intel enable ID [--direction D] [--accept-terms]
stockfw intel disable ID
stockfw intel on | off                     The master switch
stockfw intel add-feed NAME URL [--format F] [--direction D]
stockfw intel proxy [URL|none]             The download proxy
stockfw intel update [--feed ID] [--now] [--accept-shrink] [--accept-coverage] [--no-apply]
stockfw intel apply [--dry-run]            Load the lists into the kernel
stockfw intel clear                        Remove them from the kernel
stockfw intel import FILE --name NAME [--direction D]
stockfw intel lists | list show [ID]       Your own lists (and one's ranges)
stockfw intel remove ID                    A local list or custom feed
stockfw intel except | unexcept ADDRESS... Never block / block again
stockfw intel exceptions
stockfw intel lookup ADDRESS               Which lists hold it; blocked?
stockfw intel geo [status]                 Blocking by country or network
stockfw intel geo terms | on [--accept-terms] | off
stockfw intel geo update [--no-apply]      Download the location database
stockfw intel geo search TEXT [--max N]    Find country codes and AS numbers
stockfw intel geo add country|asn VALUE... [--dir D] [--name NAME]
stockfw intel geo list | remove ID         The country and network rules

stockfw intel manages threat-intel blocklists and country and network rules, each command with --json. Every feed is off until you turn it on: terms says which host a feed is downloaded from, how often, what that host learns and its licence, and enable records your consent before anything is downloaded. update fetches the feeds that are due (--now: all of them) and, when the lists are enforced and audit-only is off, puts the new copies in force; a copy that shrank to almost nothing or rolled back to an older date is refused unless --accept-shrink, and one whose coverage jumped needs --accept-coverage. D is in, out or both. A proxy with a user name or password is refused, because curl’s command line is readable by every local user.

intel geo blocks by the country a range is registered in, or by the network that owns it, from IPFire’s signed location database; it is off until geo on --accept-terms, and intel update then downloads the database at most once a day. lookup exits 5 when the address is blocked, and simulate answers from the policy alone, so it does not consult the lists. Changing the sets needs root, like every other change to the kernel. [[verified:test-intel-cli.sh]]

The app’s own flags

  -V, --version            Show the program version and exit
  -b, --background         Start in the notification area with the window hidden
                           (it is shown if no notification area takes the icon)
  -m, --minimized          Same as --background
  --quit                   Ask the running StockFW to quit (the firewall stays on)
  --enable-autostart       Start StockFW in the background when you sign in, then exit
  --disable-autostart      Stop starting StockFW when you sign in, then exit

These belong to the desktop program, StockFW, on Windows and Linux alike. A second launch brings the running copy’s window forward instead of starting another; a launch with more rights takes over from it. See Background, tray and sign-in. [[verified:test-instance.sh]]
