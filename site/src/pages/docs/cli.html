Command line

stockfw is the desktop app without the display: the same policy files, the same simulator, the same apply gate. A rule added here is the rule the Policy page shows, and an apply here writes the same audit line. It is the tool for a server, an SSH session or WSL, where there is no window to open. [[linux]] There is no Windows command line; on Windows, use the app.

Usage: stockfw [--json] [--plain] [--color=WHEN] [-q] <command> [args]

StockFW from the command line: the same policy, simulator and apply
gate as the desktop app, without a display.

Commands:
  status                     Firewall state, policy and monitoring
  policy list|show|add|...   Read, edit and diff the traffic policy
  check                      Lines of the policy files that are not rules
  apply [--dry-run]          Push the saved policy to the firewall (root)
  start | stop               Start or stop the firewall (root)
  simulate "<traffic>"       What-if: would this traffic be allowed?
  copilot health             Check the policy for overlaps and risks
  events [-n N] [-f]         Recent firewall events; --history for saved
  connections                Active TCP connections and their programs
  listening                  Open ports, their programs and who can reach them
  interfaces [--watch]       Network adapters with traffic and rates
  audit [-n N] [-f]          The audit log: every apply, start and stop
  sentinel [list]            Sentinel's staged blocks (read-only)
  intel <action>             Threat-intel blocklists (stockfw help intel)
  dashboard [--port N]       Serve the local web dashboard and open it
  help [command]             Help for one command
  version                    Print the version

Global options:
  --json          Machine-readable output (one JSON document; NDJSON
                  for -f)
  --plain, -H     Tables as tab-separated rows, no header, no colour
  --full, -l      Never cut a table cell to fit the terminal
  --color=WHEN    auto (the default), always or never; --no-color is
                  never (NO_COLOR and TERM=dumb are honoured too)
  -q, --quiet     Only errors and the result: no hints or notes
  -h, --help      This help;  -V, --version  the version
  --              The end of the options: what follows is plain words

Exit status:
  0  success          2  usage error           5  simulate: BLOCKED;
  1  failure          3  needs root privileges    intel lookup: blocked
                                               6  simulate: DEPENDS
                                               7  copilot health: findings

Policy files live in ~/.stockfw (or /etc/stockfw when run as root) --
the same files the desktop app edits.  Nothing here talks to the
network, except `stockfw intel update' downloading the blocklists and
the location database you turned on; the dashboard listens on
127.0.0.1 only.

Before you start: whose policy?

As your own user the policy lives in ~/.stockfw; as root, in /etc/stockfw. A rule added without sudo is not the rule sudo stockfw apply pushes. Pick one identity and keep to it; the simplest is sudo for everything, so the app, the command line and the firewall all read /etc/stockfw. For a script that must not depend on who runs it, set STOCKFW_RULES_DIR. On Fedora, RHEL and some Kali systems sudo does not search /usr/local/bin (Ubuntu’s default does), so write sudo /usr/local/bin/stockfw there, or add an alias; a hint that needs root always prints the full path, so you can paste it. See Install on Linux.

How options are read

The word after an option that takes a value is that value: --comment -h saves the comment -h. Everything after -- is a plain word, so a host or comment that starts with a dash goes after it, or as --comment=TEXT. An option a command does not know is refused with exit 2, never ignored and never folded into a simulate question. A mistyped command or option gets a suggestion:

$ stockfw polcy list
stockfw: error: unknown command: polcy (did you mean `stockfw policy'?)
stockfw: hint: run `stockfw help' for the list of commands
$ stockfw simulate "inbound rdp" --bogus
stockfw: error: unknown option for simulate: --bogus
stockfw: hint: see `stockfw help simulate'; a word that starts with a dash goes after --
$ echo $?
2

Tables are fitted to the terminal, and only to the terminal: a pipe or a file gets every character, --full never cuts a cell, and --plain prints tab-separated rows with no header for cut and awk. Text that came from a log or a comment is escaped before it reaches your terminal: control characters and bidi controls print as \xNN or \uNNNN, in every table, in events --csv, in the rule names of simulate and in the list names of intel. Symbols fall back to ASCII outside a UTF-8 locale. [[verified:test-cli.sh]]

$ stockfw status -q
running, live

The Policy line says whether what you saved is what is live: “9 rules, live”, “1 change not applied (stockfw policy diff)”, “never applied”, or “settings changed since the last apply” when the Firewall preferences you saved are not the ones that went out. Last apply is the newest apply, start or stop in the audit log, with cli or gui. Blocked counts since local midnight, from the saved event history while it is kept and otherwise from the kernel log. Monitoring is decided by what your account can actually read, tried rather than guessed from your user id: a user in the adm group sees “reading /var/log/kern.log”. At boot says whether stockfw.service is enabled, installed but off, or absent. Reading the firewall state needs root; without it the state is unknown, not guessed. -v adds the rules directory, the firewall settings (outbound mode, DROP or REJECT, ICMP, logging, interfaces, NAT), the event history and Sentinel. With --json the 1.0.7 keys are unchanged and new ones are added: live (live, pending, never…) with pending counts, last_apply, blocked_today with last_block, monitoring with its source, boot_unit and host. Every rule has a reference, KIND:N, numbered as policy list shows it; KIND#N and KIND N work too. show prints one rule with what it covers and whether it is live. add and remove echo the reference and run a What-If check of the rule’s own traffic on the saved policy, so you see at once that the rule does what you meant. list takes a kind, in or out, --grep TEXT for the rows that hold TEXT, and --status to mark each row live or pending. diff shows the saved policy against the applied one: + rows to add, - rows to take away, numbered as applied.

The kinds and their fields are those of the Policy page: inbound-allow-from HOST, inbound-allow-service SERVICE PORT FOR, inbound-forward SERVICE FIREWALL-PORT TO PORT, outbound-allow-to HOST, outbound-allow-from HOST, outbound-allow-service SERVICE PORT FOR, outbound-deny-to HOST, outbound-deny-from HOST, outbound-deny-service SERVICE PORT FOR. FOR is a host, a network or Anyone. --both adds the opposite-direction twin of an allow rule as one change.

Validation fails closed, with the same rules as the app:

$ stockfw policy add inbound-allow-service SSH 80abc Anyone
stockfw: error: not a valid inbound-allow-service rule: check the host, port or range
stockfw: hint: hosts are addresses, networks (10.0.0.0/8) or "Anyone"; ports are 1-65535 or a range 1024:2048
$ echo $?
2

policy list --json gives every rule with its kind, number, ref, fields, comment, covers (["ipv4"], ["ipv6"] or both) and covers_why, the sentence the Policy page shows as a tooltip. The same rule_ref names the deciding rule in simulate --json and copilot health --json. [[verified:test-cli.sh]]

1
$ sudo stockfw policy add outbound-deny-to 203.0.113.13
stockfw: error: /etc/stockfw/inbound/allow-service:3: port "99999" is out of range (1-65535): "SSH,99999,Anyone"
stockfw: error: /etc/stockfw/inbound/allow-service:4: expected NAME, PORT, FOR (no commas): "not a rule at all"
stockfw: hint: these lines are not rules and are left out; `stockfw check' lists them, apply refuses until they are fixed

stockfw: hint: fix or delete them in the file by hand, then run the command again

A line in a rule file that is not a rule is left out of the policy, and check names each one with its file, line and reason, exit 1. apply refuses such a policy, the dry run too (exit 2), and policy add and remove refuse as well, because saving would have deleted the line without a word. start still starts the last applied policy and only warns. SSH,,Anyone loads, because a known service needs no port. The check needs no root. [[verified:test-cli.sh]]

apply, start, stop

$ sudo stockfw apply --dry-run
Would apply: +1 added (1 allow, 0 block), -0 removed (0 allow, 0 block), =8 unchanged
+ inbound-allow-service:1  SSH  port 22  for 192.168.1.0/24  [IPv4 only]
= 8 rules unchanged
Nothing was changed (dry run).

$ sudo stockfw apply
Applied (only the changes): +1 added (1 allow, 0 block), -0 removed (0 allow, 0 block), =8 unchanged

$ sudo stockfw apply
Nothing to change: the policy already matches the firewall.

$ sudo stockfw stop
Firewall stopped.
$ sudo stockfw stop
Already stopped.
$ sudo stockfw apply --dry-run
The firewall is stopped: apply would load the whole policy (9 rules) and start it.
Would apply: +0 added (0 allow, 0 block), -0 removed (0 allow, 0 block), =9 unchanged
= 9 rules unchanged
Nothing was changed (dry run).
$ sudo stockfw apply
Applied (whole policy; the firewall was stopped and is now running): +0 added (0 allow, 0 block), -0 removed (0 allow, 0 block), =9 unchanged

apply goes through the gate described on the Policy page: only what changed is touched, a refused apply is rolled back to the last applied policy and the rollback is verified, and every attempt is one audit line with the source cli. An apply after a stop starts the firewall again with the whole policy, and the audit line says why (“full (firewall was stopped)”); the desktop app’s Apply shares the gate and so gets the same behaviour. When Audit-only is on in the app, apply records the change and leaves the firewall alone: “Held: audit-only mode is on. The firewall was left untouched.” --dry-run lists the rows it would add and remove and says which forwards would be left out; -v adds the chains it would write. start loads the last applied policy and starts the firewall, so saved changes you never applied stay off; stop removes StockFW’s own chains and nothing else. “Already running” and “Already stopped” write no audit line of their own, except that a stop on a stopped firewall still takes the threat-intel blocklists down and logs that as intel-suspend. All three need root and exit 3 without it. [[verified:test-cli.sh]] [[verified:test-apply-linux.sh]]

The lockout guard over SSH

$ sudo stockfw apply
stockfw: warning: this policy would block your SSH session
  from 192.168.1.50 to port 22: BLOCKED (no rule allows it)
Apply anyway? [y/N] n
stockfw: error: not done: the firewall was left as it was
$ sudo stockfw apply < /dev/null
stockfw: warning: this policy would block your SSH session
  from 192.168.1.50 to port 22: BLOCKED (no rule allows it)
stockfw: error: refused: pass --yes to apply anyway

Over SSH, apply and start ask the What-If engine whether the new policy still lets your session in before they touch anything. If it would not, they ask on a terminal, and without one (a script, a cron job) they refuse unless you pass --yes. It works under sudo, where SSH_CONNECTION is gone: your own session is found through the sshd it runs under and is always checked first, however many other SSH sessions the computer has, and sshd is found on any port, also when systemd starts it through ssh.socket. The addresses of SSH clients on every port sshd listens on are also in the set a threat-intel blocklist may never cut. [[verified:test-cli.sh]] [[verified:test-hostnet.c]]

simulate

$ stockfw simulate "allow ssh from 192.168.1.50 on port 22"
You asked to allow this. It is already ALLOWED. Rule inbound-allow-service:1 'StockFW: Allow SSH (inbound, 192.168.1.0/24) (TCP)' allows it.
Read as: you want it allowed; host 192.168.1.50; port 22; service SSH: TCP port 22; inbound (confidence 100%)

Inbound TCP port 22 (SSH) from 192.168.1.50 to this computer: ALLOWED
  Rule 'StockFW: Allow SSH (inbound, 192.168.1.0/24) (TCP)' allows it.
  How it was decided:
    - StockFW: Allow inbound (192.168.1.1): 192.168.1.50 is not 192.168.1.1
    => StockFW: Allow SSH (inbound, 192.168.1.0/24) (TCP): matches: allows it

$ echo $?
0

$ stockfw -q simulate "outbound tcp to 198.51.100.66 port 443"
BLOCKED
$ echo $?
5

Exit 0 means ALLOWED, 5 BLOCKED and 6 DEPENDS, so a script can branch without parsing; 2 means the line could not be read. With -q only the verdict word is printed. The plain output is the window in text: the verdict in a sentence with the deciding rule as KIND:N, how the line was read with a confidence, then for each direction the trace (- skipped, * a note, => the deciding step) and the checked fixes in brackets. The JSON carries the same, with read_as, rule_ref, and under answers every direction’s trace, cases and actions, each action with the exact policy row it would write. The sentence grammar is on the simulator page. Simulating reads the saved policy and needs no root; --applied asks the last applied policy instead; reading whether the firewall is running does need root, so --assume-running answers for the firewall as it would run. Sentinel’s staged blocks are part of the answer, with when each lifts. [[verified:test-whatif.c]] [[verified:test-cli.sh]]

The last N events (default 20, up to 1,000,000) that StockFW’s rules logged, oldest first (-r: newest first), read from the kernel log. Reading it needs root or the adm group. The RULE column names the threat-intel list that blocked an event, and is - for a policy rule. Well-known ports are named: 3389 is Remote Desktop and 161 SNMP, as on the Events page. --wide adds the full time with zone, the IN and OUT devices, length and ToS; --utc prints ISO times; --csv writes what the desktop app exports, with a header row and formulas made harmless. IPv6 addresses are shown short in the table and in full in a pipe. Allowed rows appear when the policy logs the first packet of each new allowed connection, which Log allowed connections in Preferences turns on.

The filters are the ones the Events page has, and all of them must match. --blocked with --allowed, or a --proto other than tcp, udp, icmp or icmpv6, is a usage error (exit 2) rather than the last flag winning:

  --since T, --until T  15m, 2h, 3d, 1w, now, 2026-11-01, "2026-11-01 14:30", or ISO with Z
                        (seconds optional: 2026-11-02T23:30Z); --until with a date takes in that whole day
  --grep TEXT           a column of the Events list contains TEXT, any case
  --dir in|out|both     the direction (inbound, outbound and --direction work too)
  --proto P             tcp, udp, icmp or icmpv6
  --port P              443, 1000-2000, 1000:2000, or a list: 22,443,8000:8100
  --addr A              source or destination in A: an address, a CIDR block or a-b
  --blocked, --allowed  the verdict (one of them)

Saved history

--history reads the history the desktop app saves instead, from ~/.local/share/stockfw/events, so no root is needed; under sudo that is root’s history, and --history-dir DIR reads another folder. A long history is streamed, never held in memory. With no saved history the command says so and points at the Preferences switch that turns it on.

$ stockfw events --history --since 1d --port 22,3389 --dir in
$ stockfw events --history -n 1000 --addr 203.0.113.0/24 --csv > scans.csv

$ sudo stockfw events -f
TIME             VERDICT  DIR  SOURCE         DESTINATION   PORT  SERVICE         PROTO  RULE
Nov 03 18:11:40  BLOCKED  in   203.0.113.5    192.168.1.20  3389  Remote Desktop  TCP    -

-f keeps printing new events in the table’s columns until Ctrl-C, which prints how many events were seen. On a terminal a status line on standard error sits under the rows and is redrawn after each event and every few seconds: the firewall state, whether the saved policy is live (or “changes pending”, “never applied”, “settings pending”), HELD (audit-only) while audit-only holds applies back, the blocks since midnight, Sentinel’s mode and how many blocks it has staged, and where the events come from. It is cut to the terminal’s width so it never wraps, and cleared before anything else is printed, so it is never left behind in your scrollback. --no-status-line turns it off, and it is never shown with --json, --csv, -q, TERM=dumb or in a pipe, so stockfw events -f --json | jq gets one event object per line and nothing else. When the event reader stops, -f says why and exits 1 instead of waiting forever. [[verified:test-cli.sh]]

audit

$ sudo stockfw audit -n 4
Audit log /root/.config/stockfw/audit.log  (212 lines, 2026-10-29 -> 2026-11-03)
TIME                 ACTION                   FROM  DETAIL
2026-11-03 18:11:57  policy applied           cli   full (firewall was stopped); +7 added (2 allow, 5 block), -0 removed (0 allow, 0 block), =0 unchanged
2026-11-03 18:11:57  policy apply: no change  cli   narrow; no change; +0 added (0 allow, 0 block), -0 removed (0 allow, 0 block), =7 unchanged
2026-11-03 18:11:57  firewall stopped         cli   stop; stopped
2026-11-03 18:11:57  policy applied           cli   full (firewall was stopped); +0 added (0 allow, 0 block), -0 removed (0 allow, 0 block), =7 unchanged

$ sudo stockfw audit --action apply --since 7d --json | jq -r '.entries[] | [.time, .detail] | @tsv'

The audit log that the Policy page appends to, read from the terminal: every apply, start and stop, and what threat intel, Sentinel, the health check and Trust did. The last N entries (default 20, 0 for all), oldest first; -r puts the newest first, --since and --until take the same time words as events, --action apply|start|stop|intel|sentinel|health|trust|policy keeps one kind, --grep TEXT keeps entries that hold TEXT, -f follows new entries (one object per line with --json), --utc prints ISO times and --file PATH reads another log. FROM is cli or gui where the line says so. The log is your account’s own (STOCKFW_AUDIT_FILE overrides it), so no root is needed; under sudo it is root’s. With --json: file, lines_total, bad_lines and the entries, each with time, epoch, action, origin, detail and the raw line. A damaged line is counted, never dropped silently. Exit 1 when there is no log yet. [[verified:test-cli.sh]]

Sentinel’s staged blocks, read from its state file and never changed: the address, the rule as a KIND:N reference while it is still in the policy, when it was staged, when it lifts (ten minutes later, or “due since …” once that has passed) and why. The header gives Sentinel’s mode, auto or detect. --json gives mode, file, ttl_seconds and the blocks. copilot health

$ stockfw copilot health
9 rules checked, 1 finding

[info] 1 outbound allow rule has no effect in this mode
  rule:  outbound-allow-to:1: 192.0.2.10, backup server
  why:   Outbound traffic is allowed by default (restrictive outbound is off in the Firewall preferences), so outbound allow rows change nothing until it is turned on. This is expected for the default policy.
  no fix offered: the rows are right as they are, and take effect when restrictive outbound is turned on.
A check only: nothing was written. Fixes are made on the Copilot page.
$ echo $?
7

$ stockfw copilot health --severity warning; echo $?
9 rules checked, 1 finding
[info] 1 outbound allow rule has no effect in this mode
  …
0

The policy health check of the Copilot page, on the saved policy: duplicates, shadowed rows, allows a deny makes unreachable, outbound allows that do nothing in the current mode, broad or risky inbound allows from anyone, and deny rules that reach no address family. It writes nothing; fixes are made on the Copilot page. Exit 0 means no findings, 7 findings, and 2 a policy that could not be read in full. --severity info|warning|critical sets the level that gives exit 7, so a deployment script can ignore notes and still stop on a warning. With --json each finding carries kind, severity, title, rule (with its rule_ref, index from 0 and the row’s csv), why, evidence, whatif, and either fix with its before and after rows and the What-If checks that verified it, or no_fix_reason. Every listening TCP socket and bound UDP socket, the program behind it, and whether the policy lets a LAN address and an internet address reach it, asked of the What-If engine with the rule that decides. A rule limited to other addresses can still let them in, so the verdict is for the sample address, not a promise for every host. Sockets only this computer can reach are counted and shown with --all; --tcp and --udp narrow the list; -q prints only the ports the internet can reach. Another user’s program needs root to be named; the cell reads ? otherwise. When the firewall is stopped the command says so once and answers for when it runs. dashboard

stockfw dashboard [--port N] [--no-open] serves the local dashboard and opens it in your browser. There is deliberately no --bind. When it is not run as root and a kernel log file is readable to your account, the dashboard follows that file itself, so monitoring works for a user in the adm group.

The manual page and completion

$ man stockfw
$ stockfw policy remove inbound-allow-<Tab>
inbound-allow-from:1     inbound-allow-service:1  inbound-allow-service:2
$ stockfw events --by=s<Tab>
src  service

stockfw(1) lists every command with its options, the global options, the exit codes, the environment variables and the files. stockfw writes the page itself from the same tables its parser reads, at build time, so it cannot fall behind the tool, and the build is reproducible: the page carries no date. Completion for bash and zsh asks stockfw too, and offers commands, options, values such as the --by keys and the TCP states, threat-intel feed ids, and the KIND:N references of your own saved rules. The Linux installer puts the page in /usr/local/share/man/man1/stockfw.1 and the scripts in /usr/local/share/bash-completion/completions/stockfw and /usr/local/share/zsh/site-functions/_stockfw; stockfw-uninstall removes all three. On a system whose shell does not load completions from /usr/local/share, source the bash script from your .bashrc, or add the zsh folder to fpath. [[verified:test-cli.sh]]

A build of the command line alone

$ cmake -S port -B build-cli -DFS_BUILD_GUI=OFF
$ cmake --build build-cli
$ sudo cmake --install build-cli

-DFS_BUILD_GUI=OFF builds stockfw and its manual page without GTK, and does not look for GTK at all, for a server that has no desktop libraries. The default still builds the desktop app too. The project’s own tests check that stockfw needs no GTK, GDK, Pango or cairo library. [[verified:test-nogui-build.sh]]

Output conventions

  • --json prints one JSON document per command, or one object per line for events -f, audit -f and interfaces --watch. Keys are stable across releases; new keys may be added, and 1.0.7’s keys are all still there.
  • Colour is decided by standard output alone: on when it is a terminal, off in a pipe, with NO_COLOR, TERM=dumb or --color=never; --color=always forces it on, even into a pipe.
  • --plain (-H) gives tab-separated rows without a header; --full (-l) never cuts a cell.
  • Errors go to standard error as stockfw: error: …, usually followed by stockfw: hint: … saying what to do, with the full path of the program when it needs root.
  • -q keeps only the essential line, leaves out hints, notes and legends, and with simulate prints only the verdict word.
  • stockfw version prints one line: stockfw {{version}} - Linux (iptables), or (nftables) for that backend.

intel

stockfw intel [status]                     State, and the lists turned on
stockfw intel feeds                        Every feed: on/off, licence, credit, entries, last update
stockfw intel terms FEED                   What turning FEED on means
stockfw intel enable ID [--direction D] [--accept-terms]
stockfw intel disable ID
stockfw intel on | off                     The master switch
stockfw intel add-feed NAME URL [--format F] [--direction D]
stockfw intel proxy [URL|none]             The download proxy
stockfw intel update [--feed ID] [--now] [--accept-shrink] [--accept-coverage] [--no-apply]
stockfw intel apply [--dry-run]            Load the lists into the kernel
stockfw intel clear                        Remove them from the kernel
stockfw intel import FILE --name NAME [--direction D]
stockfw intel lists | list show [ID]       Your own lists (and one's ranges)
stockfw intel remove ID                    A local list or custom feed
stockfw intel except | unexcept ADDRESS... Never block / block again
stockfw intel exceptions
stockfw intel lookup ADDRESS               Which lists hold it; blocked?
stockfw intel geo [status]                 Blocking by country or network
stockfw intel geo terms | on [--accept-terms] | off
stockfw intel geo update [--no-apply]      Download the location database
stockfw intel geo search TEXT [--max N]    Find country codes and AS numbers
stockfw intel geo add country|asn VALUE... [--dir D] [--name NAME]
stockfw intel geo list | remove ID         The country and network rules

stockfw intel manages threat-intel blocklists and country and network rules, each command with --json. Every feed is off until you turn it on: terms says which host a feed is downloaded from, how often, what that host learns and its licence, and enable records your consent before anything is downloaded. update fetches the feeds that are due (--now: all of them) and, when the lists are enforced and audit-only is off, puts the new copies in force; a copy that shrank to almost nothing or rolled back to an older date is refused unless --accept-shrink, and one whose coverage jumped needs --accept-coverage. D is in, out or both. A proxy with a user name or password is refused, because curl’s command line is readable by every local user. List and feed names are escaped like every other text from outside.

intel geo blocks by the country a range is registered in, or by the network that owns it, from IPFire’s signed location database; it is off until geo on --accept-terms, and intel update then downloads the database at most once a day. lookup exits 5 when the address is blocked, and simulate answers from the policy alone, so it does not consult the lists. Changing the sets needs root, like every other change to the kernel. [[verified:test-intel-cli.sh]]

The app’s own flags

  -V, --version            Show the program version and exit
  -b, --background         Start in the notification area with the window hidden
                           (it is shown if no notification area takes the icon)
  -m, --minimized          Same as --background
  --quit                   Ask the running StockFW to quit (the firewall stays on)
  --enable-autostart       Start StockFW in the background when you sign in, then exit
