Command line

stockfw is the desktop app without the display: the same policy files, the same settings, the same simulator, the same apply gate. A rule added here is the rule the Policy page shows, a setting changed here is the one the Preferences window shows, and an apply here writes the same audit line. It is the tool for a server, an SSH session or WSL, where there is no window to open. [[linux]] There is no Windows command line; on Windows, use the app.

Usage: stockfw [--json] [--plain] [--color=WHEN] [-q] <command> [args]

StockFW from the command line: the same policy, simulator and apply
gate as the desktop app, without a display.

Commands:
  status                     Firewall state, policy and monitoring
  policy list|show|add|...   Read, edit and diff the traffic policy
  check                      Lines of the policy files that are not rules
  apply [--dry-run]          Push the saved policy to the firewall (root)
  start | stop               Start or stop the firewall (root)
  simulate "<traffic>"       What-if: would this traffic be allowed?
  copilot health|scan|...    Policy health, findings, fixes, undo
  events [-n N] [-f]         Recent firewall events; --history for saved
  connections                Active TCP connections and their programs
  listening                  Open ports, their programs and who can reach them
  interfaces [--watch]       Network adapters with traffic and rates
  audit [-n N] [-f]          The audit log: every apply, start and stop
  sentinel [list|lift|mode]  Sentinel's blocks: list or lift; its mode
  intel <action>             Threat-intel blocklists (stockfw help intel)
  config list|get|set|apply  The Preferences settings; set them (root)
  trust [list|check|...]     Files you attested: changed since? (per user)
  dashboard [--port N]       Serve the local web dashboard and open it
  dashboard link             A new link to the running dashboard

  help topics | TOPIC        The guide: each page and setting explained
  about [--system]           Version, credits, licence; bug report lines

Global options:

  --full, -l      Never cut a table cell to fit the terminal
  --color=WHEN    auto (the default), always or never; --no-color is

  -h, --help      This help;  -V, --version  the version

  0  success          2  usage error           5  simulate: BLOCKED;

Policy files live in ~/.stockfw (or /etc/stockfw when run as root) --
the same files the desktop app edits.  Nothing here talks to the
network, except `stockfw intel update' downloading the blocklists and
the location database you turned on; the dashboard listens on
127.0.0.1 only.

Before you start: whose policy?

As your own user the policy lives in ~/.stockfw; as root, in /etc/stockfw. A rule added without sudo is not the rule sudo stockfw apply pushes. Pick one identity and keep to it; the simplest is sudo for everything, so the app, the command line and the firewall all read /etc/stockfw. For a script that must not depend on who runs it, set STOCKFW_RULES_DIR. On Fedora, RHEL and some Kali systems sudo does not search /usr/local/bin (Ubuntu’s default does), so write sudo /usr/local/bin/stockfw there, or add an alias; a hint that needs root always prints the full path, so you can paste it. See Install on Linux.

How options are read

The word after an option that takes a value is that value: --comment -h saves the comment -h. Everything after -- is a plain word, so a host or comment that starts with a dash goes after it, or as --comment=TEXT. An option a command does not know is refused with exit 2, never ignored and never folded into a simulate question. A mistyped command or option gets a suggestion:

$ stockfw polcy list
stockfw: error: unknown command: polcy (did you mean `stockfw policy'?)
stockfw: hint: run `stockfw help' for the list of commands
$ stockfw simulate "inbound rdp" --bogus
stockfw: error: unknown option for simulate: --bogus
stockfw: hint: see `stockfw help simulate'; a word that starts with a dash goes after --
$ echo $?
2

Tables are fitted to the terminal, and only to the terminal: a pipe or a file gets every character, --full never cuts a cell, and --plain prints tab-separated rows with no header for cut and awk. Text that came from a log or a comment is escaped before it reaches your terminal: control characters and bidi controls print as \xNN or \uNNNN, in every table, in events --csv, in the rule names of simulate and in the list names of intel. Symbols fall back to ASCII outside a UTF-8 locale. [[verified:test-cli.sh]]

The first line is the verdict of the app’s Overview, from the same table: “This computer is protected”, “IPv6 is not protected”, “This computer is not protected” or “The firewall’s state is unknown”, with its reasons under it; --json has it as a verdict object with level, key, title and body. A test holds the window’s card and the terminal to one golden table, so the two cannot drift. [[verified:fs-verdict-smoke]] The Policy line says whether what you saved is what is live: “9 rules, live”, “1 change not applied (stockfw policy diff)”, “never applied”, or “settings changed since the last apply” when the Firewall preferences you saved are not the ones that went out. Last apply is the newest apply, start or stop in the audit log, with cli or gui. Blocked counts since local midnight, from the saved event history while it is kept and otherwise from the kernel log. Monitoring is decided by what your account can actually read, tried rather than guessed from your user id: a user in the adm group sees “reading /var/log/kern.log”. At boot says whether stockfw.service is enabled, installed but off, or absent. Reading the firewall state needs root; without it the state is unknown, not guessed. -v adds the rules directory, the firewall settings (outbound mode, DROP or REJECT, ICMP, logging, interfaces, NAT), the event history and Sentinel. With --json the 1.0.7 keys are unchanged and new ones are added: live (live, pending, never…) with pending counts, last_apply, blocked_today with last_block, monitoring with its source, boot_unit and host. Every rule has a reference, KIND:N, numbered as policy list shows it; KIND#N and KIND N work too. show prints one rule with what it covers and whether it is live. add and remove echo the reference and run a What-If check of the rule’s own traffic on the saved policy, so you see at once that the rule does what you meant. list takes a kind, in or out, --grep TEXT for the rows that hold TEXT, and --status to mark each row live or pending. diff shows the saved policy against the applied one: + rows to add, - rows to take away, numbered as applied.

The kinds and their fields are those of the Policy page: inbound-allow-from HOST, inbound-allow-service SERVICE PORT FOR, inbound-forward SERVICE FIREWALL-PORT TO PORT, outbound-allow-to HOST, outbound-allow-from HOST, outbound-allow-service SERVICE PORT FOR, outbound-deny-to HOST, outbound-deny-from HOST, outbound-deny-service SERVICE PORT FOR. FOR is a host, a network or Anyone. --both adds the opposite-direction twin of an allow rule as one change.

Editing a rule in place

$ sudo stockfw policy edit outbound-deny-to:1 198.51.100.67
Changed outbound-deny-to:1  198.51.100.67  [IPv4 only]
  was: 198.51.100.66
Check: outbound tcp to 198.51.100.67 -> BLOCKED (saved policy)
Not live yet: /usr/local/bin/stockfw apply   (preview: stockfw policy diff)

$ sudo stockfw policy edit inbound-allow-service:1 - 2222 -
$ sudo stockfw policy edit outbound-deny-to:1 --comment 'old bad host'

$ sudo stockfw policy add outbound-deny-to 203.0.113.99 --apply
Added outbound-deny-to:2  203.0.113.99  [IPv4 only]
Check: outbound tcp to 203.0.113.99 -> BLOCKED (saved policy)
Applied (only the changes): +1 added (0 allow, 1 block), -0 removed (0 allow, 0 block), =9 unchanged

policy edit REF [FIELD…] changes one rule where it is: same kind, same number, the comment kept unless --comment is given (--comment '' clears it), one save. Give all the fields in the order add takes them, with - for one that stays as it is, or none to change only the comment. A rule that another command changed in the meantime is refused, not overwritten. --apply on add, edit and remove is the window’s “Save and apply”: it saves and then applies through the same gate as stockfw apply, under one lock, so nothing can land between the save and the apply; it needs root, and the SSH check runs first on the policy the change would give, so nothing is saved if it would cut your session unless you confirm or pass --yes.

One writer at a time. Every change holds a lock from the moment it reads the policy until it has saved it (/run/stockfw/apply.lock and a .lock file beside the rules); two policy add commands at once both keep their rule, and the desktop app’s applies, starts and stops take the same lock, so a window and a terminal never apply at the same moment. A comma, a line break or a leading # in a field or comment is refused before anything is written, because the rule files have no quoting and such a row would read back as something else. The settings of the Preferences window, read and written from the terminal. list shows each setting this firewall acts on, its value, its default and, for a firewall setting, the value last applied (--firewall: those only; --changed: the ones not at their default). A setting is named by its dotted name (firewall.icmp.echo_request), its key (firewall/nat) or its last part when that is unique (nat, ext_if). A switch takes on/off; deny_packets takes drop or reject, restrictive_outbound takes block or allow; a device is a name from config devices.

set, reset, audit-only on|off and apply write root’s copy of the settings, the one the firewall, the boot unit and apply run as root read, so they need root. They follow the window’s rules and refuse with its reasons and the Help topic of its page: connection sharing needs both devices (set them in the same call), the broadcast and reserved-address blocks need the Internet device, an ICMP type needs ICMP filtering on, the history limits need the history on. Only the settings you name are written, so two set calls at once each keep their own; a settings file that cannot be read is kept as stockfw.conf.bad. set warns when a StockFW window runs as root, because the window keeps its own copy and writes it back when it saves.

Saved is not applied. A firewall setting you save is not in force until an apply sends it: config apply (or set --apply) shows what changes and how many firewall rules that adds and removes, runs the SSH check, and applies the settings under the policy last applied, so policy edits you have not applied stay off. A policy apply (stockfw apply, or --apply on an edit) sends the saved settings too, as the desktop app’s Apply does, and says so: “The saved firewall settings went out with it.” Boot uses the settings last applied: stockfw start, which the boot unit runs, brings back the firewall settings recorded with the last apply, so a setting saved and never applied does not go live at the next boot either. Audit-only mode holds a settings apply like any other. [[verified:test-cli.sh]] [[verified:test-pr3-core.c]]

A line in a rule file that is not a rule is left out of the policy, and check names each one with its file, line and reason, exit 1. apply refuses such a policy, the dry run too (exit 2), and policy add and remove refuse as well, because saving would have deleted the line without a word. start still starts the last applied policy and only warns. SSH,,Anyone loads, because a known service needs no port. The check needs no root. [[verified:test-cli.sh]]

apply goes through the gate described on the Policy page: only what changed is touched, a refused apply is rolled back to the last applied policy and the rollback is verified, and every attempt is one audit line with the source cli. An apply after a stop starts the firewall again with the whole policy, and the audit line says why (“full (firewall was stopped)”); the desktop app’s Apply shares the gate and so gets the same behaviour. When Audit-only is on in the app, apply records the change and leaves the firewall alone: “Held: audit-only mode is on. The firewall was left untouched.” --dry-run lists the rows it would add and remove and says which forwards would be left out; -v adds the chains it would write. start loads the last applied policy, with the firewall settings recorded at that apply, and starts the firewall, so saved changes you never applied stay off; stop removes StockFW’s own chains and nothing else. On a terminal stop first says what stopping takes away and asks, as the window’s “Pause protection?” does; Enter keeps the firewall running (exit 1). --yes skips the question, and with no terminal on standard input (a script, cron, the boot unit) it stops without asking, as before, and never reads standard input. “Already running” and “Already stopped” write no audit line of their own, except that a stop on a stopped firewall still takes the threat-intel blocklists down and logs that as intel-suspend. All three need root and exit 3 without it. [[verified:test-cli.sh]] [[verified:test-apply-linux.sh]]

The lockout guard over SSH

$ sudo stockfw apply
stockfw: warning: this policy would block your SSH session
  from 192.168.1.50 to port 22: BLOCKED (no rule allows it)
Apply anyway? [y/N] n
stockfw: error: not done: the firewall was left as it was
$ sudo stockfw apply < /dev/null
stockfw: warning: this policy would block your SSH session
  from 192.168.1.50 to port 22: BLOCKED (no rule allows it)
stockfw: error: refused: pass --yes to apply anyway

Over SSH, apply and start ask the What-If engine whether the new policy still lets your session in before they touch anything. If it would not, they ask on a terminal, and without one (a script, a cron job) they refuse unless you pass --yes. It works under sudo, where SSH_CONNECTION is gone: your own session is found through the sshd it runs under and is always checked first, however many other SSH sessions the computer has, and sshd is found on any port, also when systemd starts it through ssh.socket. The addresses of SSH clients on every port sshd listens on are also in the set a threat-intel blocklist may never cut. [[verified:test-cli.sh]] [[verified:test-hostnet.c]]

Exit 0 means ALLOWED, 5 BLOCKED and 6 DEPENDS, so a script can branch without parsing; 2 means the line could not be read. With -q only the verdict word is printed. The plain output is the window in text: the verdict in a sentence with the deciding rule as KIND:N, how the line was read with a confidence, then for each direction the trace (- skipped, * a note, => the deciding step) and the checked fixes in brackets. The JSON carries the same, with read_as, rule_ref, and under answers every direction’s trace, cases and actions, each action with the exact policy row it would write. The sentence grammar is on the simulator page. Simulating reads the saved policy and needs no root; --applied asks the last applied policy instead; reading whether the firewall is running does need root, so --assume-running answers for the firewall as it would run. Sentinel’s staged blocks are part of the answer, with when each lifts. [[verified:test-whatif.c]] [[verified:test-cli.sh]]

Running a fix: --do N

$ sudo stockfw simulate "ssh from 203.0.113.99" --do 1
ALLOWED. The firewall is not running, so nothing is filtered.
Read as: host 203.0.113.99; service SSH: TCP port 22; inbound (confidence 90%)

Inbound TCP port 22 (SSH) from 203.0.113.99 to this computer: ALLOWED
  The firewall is not running, so nothing is filtered.
  How it was decided:
    => the firewall is not running: nothing is filtered
  1 [create-allow] Allow inbound TCP port 22 from 203.0.113.99: Adds one row to the policy (Inbound: allow service): inbound TCP port 22 from 203.0.113.99. Checked: with it this question is allowed once the firewall runs, and nothing else changes. On Linux the row also applies to traffic this computer forwards to other machines.
  2 [start-firewall] Start the firewall: The firewall is not running, so nothing is filtered. This is allowed only because of that. Once it runs, the rules decide: this is blocked.

Good to know:
  - Once the firewall runs: BLOCKED. No rule lets it in, so the default drops it.
  …
Do fix 1? [y/N]

The fixes are numbered in the answer, and --do N runs one, as the What-If window’s buttons do: a new rule (only one StockFW itself writes, one address or block, one port, one protocol, checked as safe before it is offered), a start of the firewall (through the normal start gate, so audit-only mode holds it and the audit log gets a line), an apply, or a Sentinel lift. Any other fix prints the command to run instead. The question is answered against the policy as it is now and the fix is shown before anything changes; on a terminal it asks [y/N], and without one it needs --yes. Without --do nothing is ever written. [[verified:test-pr4-core.c]] [[verified:test-cli.sh]]

events act turns one event into a rule, as the Events page’s menu does. The action is block-dest (outbound: deny all traffic to its destination), block-service (its service and port to that destination), allow-dest (allow its destination; Sentinel’s blocks of it are lifted), trust-source (inbound: allow its source) or untrust-source (remove the inbound allow for its source). An allow is saved and the saved policy is applied, so the whole apply is shown first. With the firewall stopped the rule is recorded for the next start and the firewall is not started. --no-apply only saves. [[verified:test-pr4-core.c]] [[verified:test-cli.sh]]

Topics about the desktop app’s own windows are listed apart. Where a command has a topic’s name, such as events, stockfw help events is still the command’s help and points to stockfw help topic events. The same topics are installed as the manual page stockfw-topics(7), written by the tool like stockfw(1). about is the About window: version, credits, licence and website; --licences prints both licence texts in full and --system the lines for a bug report, which name no user, host or address. The manual page and completion

$ man stockfw
$ stockfw policy remove inbound-allow-<Tab>
inbound-allow-from:1     inbound-allow-service:1  inbound-allow-service:2
$ stockfw events --by=s<Tab>
src  service

stockfw(1) lists every command with its options, the global options, the exit codes, the environment variables and the files. stockfw writes the page itself from the same tables its parser reads, at build time, so it cannot fall behind the tool, and the build is reproducible: the page carries no date. Completion for bash and zsh asks stockfw too, and offers commands, options, values such as the --by keys and the TCP states, threat-intel feed ids, and the KIND:N references of your own saved rules. The Linux installer puts the page in /usr/local/share/man/man1/stockfw.1 and the scripts in /usr/local/share/bash-completion/completions/stockfw and /usr/local/share/zsh/site-functions/_stockfw; stockfw-uninstall removes all three. On a system whose shell does not load completions from /usr/local/share, source the bash script from your .bashrc, or add the zsh folder to fpath. [[verified:test-cli.sh]]

A build of the command line alone

$ cmake -S port -B build-cli -DFS_BUILD_GUI=OFF
$ cmake --build build-cli
$ sudo cmake --install build-cli

-DFS_BUILD_GUI=OFF builds stockfw and its manual page without GTK, and does not look for GTK at all, for a server that has no desktop libraries. The default still builds the desktop app too. The project’s own tests check that stockfw needs no GTK, GDK, Pango or cairo library. [[verified:test-nogui-build.sh]]

Output conventions

  • --json prints one JSON document per command, or one object per line for events -f, audit -f and interfaces --watch. Keys are stable across releases; new keys may be added, and 1.0.7’s keys are all still there.
  • Colour is decided by standard output alone: on when it is a terminal, off in a pipe, with NO_COLOR, TERM=dumb or --color=never; --color=always forces it on, even into a pipe.
  • --plain (-H) gives tab-separated rows without a header; --full (-l) never cuts a cell.
  • Errors go to standard error as stockfw: error: …, usually followed by stockfw: hint: … saying what to do, with the full path of the program when it needs root.
  • -q keeps only the essential line, leaves out hints, notes and legends, and with simulate prints only the verdict word.
  • Every command that changes something (events act, simulate --do, copilot block, copilot health --fix, copilot changes --undo, sentinel lift, sentinel mode, trust attest and forget, and the intel saves with --apply) asks [y/N] on a terminal, No by default, and --yes skips the question. With no terminal on standard input and no --yes it stops at once, changes nothing, names --yes and never reads standard input.
  • With the firewall stopped, a command that adds or lifts a rule prints one line: “The firewall is stopped: the change is saved and goes live at the next start; the firewall stays stopped.” None of them starts the firewall. In audit-only mode the line says the firewall was not changed and how the change goes live.
  • stockfw version prints one line: stockfw {{version}} - Linux (iptables), or (nftables) for that backend.

intel

stockfw intel [status]                     State, and the lists turned on
stockfw intel feeds                        Every feed: on/off, licence, credit, entries, last update, next
stockfw intel terms FEED                   What turning FEED on means
stockfw intel enable ID [--direction D] [--accept-terms]
stockfw intel disable ID
stockfw intel on | off                     The master switch
stockfw intel add-feed NAME URL [--format F] [--direction D]
stockfw intel proxy [URL|none]             The download proxy
stockfw intel update [--feed ID] [--now] [--accept-shrink] [--accept-coverage] [--no-apply]
stockfw intel apply [--dry-run]            Load the lists into the kernel
stockfw intel clear                        Remove them from the kernel
stockfw intel import FILE|- --name NAME [--direction D] [--apply]
stockfw intel lists | list show [ID]       Your own lists (and one's ranges)
stockfw intel remove ID [--apply]          A local list or custom feed
stockfw intel except | unexcept ADDRESS... [--apply]
                                           Never block / block again
stockfw intel exceptions [--set FILE|- [--apply]]
stockfw intel lookup ADDRESS               Which lists hold it; blocked?
stockfw intel geo [status]                 Blocking by country or network
stockfw intel geo terms | on [--accept-terms] | off
stockfw intel geo update [--no-apply]      Download the location database
stockfw intel geo search TEXT [--max N]    Find country codes and AS numbers
stockfw intel geo add country|asn VALUE... [--dir D] [--name NAME]
stockfw intel geo list | remove ID         The country and network rules

stockfw intel manages threat-intel blocklists and country and network rules, each command with --json. Every feed is off until you turn it on: terms says which host a feed is downloaded from, how often, what that host learns and its licence, and enable records your consent before anything is downloaded. update fetches the feeds that are due (--now: all of them) and, when the lists are enforced and audit-only is off, puts the new copies in force; a copy that shrank to almost nothing or rolled back to an older date is refused unless --accept-shrink, and one whose coverage jumped needs --accept-coverage. D is in, out or both. A proxy with a user name or password is refused, because curl’s command line is readable by every local user. List and feed names are escaped like every other text from outside.

intel geo blocks by the country a range is registered in, or by the network that owns it, from IPFire’s signed location database; it is off until geo on --accept-terms, and intel update then downloads the database at most once a day. lookup exits 5 when the address is blocked, and simulate answers from the policy alone, so it does not consult the lists. Changing the sets needs root, like every other change to the kernel. [[verified:test-intel-cli.sh]]

$ printf '198.51.100.7   # office vpn\n192.0.2.0/24\n' | sudo stockfw intel exceptions --set -
Saved.  Never blocked by a list:
192.0.2.0/24
198.51.100.7
Not live yet: run `sudo stockfw intel apply'.

$ printf 'allow 198.51.100.7\n' | sudo stockfw intel exceptions --set -
stockfw: error: line 1: not an address, CIDR or range: allow 198.51.100.7
stockfw: hint: each line: an address, a network (198.51.100.0/24) or a range (192.0.2.10-192.0.2.20); '#' starts a comment; nothing was saved

The Threat Intel page’s editors have their terminal form. exceptions --set FILE|- replaces the whole allow list with a text, one address, network or range a line, # starting a comment; a line that does not read changes nothing (exit 2) and empty input clears the list. import - reads a list from standard input, and --name "My blocklist" is the page’s “Your blocklist”. enable, disable, on, off, import, remove, except, unexcept and exceptions --set take --apply, which puts the saved change in force at once, as the page does after a save: it needs root, checked before anything is saved, asks on a terminal, audit-only mode holds it, and with the firewall stopped the lists go in force when it starts. intel feeds has a NEXT column: “due now”, or when intel update downloads the feed next. The app’s own flags

  -V, --version            Show the program version and exit
  -b, --background         Start in the notification area with the window hidden
                           (it is shown if no notification area takes the icon)
  -m, --minimized          Same as --background
  --quit                   Ask the running StockFW to quit (the firewall stays on)
  --enable-autostart       Start StockFW in the background when you sign in, then exit
  --disable-autostart      Stop starting StockFW when you sign in, then exit

These belong to the desktop program, StockFW, on Windows and Linux alike. It takes options only: a word such as StockFW dashboard exits with status 2 and names the command you meant, sudo /usr/local/bin/stockfw dashboard. A second launch brings the running copy’s window forward instead of starting another; a launch with more rights takes over from it. See Background, tray and sign-in. [[verified:test-instance.sh]]

Tests

tests/test-cli.sh drives every command above against a scratch policy and a fixture log, checks the exit codes and the JSON, runs copilot health with the local network fixed, runs real applies, starts and stops in a private network namespace, follows events -f under a real terminal and reads the raw bytes of its status line, checks the lockout guard with a fake sshd, holds the policy lock while two writers race, runs config set refusals against the Preferences rules, compares the manual page and completion against the command tables, and `tests/test-dashboard.sh` starts a dashboard and exercises its owner, link, session, Host and deadline checks as the served account, as root and as another user. It runs as the build user and again as root, and the root run fails if a root-only part is skipped. tests/test-intel-cli.sh does the same for intel. tests/test-pr4-core.c covers the core step that puts one block live alone and the Sentinel lift on a stopped and a running firewall, and tests/test-help-text.c checks every help topic against the desktop app’s.
