Copilot

A local analyst that reads the same events the Events page shows, learns what each program normally does, and tells you when something steps outside that. It is a parser and a set of counters, not a language model: it has no network, no account and no prompt, so it works on an air-gapped machine and cannot be talked into anything.

What is on the page

  • Sentinel: Detect only or Detect + auto-block. Detect only is the default and reports without touching the policy.
  • Run analysis looks at the current policy and the events seen so far and lists what it finds. Sentinel’s detectors run on every event regardless.
  • Four tiles: Apps learned, Active insights, Events analyzed, Policy rules.
  • Insights and suggestions: a table of findings with title, type, severity, description, program and status. Double-click a row for the full explanation. Apply selected rule stages the rule a finding suggests, after showing it; Clear insights empties the list; Undo auto-block lifts what Sentinel staged.
  • What-if simulator: a question about traffic, answered against the saved policy. It has its own page.

The baseline

Every event is attributed to a program (on Windows the event carries its path; on Linux the connection table does), and each program gets a profile: the ports it has used, the destinations it has contacted, the hours of the day it is active, and how many connections it makes per ten-minute window. The profile is written to behavior.csv in your profile folder and read back at the next start, so what was learned survives a restart.

The profile is deliberately bounded: 256 programs, 256 ports and 1,024 destinations each. When a program reaches a cap its profile is marked partial, and the novelty findings (“first time on this port”) go quiet for it, because a truncated baseline cannot honestly claim “never seen before”. Findings about hours need four distinct hours of history first; findings about rate need eight completed windows and at least ten events in the window being judged. [[verified:test-core.sh]]

Severities are Info, Warning and Critical. The list keeps the newest 200 findings. A finding that suggests an allow is only ever a suggestion: nothing on this page can open the firewall without you pressing a button and reading the rule in a Yes/No dialog first. [[verified:test-adversarial.sh]]

Sentinel

Sentinel watches outbound traffic for the two signatures of a program that is no longer working for you. It is egress-only by design: an inbound scan is the Events page’s business, and the engine already drops it.

Beacon
Six or more contacts with the same host and port, at a mean interval between 10 seconds and 10 minutes, with a coefficient of variation of 0.30 or less. A human clicking, a browser’s jittered keep-alives and git’s background fetches do not pass that regularity test; a command-and-control callback does. The finding is Critical and carries a deny rule for the destination.
Fan-out
Sixty distinct destinations within sixty seconds, or ten distinct destinations the firewall blocked within sixty seconds. The finding is Critical and deliberately carries no rule, because “block everything this program touched” is a decision for you, not for a counter. A package manager pulling from 59 mirrors reports nothing; the 60th reports a line.

Both thresholds are pinned by the adversarial suite, which plays a blocked port scan, a single-host port sweep, a command-and-control beacon, a replay of a real incident, benign developer tools, an exfiltration burst and a failed apply through the detectors, and asserts that only the beacon would ever reach the firewall unattended. [[verified:test-adversarial.sh]]

Auto-block, and what it may never do

With Sentinel set to Detect + auto-block, a beacon’s deny rule is staged into the policy and pushed through the apply gate without waiting for you. Because that is the one place where StockFW acts on its own, it is fenced on every side:

  • Only a deny, only for a public stranger. Auto-block can tighten the policy, never loosen it. A destination that is loopback, link-local, multicast, a private LAN range, carrier NAT, a reserved range, or an IPv4-mapped IPv6 address standing for any of those, is never auto-blocked, and neither is anything that does not parse as an address. A destination this program has contacted three or more times before the current run is established, and established traffic is reported, never blocked. That is the browser-talking-to-a-CDN case. [[verified:test_sentinel_auto_gates]]
  • Ten minutes. Every staged block expires ten minutes after it was staged. The staging record is written to the autoblocks file as it changes, so a block survives a restart with its original clock: a restart grants no fresh ten minutes, and a block that expired while StockFW was closed is taken out at the next start, with an audit line saying so. [[verified:fs-copilot-smoke]]
  • No loops. Once a block is taken down, by expiry, by Undo, by your own Allow or by switching to Detect only, the same rule cannot be staged again in this session. The incident that shaped these rules was a ten-minute block that re-staged itself every ten minutes for two days.
  • Your Allow wins. Allowing a destination from the Events page first lifts any Sentinel block for it, then pushes the allow, so both reach the firewall together. On Windows a block rule outranks an allow rule, so without this your Allow would have changed nothing on the wire.
  • Detect means detect. Switching Sentinel out of auto mode takes every staged block down at once.
  • Your rules are never touched. Sentinel’s rows carry a Sentinel: comment and are the only rows it will ever remove.

In the Status column a staged rule reads Auto-blocked; the Undo auto-block button lifts the selected one at once.

The audit trail

Every stage, push, undo, expiry, restore at start-up and mode switch is one line in audit.log: sentinel auto-block, sentinel auto-block is live, sentinel auto-block staged, not live, sentinel rule removed, sentinel auto-blocks restored, and the failure variants. The file is only ever appended to. Files and formats describes the line.

Honest limits

  • On Linux the kernel log carries no program name, so profiles are keyed by what the connection table can attribute; a connection that closes before the next poll is counted without a program. [[gap]]
  • Sentinel has no inbound scan detector, by design.
  • The behaviour analysis is heuristic. It is explained in plain words so you can judge it; it is not a verdict about the program’s intent.
  • An older About dialog still describes the Copilot as “AI-powered”. It is rule-based; the wording is being corrected. [[soon]]
