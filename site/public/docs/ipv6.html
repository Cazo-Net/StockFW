Docs / Protection

IPv6

A rule that only exists for IPv4 is a door left open on every network that also speaks IPv6, which today is most of them. StockFW tells you, per rule and on the Overview, exactly which families are filtered, and on Linux since 1.0.7 it filters both from the same policy.

Windows#

Windows Windows Firewall rules apply to both families unless an address scopes them, so a rule for Anyone covers IPv4 and IPv6, and a rule for 2001:db8::5 covers IPv6 only. The Overview’s two tiles both read “Filtered” whenever the firewall is on. One limit: the Windows engine takes addresses, not names, so a rule whose target is a host name covers nothing there, and the Covers column says so. Known gap

Linux before 1.0.7#

Linux The 1.0.5 and 1.0.6 releases drive iptables only. Their IPv4 policy is complete, and IPv6 traffic is not filtered by StockFW at all: whatever the kernel’s default is, that is what happens. Both releases say so in the README and the architecture document; neither pretends otherwise in the app. Known gap If you run one of them on a network with IPv6, you are relying on your router or on another firewall for that family.

Linux since 1.0.7#

Linux Built for 1.0.7 The whole policy is rendered before the kernel is touched into two payloads, one for iptables-restore and one for ip6tables-restore, each with a filter part and, in router mode, a nat part. The backend snapshots StockFW’s chains in both families, loads IPv4, then IPv6, and on any failure puts back every table it changed. Each payload is loaded with --noflush and declares only StockFW’s own chains, so rules that Docker, libvirt or ufw keep in the same tables are never seen, and the hook from INPUT into INBOUND is not removed and re-added during a re-apply. Verified test-apply-dual.sh

The rollback covers both families, always. The first version rolled IPv6 back and skipped IPv4 whenever the IPv6 restore itself failed, which would have left IPv4 on the new policy while the dialog said nothing changed; four “teeth” runs now pin it, each removing one part of the rollback and watching a specific check go red.

Which family a rule reaches#

TargetRendered into
An IPv4 address or networkThe IPv4 payload only.
An IPv6 address or networkThe IPv6 payload only.
Anyone, or emptyBoth.
A host nameLooked up once per apply and written as each family’s addresses, so no name is left for the tools to resolve while loading. A name with no address in one family gets a note. An allow whose name cannot be looked up is left out and reported (it fails closed). A block whose name cannot be looked up refuses the apply while rules are loaded, so the last good addresses stay blocked; when nothing is loaded yet (Start), it is left out and the notes begin with “NOT BLOCKED:”, because refusing would leave every host unfiltered over one name. A port forwardIts destination’s family, written as [2001:db8::5]:80 for IPv6. Masquerading stays IPv4-only. A destination that is a name or a range is left out and noted.

The same decision drives the Covers column on the Policy page, stockfw policy list and its JSON, and a test checks that “Covers” names a family exactly when that family’s payload contains the rule. Verified test-core.sh

What IPv6 always needs#

Neighbour discovery is ICMPv6, not ARP, so it goes through the filter, and a firewall that drops it takes the host off the network. Ahead of every preference and never rate-limited, INBOUND accepts packet-too-big, time-exceeded and parameter-problem; router advertisements from fe80::/10, neighbour solicitations and advertisements, all with hop limit 255; multicast listener discovery with hop limit 1; and DHCPv6 replies from link-local. OUTBOUND lets the host’s own solicitations, advertisements, listener reports, packet-too-big and DHCPv6 requests out, ahead of restrictive mode’s default drop. The ICMP preferences map to ICMPv6 where a counterpart exists; timestamps, address masks and source quench are IPv4-only and labelled so.

Router mode#

IPv6 forwarding is hooked only in router mode, because container and VM runtimes accept forwarded traffic in their own tables and would otherwise be cut by INBOUND’s default drop. An IPv6 forward needs net.ipv6.conf.all.forwarding=1, and a forwarding host ignores router advertisements, which would drop its own default route; before turning forwarding on, the backend sets accept_ra=2 on the external interface, and only if it was 1, since 0 means someone turned advertisements off on purpose.

What the app tells you#

  • The Overview has an IPv6 traffic tile that reads the kernel: “Filtered”, or “Not filtered” with the reason in the sidebar: ip6tables not installed, chains not loaded, loaded but not hooked, or the firewall stopped. “None on this system” when the kernel has no IPv6 stack. It never infers IPv6 from IPv4.
  • stockfw status has an IPv6 line and an ipv6 object in its JSON.
  • The dashboard’s Firewall tile reads “In force for IPv4 and IPv6” or warns “IPv4 only”.
  • A successful apply on a host without ip6tables is a success with a note, not a failure: “IPv6 is not filtered: ip6tables is not installed”. Install the package and Apply again.

Testing it without IPv6#

The project’s test container has no IPv6 stack. STOCKFW_ASSUME_IPV6=1 makes the backend load the IPv6 payload anyway, so rule loading is exercised for real in a private network namespace while packet behaviour is checked as rule text. The screenshots on this site were taken that way.
