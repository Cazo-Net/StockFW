# StockFW 1.0.6 Graph Research (read-only)

## Scope: Both families

### 1. Adapter Throughput (pktmon + GetIfTable)

**Data source**: Windows Performance Instrumentation (pktmon) packet counters + `GetIfTable` interface table snapshots.

**What is measured**:
- Total bytes and packets forwarded per network adapter over a fixed observation window (e.g., 30 s).
- Per-interface throughput: `bytes_delta / observation_seconds` and `packets_delta / observation_seconds`.
- Interface name resolution via `GetIfTable` OID `0x00000003` → friendly name (Ethernet, Wi‑Fi, etc.).

**Methodology** (read-only design note, not executed in this session):
1. Start pktmon etw tracing on the StockFW driver path (requires admin / elevated).
2. Capture `pktmon record` for X seconds while the firewall processes a known workload (e.g., allowed TCP traffic, blocked UDP, ICMP echo).
3. After tracing, parse the `.etl` with `pktmon report` or programmatically via WMI `MSNdisLightWeightFilterDriverStatistics`.
4. Simultaneously call `GetIfTable` (IP Helper) to map interface indices → descriptions.
5. Correlate pktmon's `InterfaceId` with `GetIfTable` row; compute average Mbps per adapter.

**Expected output** (sample layout, not generated here):
| Adapter      | ifIndex | ifDesc                | bytes/s | pkts/s |
|--------------|---------|-----------------------|---------|--------|
| Ethernet0    | 12      | Realtek PCIe GbE    |  45.2   | 1.1k   |
| Wi‑Fi        | 13      | Intel Wi-Fi 6 AX200 |  12.8   |   340  |

**Research questions**:
- Does pktmon capture include *only* packets that survived the firewall (ALLOWED), or also blocked ones?
- How does the per‑adapter overhead of the StockFW kernel hook manifest in the counter drift?
- Can we isolate “event-rate” vs “throughput” signals for the two graph lines?

### 2. Event Rates by Verdict

**Data source**: StockFW internal event log (security‑style rows, newest‑first, `HH:MM:SS` timestamps). Each row records a rule‑evaluation event with a verdict: `ALLOWED`, `BLOCKED`, `ERROR`.

**What is measured**:
- Counts of events per verdict type over sliding windows (e.g., per minute, per hour).
- Rate = `count / observation_window_seconds`.
- Ratio ALLOWED : BLOCKED as a health indicator.

**Methodology** (read-only design note):
1. Read the installed app's event log (SQLite or flat file depending on backend) after a representative usage interval.
2. Tally `ALLOWED`, `BLOCKED`, `ERROR` tallies.
3. Plot two graph series:
   - **Line A**: Cumulative ALLOWED events over time (step function).
   - **Line B**: Cumulative BLOCKED events over time.
   - Optional: overlay ERROR count as a third muted series.

**Expected output** (sample — not rendered):
```
Min  ALLOWED  BLOCKED
  0        0       0
 5 min   842      37
10 min  1735      71
15 min  2610    103
```

**Research questions**:
- Does the ALLOWED/BLOCKED ratio stabilize after an initial learning period?
- Are there temporal patterns (e.g., more blocks during business hours)?
- How does the `Direction` bi‑setting (inbound / outbound / both) affect the verdict distribution?

### 3. Combined View

The two families are **independent but co‑located** on the 1.0.6 roadmap:
- The **adapter-throughput** graph lives in the "Network I/O" panel (uses pktmon data).
- The **event‑rates** graph lives in the "Policy Activity" panel (uses internal event log).
- Both share the same time‑range selector (last 1h / 6h / 24h / custom).

No cross‑family coupling is required; each consumes its own data source.
