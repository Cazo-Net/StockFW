## 0. Goals and non-goals

Goals

1. **IPv6 is filtered on Linux** with the same policy as IPv4, without breaking IPv6 itself
   (neighbour discovery, router advertisements, PMTU, DHCPv6 replies).
2. **IP blocklists ("threat-intel feeds")**: the user opts in to well-known feeds; StockFW downloads,
   validates, normalizes and stores them, and blocks listed addresses inbound and outbound.
3. **Country and network-owner (ASN) blocking** from an offline location database built from a
   public-domain / open source.
4. **Enrichment**: every event and connection can show the remote country, network owner (ASN + name),
   and which blocklists contain the remote address.
5. Every one of these is visible and controllable in the desktop app, the `stockfw` CLI (JSON), and
   (read-only) the local dashboard.

Non-goals for 1.0.7: DNS/domain filtering, IDS, gateway features, a native nftables backend for the
*policy* (that is 1.0.8; 1.0.7 uses nftables only for the threat-intel sets), signed feeds (no feed
offers signatures; see the integrity section for what we do instead).

House rules that apply to all of it: local-first and **no network traffic unless the user enabled a
feed** (StockFW is otherwise offline); WYSIWYG (never claim protection that is not in the kernel);
argv-only process spawning (no shell); every security claim has a test with teeth.

## 1. IPv6 on Linux (iptables backend)

- `fs-script.c` gains a family dimension: `fs_script_generate_inbound_family()` /
  `fs_script_generate_outbound_family()` with `FS_SCRIPT_V4` / `FS_SCRIPT_V6`. The existing
  `fs_script_generate_inbound/outbound()` stay and mean IPv4 (no behaviour change for callers).
  The v6 script uses the token `$IP6T` (mapped to `ip6tables`), the v4 script keeps `$IPT`.
- Rule targets are classified: IPv4 literal/CIDR → v4 only; IPv6 literal/CIDR → v6 only;
  "anyone"/empty → both; hostnames → both (iptables/ip6tables resolve A/AAAA themselves at insert time;
  a name with no AAAA makes ip6tables fail → that one rule is skipped with a warning, not a failed apply).
- v6 ICMP (`-p ipv6-icmp --icmpv6-type ...`), placed in the ICMP section, i.e. **before** the
  `ctstate INVALID` drop:
  - always (whatever the ICMP page says): `packet-too-big`, `time-exceeded`, `parameter-problem`,
    `neighbour-solicitation`, `neighbour-advertisement`, `router-solicitation` (all with `-m hl --hl-eq 255`
    for the NDP ones), `router-advertisement` (`-s fe80::/10 -m hl --hl-eq 255`), MLD
    (130,131,132,143 from `fe80::/10`). Without these the host loses IPv6 connectivity.
  - per Preferences: echo-request/echo-reply (limited like v4), destination-unreachable
    (mapped from `icmp_unreachable`/`icmp_mstraceroute`), traceroute UDP 33434 as v4.
  - v4-only types (timestamp, address-mask, source-quench, redirect) have no v6 rule.
  - "ICMP filtering off" → allow all ICMPv6 (rate-limited like v4).
- DHCPv6 client replies: `-p udp -s fe80::/10 --sport 547 --dport 546 -j ACCEPT` (replies to a
  multicast solicit are not matched by conntrack).
- Reserved sources on the external interface (v6 analogue of the RFC1918 block): `::1/128`,
  `::ffff:0:0/96`, `2001:db8::/32`. ULA and link-local are **not** blocked (both are legitimate on a LAN).
- Broadcast rules: none in v6 (no broadcast). NAT/MASQUERADE: v4 only (documented).
  Port-forward DNAT is emitted in the family of its `to` address only.
- Default action: v6 LOG with the same `STOCKFW-DROP`/`STOCKFW-REJECT` prefix; REJECT uses
  `--reject-with icmp6-addr-unreachable`.
- Backend: `apply_lines()` accepts `iptables` and `ip6tables` argv; apply runs v4 then v6;
  stop/clear detach+flush+delete both families; `get_state` is driven by the v4 chain as before.
- New vtable slot `ipv6_state(&detail)` → `FILTERED` (v6 INBOUND exists and is hooked from INPUT),
  `UNFILTERED` (v4 running, v6 not; detail says why), `ABSENT` (kernel has no IPv6:
  no `/proc/net/if_inet6`), `UNKNOWN` (not root / cannot tell). Windows returns `FILTERED`
  (Windows Firewall rules cover both families). Shown on the Status page, `stockfw status`, dashboard.
- If `ip6tables` is missing or the v6 apply fails while the kernel *has* IPv6, the apply result is
  `FS_APPLY_PARTIAL` with a message naming IPv6; when the kernel has no IPv6 at all it is `FS_APPLY_OK`.
- The kernel log parser names `PROTO=ICMPv6` events "ICMPv6".

## 2. Rounds

Threat intel ships in three rounds inside 1.0.7, each one complete and tested on its own:

1. **Round 1 (this revision): blocklists on Linux.** The kernel rules, feed downloads, consent,
   local list files, exceptions, the engine, the `stockfw intel` commands, the Threat Intel page,
   events attributed to a list, and What-If/Copilot that know about lists.
2. **Round 2: country and network-owner (ASN) blocking**, with the location data question settled
   first ([P3]: the iptoasn country column is the AS owner's registration, not where an address is).
3. **Round 3: Windows** (section 11). Blocklists are enforced with Windows Firewall rules of
   their own. Its enforcement cannot be run in the development container: the pure parts are
   tested on Linux, and a test against the real firewall runs on the CI's Windows runner.
   Country and network-owner blocking (sections 12 and 13) stay unavailable on Windows.

Everything below is Round 1 unless it says otherwise.

## 3. Address ranges (`core/fs-iprange.[ch]`, built)

Sorted, merged, inclusive intervals per family; strict parsing; union, subtract, membership, text
form. Built and tested in 7e5afd7. Round 1 adds to the **protected ranges** (never blocked by
anything): `192.0.0.0/24`, `192.88.99.0/24`, `198.18.0.0/15` [P7] and the NAT64 prefixes
`64:ff9b::/96`, `64:ff9b:1::/48` [S7.3]. TEST-NETs stay unprotected (the tests use them).

## 4. Feeds (`core/fs-feed.[ch]`)

### 4.1 Catalog

Every feed is **off** until the user turns it on and accepts its terms. No mirrors in 1.0.7
[S12, P6]: a feed is fetched from its own publisher or not at all. Each entry carries: id, name,
category, one-sentence description, URL, the host contacted, an info page, a terms page, the licence
name *only where it has been verified* (otherwise the UI says "See the provider's terms"), a
non-commercial flag, format, default direction, update interval, `recommended`, `includes` (ids of
feeds it already contains) and whether it publishes IPv6.

| id | publisher | format | default dir | interval | recommended |
|---|---|---|---|---|---|
| spamhaus-drop | Spamhaus DROP (IPv4) | spamhaus-json | both | 24 h | yes |
| spamhaus-dropv6 | Spamhaus DROP (IPv6) | spamhaus-json | both | 24 h | yes |
| feodo | abuse.ch Feodo Tracker (botnet C2) | plain | both | 6 h | yes |
| dshield | DShield top attackers | dshield | in | 24 h | no (non-commercial terms) [P9] |
| firehol-level1 | FireHOL level 1 (aggregate; includes the three above and DShield) | plain | in | 24 h | no |
| blocklist-de | blocklist.de (fail2ban reports) | plain | in | 24 h | no |
| et-compromised | Emerging Threats compromised hosts | plain | in | 24 h | no |
| cins-army | CINS Army | plain | in | 24 h | no |
| tor-exits | Tor exit relays (a policy choice, not a threat list) | plain | in | 6 h | no |

As built, Spamhaus DROP is fetched once a day, not every 12 hours: its page asks that the data not be
downloaded more than once per day. Each catalog entry also carries a **credit** line (Spamhaus asks
to be credited in a product), which the page, `stockfw intel feeds` and the dashboard show beside
the list's name.

Turning on a feed whose `includes` names one that is already on adds a note ("FireHOL level 1
already contains Spamhaus DROP"); both stay on if the user wants. Custom feeds: any URL that passes
the URL rule (4.4), with a name, a format and a direction; the user typed the URL, which is consent
for that host.

### 4.2 Formats

- **plain**: one address, CIDR or `a-b` range per line; `#` and `;` start comments; anything after
  the first whitespace, `;` or `,` is ignored.
- **spamhaus-json**: NDJSON. Lines that are objects with a `"cidr"` string give entries; the
  object with `"type":"metadata"` gives the content date (`"timestamp"`, unix seconds) and the
  advertised `"records"` count (recorded, not enforced: format from documentation).
- **dshield**: `start<TAB>end<TAB>prefix...` rows, `#` comments, a `Start` header row; the range is
  `start-end`.

Content dates are read where a format has one [S12.2]: FireHOL `# This File Date`, abuse.ch
`# Last updated`, DShield's header date, Spamhaus metadata. Unknown dates are 0, and staleness then
falls back to the download time.

### 4.3 Parse guards (pure, in `fs_feed_parse`)

- At most **32 MiB**, at most **200,000** entries [S8.1], lines over 4096 bytes are invalid, a NUL
  byte refuses the body, a UTF-8 BOM and CRLF are accepted.
- Each entry is first reduced by the protected ranges, then **every remaining piece is measured by
  size, never by prefix length** [S1.1, S4]: an IPv4 piece wider than 2^22 addresses (a /10) or an
  IPv6 piece wider than 2^99 (a /29) drops the entry as *too broad*. This catches
  `::ffff:0.0.0.0/96`, `0.0.0.0-255.255.255.255` and `2000::-3fff:...` as well as plain wide CIDRs.
  Aggregates whose wide entries are all protected space (FireHOL's `224.0.0.0/3`) lose nothing and
  report nothing [P7].
- **Coverage caps** on the whole list after subtraction [S1.2]: IPv4 at most 2^25 addresses, IPv6
  at most 2^42 /64 networks. Over the cap, the download is refused.
- Nothing parsed while lines were invalid, or more invalid data lines than valid ones (an HTML
  error page), refuses the body.

### 4.4 URL rule

`https://` only, at most 2048 bytes, printable ASCII without spaces, no `user@` part, a non-empty
host, and never starting with `-`. Query strings are allowed (paid feeds use keys there) but are
shown as `?…` everywhere except the feed editor [S18].

Not a secret store: curl gets the URL on its command line, which every local user can read in
`/proc/<pid>/cmdline` while a download runs. A key in a custom feed's query string is therefore
visible to local users during that download; the docs say so, and Round 1 has no way to pass it
otherwise. A proxy with `user:pass@` in it is refused outright for the same reason.

### 4.5 Accepting an update (`fs_feed_judge`, pure)

Compared against the feed's history (the last 7 accepted copies) [S15]:

- **empty**: a list that parses to nothing replaces a non-empty one only with *accept shrink*;
- **shrank**: fewer than a quarter of the largest recent entry count (when that was 8 or more), or
  less than a quarter of the largest recent IPv4 coverage (when that was 2^16 or more);
- **grew**: IPv4 coverage more than doubled *and* grew by more than 2^22 addresses [S1.3]; needs
  *accept coverage*;
- **rollback**: an older content date than the copy we have [S12.4]; needs *accept shrink*.

A refused update keeps the previous copy, sets `refused` in the feed's state with the reason, and
writes an audit line. `--now` (ignore the schedule) and `--accept-shrink` / `--accept-coverage`
(override a guard) are separate flags [S15.2].

## 5. Downloads (`core/fs-fetch.[ch]`)

curl, spawned with an argv, hardened against everything a root process inherits [S0, S2, S9, P14]:

- `argv[0]` is absolute: `/usr/bin/curl`, else `/bin/curl`; missing curl is a clear error.
- `-q` first (no curlrc), then `--proto =https --proto-redir =https --proto-default https
  --tlsv1.2 --fail --silent --show-error --location --max-redirs 3 --globoff
  --max-filesize <cap> --max-time <t> --connect-timeout 20 --user-agent StockFW/<version>
  --output -`, then either `--noproxy *` or `--proxy <url>` (only from `intel.conf`, validated),
  then `--url <url>`. `--globoff`: one URL is one transfer; curl would otherwise expand `[..]`
  and `{..}` into many requests, even to hosts the URL does not name.
- An **explicit environment**: `PATH=/usr/sbin:/usr/bin:/sbin:/bin` and `LC_ALL=C`, nothing else:
  no HOME, no `CURL_CA_BUNDLE`, `SSL_CERT_*`, `SSLKEYLOGFILE` or `*_proxy`.
- As root, curl runs as **nobody** (uid/gid looked up before the fork, supplementary groups
  cleared in the child); if that account does not exist the download is refused [S2.5].
- The body arrives on a **pipe**, never a file; StockFW counts bytes itself and kills curl at
  cap + 1 [S9]. No `--compressed`. A whole-transfer timeout kills it too.
- Errors are classified (no curl, refused URL, too large, timed out, TLS, HTTP status, network)
  with curl's first stderr line.
- Test builds only (`FS_FETCH_TESTING`) read `STOCKFW_TEST_CURL` and `STOCKFW_TEST_CACERT`; release
  builds have no such hook.

Every download goes through one engine function that refuses unless that feed is enabled *and* its
terms were accepted [S14.1]. With the default configuration StockFW makes no network request at
all, and a test with teeth proves it [S14.4].

## 6. The engine (`core/fs-intel.[ch]`)

### 6.1 Store

- Linux, root: `/var/lib/stockfw/intel`, mode 0700, owned by root (parent 0755).
  `STOCKFW_INTEL_DIR` overrides it only when that directory and every parent are owned by the
  current user or root and not writable by group or others (OpenSSH's StrictModes) [S2.1-2]; a
  user-owned directory under `sudo -E` is refused, not used. Non-root without an override: the
  engine says it needs root.
- Every file operation goes through a directory descriptor opened `O_DIRECTORY|O_NOFOLLOW`, files
  are opened `O_NOFOLLOW|O_CLOEXEC`, must be regular files, are read with a size cap, and are
  written to a fresh temp name (`O_EXCL`), fsynced and renamed [S2.3]. All files are 0600.
- Files: `intel.conf` (config), `<id>.list` (normalized ranges), `<id>.state` (key file: dates,
  counts, history, last error, refusal, carried counters), `applied.state` (what the kernel was last
  given: digest, set ids and counts, suspended flag).
- Loading a stored list re-applies the strict syntax, the entry count and the coverage caps,
  counted exactly as the parser counts them [S2.7, S4.4]: a tampered list is an error, not a block.
  The per-entry size floor is not re-applied: a stored list is normalized, so adjacent entries
  that each passed it are merged into wider intervals (eight adjacent /10s are stored as one /7);
  the coverage caps bound what a tampered list can block to what an accepted feed may.
- An existing store directory that group or others can read is tightened to 0700 when it is
  opened (its files are 0600, but a readable directory lists the feeds and local lists in use).
- Windows: `%ProgramData%\StockFW\intel` with an admin-only protected DACL [S3]; see 11.5.

### 6.2 Configuration (`intel.conf`)

Master switch (default on, which does nothing until something is enabled), optional proxy, one
group per feed (enabled, direction, terms accepted at), custom feeds (name, URL, format), local lists
(name, direction, enabled) and exceptions (addresses, CIDRs or ranges). Unknown keys are ignored;
invalid values fail the load naming the key. Ids are `^[a-z0-9][a-z0-9-]{0,39}$` [N7].

### 6.3 Local list files

`stockfw intel import <file> --name <name>` (and Import on the page) read a CSV or plain file with
the rules of `fs_blocklist_parse_csv` (first field; a header line; quoted fields), apply the parse
guards of 4.3, and store it as list `local-<slug>`. Importing the same name again (in any case or
spacing) replaces it; a different name whose slug is already another list's id ("Office VPN" and
"office-vpn") is refused, never written over that list. No network is involved.

### 6.4 Building the rule set (`fs_intel_build`)

One set per enabled feed or local list with a stored copy (never fetched: a note, not an error).
From each set the engine subtracts, and lists in the notes what it subtracted:

- the protected ranges and the user's exceptions;
- this computer's own addresses, its connected prefixes and its default gateways [N4b, S5.2];
- the DNS servers in use: `/etc/resolv.conf`, and when every server there is loopback,
  `/run/systemd/resolve/resolv.conf` and `/run/NetworkManager/no-stub-resolv.conf` [N5, S7.1];
- the peers to keep reachable: the client in `$SSH_CONNECTION`/`$SSH_CLIENT` and every established
  inbound TCP connection to the local SSH port [N4c, S5.3];
- the addresses of the enabled feeds' own hosts, so a list cannot block its own updates [S7.2], and,
  while any feed is enabled, the configured proxy's host, which every download connects to instead
  (`fs_intel_update_hosts`).

Then, for sets that block outbound (out or both), each IPv4 interval is also added to the IPv6 set
inside `64:ff9b::/96`, so NAT64 does not bypass an outbound list [N9, S7.3, P15].

Limits [S8.2, S1.2]: at most **300,000 intervals** over all sets (v4 and v6 together), and at most
2^26 IPv4 addresses in the union of all sets; above either the build fails naming the largest sets.

### 6.5 The gate (`fs_intel_apply_safe`) and the lifecycle

- Audit-only mode and the Policy Lock hold the apply exactly like the policy gate
  (`FS_APPLY_DRY_RUN`, nothing reaches the kernel). A backend without the intel slots answers
  "not available on this platform".
- The live counters are read before the kernel's sets are replaced and added to each source's
  carried total once the replacement is proven, so "blocked N" survives updates and is labelled
  "since <date>" [N8, P8]. Proof is a new digest where another one (or none) was live, or a counter
  lower than before. A re-apply of the same digest that the tool fails is exactly what a refused
  transaction leaves behind, so it is a failure with a note that the same rules are still in force,
  and nothing is carried: the old table still counts, and is never counted twice.
- Success records `applied.state`; every attempt is one audit line.
- **The policy never touches the threat-intel table** [N6, S10.2, P4a]: `linux_stop`, which the
  policy apply, reload and clear all call, never runs nft. The user-facing **Stop** (Status page,
  `stockfw stop`) calls stop and then `fs_intel_suspend`, which removes the table and marks it
  suspended; the user-facing **Start** (Status page, `stockfw start`, start-on-open) calls start and
  then `fs_intel_resume`, which re-applies through the gate under the same hold as any apply. Resume
  first clears "suspended", so a Start whose apply is held, refused or fails reads not-loaded, never
  suspended. Where no list was ever turned on (no store directory), Stop and Start do nothing and
  create nothing. Without nft, a Stop is not an error when StockFW's record says it left no table;
  when the record says it left one, the Stop fails and says why.
- **One engine operation at a time.** An apply, a Stop (suspend), a clear and a Start (resume)
  each hold an exclusive lock on `<store>/engine.lock`, so the CLI, cron, the app and the app's
  own worker threads (the Threat Intel page's jobs, the Status page's Stop/Start) never interleave
  them. On Linux the lock is a `flock` on a descriptor opened through the store's directory
  descriptor (`O_NOFOLLOW`); on Windows it is `LockFileEx` (exclusive, on the first byte) on a
  handle to the same file in the pinned store, opened without following a link
  (`fs_winstore_lock`). Both kinds belong to the open file or handle, so two threads of one
  process exclude each other as two processes do. A Start holds the lock across its own apply
  (`apply_in` is told so), on Windows too: it tests the lock it holds, not a descriptor. A Stop that arrives during an apply waits for it and then takes the lists down; an apply
  that had to wait and finds that the operation it waited for was a Stop is held ("the firewall
  was stopped while this apply waited"), so it never loads the lists behind the Stop's back. An
  update re-reads a source's carried counters under the same lock before it writes its state.
  The Status page's Start is held by the same answer as the page's applies
  (`fs_intelview_hold_reason`: audit-only mode, else the Overview's Lock).
- Nothing survives a reboot on Linux, policy or lists, until Start is pressed; the docs and the page
  say so [P4b]. Unattended re-applies (the app's hourly check, `stockfw intel update`) happen only
  when the firewall is running, the table is enforced or differs, and no hold is active [P4].

### 6.6 State: what the kernel is actually doing [S10, P4]

The table carries `comment "sfw:<digest>"`, where the digest is the first 32 hex digits of the
SHA-256 of the canonical rule set (each set's id, direction and stored text form, in order); each
of its three chains carries the same comment. `fs_intel_state` compares the live table with
`applied.state`. The backend reads it with `nft -j list chains inet` (milliseconds: chains carry
no elements), and only when no chain of ours carries a common digest (an older table, one changed
by hand, or no chain at all) with `nft -j list tables`, which loads every set element (about 2 s at
240k intervals) but is cheap when there is no table. When the kernel cannot be read the backend
says why (`intel_live_error`: no nft, a timeout), and the state's sentence carries it.

| state | meaning |
|---|---|
| off | master switch off, or nothing enabled (also when the kernel cannot be read, e.g. no nft, as long as StockFW's record says it left nothing loaded) |
| enforced | the live table's digest is the one StockFW last applied, and every applied list that has addresses still has its rules (the counter rules, listed per chain) |
| not-loaded | something should be enforced but the table is missing (a reboot, `flush ruleset`) |
| differs | a table is there but not the one StockFW applied |
| suspended | the firewall was stopped by the user, so the lists are off on purpose |
| not-in-force | Round 3 (Windows): rules are there, or cannot be read, and the firewall does not enforce them on a network in use (11.6) |
| unsupported / needs-root / unknown | cannot enforce here / cannot read the kernel / cannot tell |

A table whose chains were flushed (`nft flush table`) keeps its comment, so the digest alone would
still read enforced; the rules check makes it differs. Not seen: elements removed from a set, or some
of a list's rules removed while others remain.

Every surface shows this state, never just the configuration.

### 6.7 Updates and scheduling

`fs_intel_update` takes the enabled, consented feeds that are due (or one feed, or `--now`), fetches,
parses, judges, stores and reports one result per feed: updated, unchanged (same SHA-256), not due,
needs consent, refused (with why) or failed (with why). A failed or refused update never removes
the previous copy. The desktop app checks hourly in a worker thread [P13]; `stockfw intel update`
does the same for cron or a timer. Staleness: older than 7 update intervals, measured from the
content date when known [S12.3].

### 6.8 Lookup

`fs_intel_lookup` answers, for one address: the enabled sets that list it, whether it is protected,
an exception, or kept reachable as this computer's own network, and whether the current
configuration blocks it and in which direction. What-If and Copilot use it [P2]: an address the
policy allows but a list blocks is answered "Blocked by threat intel: <list>".

That is the configuration's answer. `fs_intel_lookup_live` adds what the kernel does: the state,
and, when enforced, whether a set the kernel was given holds the address, minus the exceptions
applied with it. `applied.state` records, per set, the direction and the digest of the stored list
it was built from, and the exceptions as applied, so an exception or a direction saved but not
applied is told apart ("pending"), and a list updated but not applied is "uncertain", never "not
blocked". `stockfw intel lookup` exits 5 only when the kernel blocks the address now (`in_force`);
the page says "is blocked" only then, and otherwise "would be blocked once in force" with the
reason. The page hides a lookup's answer when the state changes.

## 7. Enforcement on Linux (`core/fs-intelset.[ch]`, backend slots)

One table, `inet stockfw_intel`, owned by StockFW and replaced in one `nft -f -` transaction
(create-if-missing, delete, re-create), so it applies whole or not at all and a failed apply leaves
the previous table in force. Set names are `s_<id with - as _>_4` and `_6`; a family with no
addresses has no set and no rules [N7]. Every statement ends with a newline [N7]. Elements are
added 1000 to a statement. nft gets 60 seconds [S8.4].

Three base chains at `priority filter - 10` (before the iptables policy at 0), always present:

```
chain input   { type filter hook input   priority filter - 10; policy accept;  iif "lo" accept ... }
chain output  { type filter hook output  priority filter - 10; policy accept;  oif "lo" accept ... }
chain forward { type filter hook forward priority filter - 10; policy accept;  ... }
```

Directions [N0, S6, P1] — the same meaning as Windows' stateful rules:

| direction | input | output | forward |
|---|---|---|---|
| in ("stops them connecting to you") | `saddr @set ct direction original` drop | — | `saddr @set ct direction original` drop |
| out ("stops you connecting to them") | — | `daddr @set ct direction original` reject | `daddr @set ct direction original` reject |
| both | `saddr @set` drop | `daddr @set` reject | both of the above |

Drops are silent to the outside; outbound blocks are `reject with icmpx type admin-prohibited` so a
local program fails at once instead of hanging [P11]. Each blocking rule is preceded by the same
match with `limit rate 10/second burst 20 packets log prefix "STOCKFW-TI <id> " level info`, and
carries `counter` and `comment "<id>"`. Counters are read with `nft list chain` per chain, never by
listing the table or sets [S8.3].

Backend slots: `intel_apply`, `intel_clear`, `intel_counters`, `intel_live` (table present, and its
digest). The standalone CSV-to-set helper written earlier (`fs_nftset_load_csv`) keeps its API and
now uses its own table, `inet stockfw_blocklist`, so the two never collide.

Events: a kernel log line with `STOCKFW-TI <id>` becomes a blocked event whose rule is
"Threat intel: <list name>", accepted only when `<id>` is a set in the applied rule set [S17.3].

## 11. Round 3: blocklists on Windows

Round 3 enforces the same rule set (section 6.4) with Windows Firewall rules. The engine, the
store's file formats, the build and every subtraction are shared with Linux; what differs is
below. The shape of the rules and every verdict on what is read back are decided in pure code
(`core/fs-intelwin.[ch]`), which the core suite checks on Linux; the backend
(`platform/windows/fs-backend-windows.c`) only moves them across COM.

### 11.1 The rules

Every rule is written in-process through `INetFwPolicy2`, `INetFwRules` and `INetFwRule`. No
netsh and no PowerShell: a spawned console would flash, and its output would have to be parsed.
The vtable slots StockFW calls are pinned to their documented positions at compile time
(`netfw-compat.h`), so a header that disagreed stops the build instead of calling the wrong method.
(The old note that MinGW's `INetFwRules` was wrong was itself wrong: Microsoft documents
`Add(INetFwRule *)`, `Remove(BSTR name)` and `Item(BSTR name, ...)`, as MinGW declares them.)

- Every rule is in the rule group `StockFW Threat Intel` and nothing else of StockFW's is. The
  policy's rules are named `StockFW-...`, live outside the group, and the policy's clear keeps to
  that prefix, so applying or clearing either never touches the other [N6, P0].
- One rule per chunk: `SFW-TI <id> <in|out> IPv<4|6> <i>/<n> g<8 hex>`. A list in both directions
  gets an inbound and an outbound copy. Every rule blocks, applies to every profile, protocol,
  port, local address, program and interface type, and names its addresses in `RemoteAddresses`.
- The last part of the name is the generation: a random value per apply that no rule on the
  firewall already carries.
- One manifest rule per generation, `SFW-TI manifest g<8 hex>`, disabled, with `RemoteAddresses`
  192.0.2.1 (TEST-NET-1, so enabling it by hand still blocks nothing that exists). Its description
  ends `sfw:<digest> plan:<plan hash> rules:<n>`. The plan hash is the SHA-256 (first 32 hex
  digits) of `sfw:<digest>` followed by, for every address rule in name order, its name, its
  direction and its addresses in the stored text form. The manifest also keeps a rule set whose
  lists were emptied by subtraction visible, as the nft table without sets is on Linux.
- Descriptions name the list (control characters and `|` replaced, at most 80 characters).
- The empty rule set leaves no rule at all.

### 11.2 How many addresses a rule takes

Microsoft documents no limit on `RemoteAddresses` (the `put_RemoteAddresses` reference says only
that it is a list of addresses, ranges and keywords). Reports from tools that write blocklists into
Windows Firewall rules agree on: at most 1000 addresses per rule on Windows 7, 10,000 on later
versions; the WaGi Mass IP Blacklister, for one, splits at 10,000 and at 1000 for Windows 7. StockFW
writes at most **1000 tokens** per rule, the value every supported Windows takes, and at most
**32,000 characters**: a `UNICODE_STRING` holds 32,767 UTF-16 units, and 1000 IPv6 ranges written
as `a-b` can reach about 79,000 characters, so the character cap keeps every string inside what any
layer between the API and the filter engine could store. A token (an address, a CIDR block or
`a-b`, as the stored text form prints it) is never split; a single token longer than the cap would
get a rule of its own.

At the 300,000-interval build cap (6.4) that is 300 rules per direction, which the firewall
handles; Linux uses sets instead because nft has them.

### 11.3 Apply and clear

- **Apply** reads our rules first. Exactly the asked-for rules, whole (11.6), is a no-op: no
  rule is rewritten on every hourly re-apply, and there are no counters a replacement could reset.
- Otherwise the new generation is written first, its manifest last, so until the manifest exists
  the new rules read as incomplete, never as a rule set. A rule the firewall refuses takes the new
  generation out again and leaves the old one untouched and in force. `Remove` succeeds for a
  name it does not find, so the firewall is listed again afterwards, and the error says "Nothing
  was changed" only when no rule of the new generation is left (11.11, W6).
- Then every rule of ours that is not the new generation is removed (for the empty rule set,
  all of them). A rule that will not go blocks more than asked, never less, and the apply says so.
- `INetFwRules::Remove` goes by name, and Windows lets two rules share one. A rule whose name any
  other rule also has is first renamed, on the rule object itself, to a name nothing else has, so
  a removal can only take that rule, never a user's rule that happens to share the name. Names
  are compared case-folded for this, so a name that differs only in case counts as shared
  (11.11, W6).
- What the firewall holds afterwards, read back whole, decides success [S10]: the asked-for
  digest, PRESENT; for the empty rule set, nothing of ours.
- **Clear** removes every rule in the group and nothing else, then lists the firewall again: only
  none left is success. A rule someone else put in the group is removed too; the group is
  StockFW's.

### 11.4 Exceptions and what is kept reachable

Windows Firewall has no rule order: a block rule beats every allow rule (the one exception is an
allow rule with "override block rules", which needs authenticated IPsec, below). An exception is
therefore never written as an allow rule. It holds because the build subtracts it, with the
protected ranges and everything in 6.4, before any rule is written; the Windows rules are made
from the same rule set as the nft sets, and `fs-intel-test` checks that no rule they would write
names a subtracted address.

What the build keeps reachable is read on Windows by `fs_hostnet_read`:
`GetAdaptersAddresses` for every adapter that is up (its addresses, the block each lies in from
`OnLinkPrefixLength`, its gateways and its DNS servers), the SSH variables and
`GetExtendedTcpTable` for established connections to local ports 22 (SSH) and 3389 (Remote
Desktop), and `getaddrinfo` for the update hosts. A prefix length of 0, or wider than the family,
keeps the address alone; it never keeps everything (which would empty every list without a word).

### 11.5 Store

`%ProgramData%\StockFW\intel`, from `SHGetFolderPathW`, never from the environment [S3]. Applying
needs StockFW to run as administrator (`FS_INTEL_ERR_NEEDS_ROOT` otherwise).

- `%ProgramData%\StockFW` is created with a protected DACL: SYSTEM and Administrators full,
  Users read. `intel` inside it: SYSTEM and Administrators only. Nothing is inherited from
  `%ProgramData%`, which lets every user create folders.
- **How a folder is created** (`fs_winstore_sddl`, one `CreateDirectoryW` with a
  `SECURITY_ATTRIBUTES` built from SDDL, so the folder never exists, even for a moment, with
  another owner or an inherited access list):
  - `%ProgramData%\StockFW`: `O:BAD:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)(A;OICI;0x1200a9;;;BU)`;
  - `intel`: `O:BAD:P(A;OICI;FA;;;SY)(A;OICI;FA;;;BA)`;
  - `STOCKFW_INTEL_DIR`: the `intel` one plus `(A;OICI;FA;;;<current user's SID>)`, and `O:BA`
    only when StockFW is elevated.

  `O:BA` makes BUILTIN\Administrators the owner. Without it Windows makes the creating account
  the owner: an elevated administrator included, since the policy "System objects: Default owner
  for objects created by members of the Administrators group" is "Object creator" by default. The
  check below then refused StockFW's own new folder (found by the first run on the CI's Windows
  runner: "owned by ... runneradmin"). An elevated token holds Administrators with the
  `SE_GROUP_OWNER` attribute, so it may name that group as owner at creation; a token without it
  cannot (`ERROR_INVALID_OWNER`), which is why an unelevated override keeps the current user as
  owner, trusted there. `D:P` is a protected DACL: nothing is inherited from the parent. `OICI`:
  files and folders created inside inherit the same entries. The check is not widened for this:
  a folder owned by the account StockFW runs as is still refused in the default store, whoever
  made it.
- An existing folder must be owned by Administrators, SYSTEM or TrustedInstaller, grant no other
  account a right to change it and be no link; otherwise it is refused (`FS_INTEL_ERR_UNSAFE_DIR`).
  A folder another account made first is never used. An `intel` folder others can read is set
  back to SYSTEM and Administrators.
- `%ProgramData%` lets every user create a folder, so a standard user could make
  `%ProgramData%\StockFW` first. StockFW (always elevated when it gets here) moves such a folder
  aside, renamed to `StockFW.untrusted-<random>` in the same place, and makes its own: when it is
  owned by an account other than Administrators, SYSTEM or TrustedInstaller, is a link, or is not
  a folder. A rename moves a link itself, never what it points to, and nothing is deleted. When
  the move fails (a program holds a file in it open), the refusal names the owning account and
  says that an administrator can delete or rename the folder (11.11, W7).
- Win32 has no `openat`, so the store is pinned: a handle on the directory opened without
  `FILE_SHARE_DELETE`, so nobody can rename or delete it, or a parent of it, while StockFW works in
  it. Files are opened with `FILE_FLAG_OPEN_REPARSE_POINT` and refused when they are links, read
  with a size cap, written to a fresh name and moved over the old one with
  `MOVEFILE_WRITE_THROUGH`.
- `STOCKFW_INTEL_DIR` (absolute) gets the same checks, with the current user trusted too, and is
  created with SYSTEM, Administrators and the current user (above). Its parent must already pass
  the same check (owner and access list); a folder that inherits a drive root's default access
  list (Users may create folders in every folder below it, as `D:\a\_temp` on the CI runner) is
  refused, and the error names the parent. The tests make their parents with a protected DACL.
- The judgement itself is pure (`fs_winstore_judge`): the owner must be trusted; there must be
  an access list; inherit-only entries apply to what is created inside and are skipped, as are
  deny, audit and label entries; an allow entry for an untrusted account with any of add file,
  add folder, delete child, delete, write DAC, write owner, generic write, generic all or maximum
  allowed is a refusal; one with only list or read rights makes the folder "readable" (an `intel`
  folder is then set back); any other entry type is a refusal. `tests/test-core.sh` checks it,
  and the SDDL StockFW creates with, on Linux.

### 11.6 Live state and "in force"

`intel_live` lists every rule on the firewall and judges ours (`fs_intelwin_read`):

| live | when |
|---|---|
| ABSENT | no rule in our group |
| PRESENT (with the digest) | one generation, one manifest, and its rules all there and unaltered: the plan hash recomputed from what was read (names, directions, addresses) is the manifest's, the count matches, and every rule is enabled, blocks, has its direction, covers every profile (the three bits; Windows reports `NET_FW_PROFILE2_ALL`), every protocol (256), every local address and port, no program or service, interface types `All`, no named interface and no `INetFwRule3` condition (app package, users, machines, IPsec flags) |
| PARTIAL | anything else: a rule missing, added, edited, disabled or narrowed, a second generation (a removal that failed), a rule in the group StockFW did not write |
| INACTIVE | rules of ours are there, but the firewall does not enforce them on a network in use |
| UNKNOWN | the rules cannot be read |

Addresses are compared as sets: Windows hands IPv4 back with dotted masks
(`10.0.0.0/255.0.0.0`) and may reorder them. Keywords (`*`, `LocalSubnet`, `DNS`,
`DefaultGateway`, ...) and masks with holes are refused, so they read PARTIAL.

"Not in force" (`intel_not_in_force`, `fs_intelwin_not_in_force`) is one sentence, or nothing:

- the Windows Firewall service (MpsSvc) is not running (asked of the service manager, which a
  standard user may ask);
- Group Policy manages the firewall and does not apply local rules
  (`LocalPolicyModifyState` is `GP_OVERRIDE`);
- the firewall is off for a profile a network in use has (`CurrentProfileTypes`,
  `FirewallEnabled`);
- adapters are excluded from such a profile (`ExcludedInterfaces`).

What cannot be read is never reported as on: settings, Group Policy's state or a profile in use
that cannot be read give the sentence "StockFW cannot read whether Windows Firewall is on for the
network in use, so it does not report the blocklists as in force." (11.11, W5). A profile known
to be off is named first. The engine (6.6) gains one state, **not-in-force**,
which wins over enforced: INACTIVE reads not-in-force with that sentence (and says when the rules
there are not the ones last applied either); UNKNOWN with a sentence (the service stopped, so the
rules cannot even be read) reads not-in-force too; PARTIAL reads **differs** ("Some of the
blocklist rules are missing or were changed outside StockFW; apply to restore them."). An apply
whose rules are written but not enforced is a success with a note: "The rules are in place, but
not in force: ...". Stop removes rules that are PARTIAL or INACTIVE as well.

### 11.7 Counts

Windows Firewall keeps no count of what each rule blocks, so `intel_counters` stays NULL. The
engine says so in words, `fs_intel_counts_unavailable()`: "Windows Firewall does not count what
each rule blocks, so StockFW cannot show blocked counts here." Surfaces show that sentence instead
of a number; `fs_intel_counters()` on Windows holds no entry, so no list is ever shown as "0
blocked". The firewall log (`pfirewall.log`) does not name the rule that dropped a packet either,
so Events on Windows cannot say which list blocked an address.

### 11.8 Downloads on Windows

`fs-fetch.c` spawns the curl that ships with Windows by its absolute path
(`<system folder>\curl.exe`, from `GetSystemDirectoryW`, never `PATH`), with the same argv as
Linux, an explicit environment (`SystemRoot`, which Winsock needs, and
`NoDefaultCurrentDirectoryInExePath=1`, nothing from StockFW's own environment) and the system
folder as working folder. Missing curl (Windows before 10 1803) is a clear error. Known gaps, not closed in Round 3:

- No privilege drop: curl runs with StockFW's rights, which on Windows are an administrator's.
  Windows has no `nobody`; a restricted token is possible but not done.
- GLib starts a console program through its spawn helper, so a console window may flash for the
  length of a download. Not seen in the container; unverified.
- Windows' curl uses Schannel and the Windows certificate store, not a CA file. The test hooks
  (`STOCKFW_TEST_CACERT`) are Linux only.

### 11.9 What blocklists do not cover on Windows

- Routed traffic: the "out" direction on Linux also stops connections a routed LAN host starts.
  Windows Firewall rules filter this computer's own traffic; Internet Connection Sharing is not
  filtered by them.
- An allow rule with "override block rules" (authenticated bypass) wins over a block rule. It
  only matches traffic authenticated with IPsec, which a listed address cannot provide unless the
  administrator set that up.
- Country and network-owner (ASN) blocking (Round 2) are not available on Windows.

## 12. Round 2, part 1: the location database reader (`core/fs-geodb.[ch]`, built)

Country and network-owner blocking needs one question answered first [P3]: where does an address
belong? This section settles the data and builds the reader. Nothing uses it yet: the engine, the
nftables sets, the CLI and the page come next (12.7).

### 12.1 The data [S11, P3, P10]

- **IPFire's location database** (format version 1,
  `https://location.ipfire.org/databases/1/location.db.xz`), published daily, licence CC BY-SA 4.0.
  Each network carries a country, an AS number and flags (anonymous proxy, satellite provider,
  anycast, "drop": hostile, safe to drop); the file also names ASes and countries (with continents).
- It is **signed** (ECDSA P-521) with IPFire's key, so a mirror, proxy or cache cannot change it.
  The key is pinned in `fs-geodb.c`. It is the key Ubuntu's `location` package ships
  (`/var/lib/location/signing-key.pem`, created 2019-12-10), SPKI SHA-256
  `f2af409aeb339c55d686644f661b96d329f80c5f1ab34ef027cb36d2620b53aa`, which the test pins too. A key
  rotation needs a StockFW release.
- The country of a network is where its address space is **registered** (RIR data with IPFire's
  corrections), never a measured position. Every word shown to users says "registered in".
- The attribution the licence asks for belongs on the page that shows the data (12.7).

### 12.2 Our own reader

`fs-geodb.c` is written from the format's published layout (offsets, record sizes, byte order) and
checked against libloc's writer and IPFire's own file. It shares no code or structure definitions
with libloc; libloc and its Python binding are used only by the tests, as the reference.

The file is `LOCDBXX` and a version byte, a 4,192-byte big-endian header (creation time; vendor,
description and licence as string offsets; five sections as offset and length: ASes, networks, the
network trie, countries, the string pool; two signature lengths and two 2,048-byte signature
slots), then the sections. Records are 8 bytes (AS, country) or 12 (network, trie node).

### 12.3 Trust, in the order the checks run

1. **Unpack** (`fs_geodb_unpack_xz`): the download (at most 64 MiB) is decoded as a stream by
   liblzma's stream decoder with a 96 MiB memory limit (every xz preset fits; a stream asking for a
   larger dictionary is refused) into a temporary file next to the copy in use. More than 256 MiB
   of output is refused before the chunk that would pass the cap is written. One stream only:
   anything after it is refused.
2. **Verify**: before any other field is trusted, at least one slot must hold a DER ECDSA
   signature made with the pinned key over SHA-256 of the whole file, with both signature lengths
   and both full slots read as zeros (the reserved bytes after them are signed). Either slot may
   verify. A slot whose length is 0 or past 2,048 is no signature, and no usable slot is "not
   signed". There is no unsigned path in release builds. The key must be an EC key on P-521.
3. **Check**, once at open, so that a file is refused whole or not at all. The file is a regular
   file (never a symbolic link) of at most 256 MiB, mapped read-only. Every offset and length is
   checked with checked arithmetic: sections lie after the header, inside the file, and do not
   overlap (an empty section's offset means nothing). Record tables are whole records. The trie is
   walked once, depth first with an explicit stack: every child and network index is in range, no
   node is reached twice (no loops, no shared subtrees), and the depth is at most 128. Every string
   offset is inside the pool and terminated there, at most 4,096 bytes. Country codes are two
   capital letters (or none, for a network); the AS and country tables are strictly ascending. The
   creation time is positive. Accessors check ranges again on every access.
4. **Judge** (`fs_geodb_judge`, pure): see 12.5.

The header is parsed from a private copy of the verified bytes. The mapped file can only change
underneath us if someone with write access to the store rewrites it in place. StockFW itself only
ever replaces it by rename, and every access is range-checked, so even then a read stays inside the
mapping.

### 12.4 Answers

- **Lookup** (an address as text or a `GInetAddress`): the most specific network holding it, with
  its country, AS (number and name), flags, prefix and family. IPv4 addresses, and IPv4-mapped IPv6
  ones, are looked up among the IPv4 networks only (the trie's `::ffff:0:0/96` subtree). An IPv6
  network that happens to cover that subtree never answers for an IPv4 address (libloc fails on
  that lookup; we say "no network").
- **Enumerate** (for nftables interval sets): every address whose most specific network has a
  country in the filter, an AS in the filter or one of its flags, as a normalized `FsRangeSet`,
  equal to libloc's flattened search, merged. The IPv6 side leaves out `::ffff:0:0/96`. AS 0 and
  bad country codes are refused; an empty filter is an empty set. `fs_geodb_set_prefixes` gives the
  fewest CIDR prefixes for a set.
- **Countries and ASes** for the picker: every country (code, continent, name), one country, an AS
  name, and an AS search by name (ASCII case-insensitive) or number.
- **Metadata**: creation time, vendor, description, licence, the slot that verified, counts.
- Strings from the file are shown safely: invalid UTF-8 is repaired, and control and format
  characters (a bidi override, a BEL) become `?`. The description keeps its newlines.

### 12.5 Freshness and anti-rollback

The format has no expiry date, so the creation time does the work. A new copy is judged against a
**floor**: the larger of the copy in use (when it verifies) and the creation time of the newest copy
ever accepted, which the caller passes in (`min_created`; the engine keeps it in `geodb.state`,
13.4). A copy created after the floor replaces the copy in use. A copy created before it is a
rollback, and is refused. A copy created at the floor is "unchanged" when it is the good copy in
use; when the copy in use is damaged or gone, the same copy repairs it. A copy more than 24 hours
ahead of our clock is refused (checked first, so a far-future file cannot lock out every later
update). A copy older than 30 days is stale. Every failure keeps the last good copy.

A copy in use that no longer verifies or checks counts as no copy (the new one is still verified
and checked), so a damaged file cannot block its own repair. It does not lower the floor: a damaged
or deleted `location.db` is repaired only by a copy at least as new as the last one accepted
(review GEO-ROLLBACK-1, 13.14). A caller that passes no floor (0, a store never written) gets the
copy in use alone as the floor; only the reader's own tests do that.

### 12.6 Store and download

- The copy in use is `location.db` in the threat-intel store (6.1). `fs_geodb_install_xz` opens the
  store `O_DIRECTORY|O_NOFOLLOW` and takes an exclusive `flock` on it, so installs into one store
  run one at a time. It then removes every regular file named `.location.db.<anything>.tmp`: the
  temporary file of an install that was killed (SIGKILL, the OOM killer, power loss), up to 256 MiB
  each, which nothing else would ever remove (review GEO-TMP-LEAK-2). It removes nothing else: no
  other name, no symbolic link, no directory, and never through a link. Because of the lock it
  never removes the file of an install that is still running. It unpacks to a fresh `O_EXCL` 0600
  temporary file in the store, fsyncs,
  opens that file through the directory (no symbolic link), verifies, checks and judges it, and only
  then renames it over `location.db` and fsyncs the directory. On every failure the temporary file
  is removed and `location.db` is byte for byte what it was. Linux only for now; Windows says
  "not available on this platform yet" (Round 3).
- `fs_geodb_update` downloads through `fs_fetch` (section 5: curl as nobody, https only, the
  caller's proxy or none, a 64 MiB cap, 300 s) and installs. It is a network request, made only when
  the user turned country or network-owner blocking on. Nothing schedules it yet.
- Libraries: liblzma (xz) and OpenSSL's libcrypto, on Linux from the distribution, on Windows from
  MSYS2 (`mingw-w64-ucrt-x86_64-xz`, `mingw-w64-ucrt-x86_64-openssl`), staged beside the exe and
  shipped by the installer by name.

## 13. Round 2, part 2: country and network-owner blocking in the engine (Linux)

This part puts the reader of section 12 to work: the user picks countries or network owners (ASes),
StockFW compiles them into nftables interval sets in the threat-intel table, and the gate, the
lifecycle and the honest state of sections 6 and 7 apply to them unchanged. It adds no surface itself:
the `stockfw intel geo` commands and the page's card (13.16) call the engine functions listed in
13.11. Windows keeps saying
the feature is not available there (13.10).

### 13.1 The data and its licence

- One source: IPFire's location database (12.1), signed, verified with the pinned key, judged for
  rollback. It names where address space is **registered**, never where a machine is.
- **The licence is CC BY-SA 4.0, confirmed by IPFire.** The file says "CC BY-SA 4.0" in its licence
  field and IPFire's site said so too, but the terms had also been quoted as CC BY-NC-SA. The
  project owner asked IPFire which one covers the copy served today, and IPFire confirmed CC BY-SA
  4.0 (2026-11-03, before the 1.0.7 release). The feature stays **off by default**, and the licence
  is stated wherever the data is offered: the consent text and `fs_intel_geo_attribution()` (the
  one-line attribution for every screen and every `--json` answer that shows location data) name
  IPFire, the licence, that IPFire confirmed it, and what it asks: credit IPFire and share any
  changed copy under the same licence.
- The fallback discussed in review (DB-IP Lite for countries plus iptoasn for ASes) is **not
  implemented in this round**. Nothing in the engine reads either. Adding one would be a new source
  with its own consent, licence text and integrity story (neither is signed).

### 13.2 Consent and the switch

- `[geo] enabled` in `intel.conf` turns the location database on: download it, keep it updated, use
  it for location rules and lookups. The default is off.
- Turning it on needs the database's terms accepted once (`accepted-at`), exactly like a feed (4.1,
  [S14.1]): `fs_intel_config_enable_geo (config, accept_terms)` fails with `FS_INTEL_ERR_CONSENT`
  and changes nothing until `accept_terms` is given. The consent text (`fs_intel_geo_consent_text`)
  names the host (`location.ipfire.org`), how often (once a day), what the host learns (this
  computer's public address and "StockFW/<version>"), the download size (about 6 MB), the licence
  status of 13.1, the "registered in" meaning, and that anycast networks are included and counted
  (13.6).
- A location rule can be added or turned on only once those terms were accepted (the same error
  otherwise). Turning the database off keeps the rules but enforces none of them.
- With the default configuration StockFW still makes no network request: the update refuses before
  the downloader is reached unless the master switch is on, the database is on, and its terms were
  accepted. A test with teeth proves it with the downloader replaced by a counter.

### 13.3 Location rules (`intel.conf`)

```
[geo]
enabled=true
accepted-at=1762041600

[location country-high-risk]
name=High-risk countries
countries=KP;IR;
direction=in
enabled=true

[location asn-bulletproof]
name=Bulletproof hosters
asns=64500;64501;
direction=both
enabled=true
```

- A rule has one kind, given by its id: `country-<slug>` holds countries, `asn-<slug>` holds AS
  numbers. The user's name becomes the slug as for local lists (6.3); a name whose slug is already
  another rule's id is refused. Rules of both kinds can be on at once, so a selection can be
  countries, ASes, or both.
- Countries are two ASCII letters, stored upper case. ASNs are 1 to 4294967295 (`AS13335` and
  `13335` are both accepted). Duplicates are dropped; a rule holds 1 to 1,000 values. A country
  rule with an `asns` key or the reverse, a value of the wrong form, or an empty rule fails the load
  naming the group and key (6.2: invalid values are an error, unknown keys are ignored).
- Directions are the three of section 7, with the same meaning.

### 13.4 Storage

- `location.db` is the copy in use (12.6). Only `fs_geodb_install_xz` writes it (temporary file,
  verify, check, judge, rename), so the last good copy is kept on every failure.
- `geodb.state` (0600) records the last attempt, the last success, the creation time of the newest
  copy ever accepted (`created-at`), and the last error or refusal, like a feed's state. `created-at`
  is the floor of 12.5: every update passes it to `fs_geodb_update`, and it never goes down, also
  not when the copy in use is damaged or gone (review GEO-ROLLBACK-1). Only removing the file (root,
  by hand) resets it; no surface offers that.
- A location rule has an `<id>.state` for its carried counters only. It has no `.list`: its
  addresses are computed from the database at every build, so a rule and the database in use never
  disagree.

### 13.5 Update cadence

- `fs_intel_update` also updates the database, as one more result with the id `location`, while the
  database is on: it is due 24 h after the last attempt, or at once with `FS_INTEL_UPDATE_NOW`;
  `only_id = "location"` updates just it. It goes through `fs_geodb_update` (12.6): curl as nobody,
  https only, the configured proxy or none, a 64 MiB cap and 300 s.
- Outcomes: updated (a newer copy is in use), unchanged (the same creation time), refused (bad
  signature, malformed, a rollback, from the future: the copy in use stays), failed (the download
  or the store), needs consent, not due. A rollback is never accepted, with or without the shrink
  flag, and whatever state the copy in use is in: the creation time is the only thing that says a
  copy is current, and it is judged against the newest copy ever accepted (13.4).
- The database's host is kept reachable like a feed's (6.4, [S7.2]): while the database is on,
  `fs_intel_update_hosts` names `location.ipfire.org` (and the proxy), so a country rule cannot
  block its own updates.
- A copy older than 30 days (12.5) is still enforced, with a note saying how old it is: blocking
  less because the data is old would quietly weaken a rule the user chose.

### 13.6 Building location sets

`fs_intel_build` adds, after the feeds and the local lists, one set per enabled location rule while
the database is on:

1. The database is opened from the store (verified and checked). When it is missing, each rule gets
   the note "not enforced: the location database has not been downloaded yet". A copy that no
   longer verifies or checks fails the build with `FS_INTEL_ERR_TAMPERED`, as a tampered list does
   (6.1): the kernel keeps what it had, and the next update replaces the copy (12.5).
2. `fs_geodb_enumerate` with the rule's countries or ASNs gives every address whose most specific
   network matches (12.4).
3. Every subtraction of 6.4, in the same order: protected ranges, **exceptions**, this computer's
   own addresses and networks, gateways, DNS servers, SSH peers, the update hosts. An exception
   always wins over a location rule, as over a list. The notes name what was kept reachable and
   which rules named it.
4. Outbound rules are also mapped into `64:ff9b::/96`, as lists are (6.4, [N9]).
5. **Anycast.** Networks flagged anycast stay in the set (leaving them out would be a hole the user
   did not choose), but never silently: per rule the engine counts the anycast prefixes and
   addresses it kept, after the subtractions (`FsIntelLocationStats`), and the build adds a note
   such as "High-risk countries includes 12 anycast networks (2,048 IPv4 addresses): anycast
   addresses are answered from many places, so this may also block services outside what you
   chose." The page shows the same numbers as the warning tooltip the owner asked for.
6. A rule that matches nothing is enforced as empty, with a note; a country code the database does
   not name gets its own note.

Limits. Location sets are measured on their own: at most **500,000 intervals** over all of them (v4
and v6, NAT64 copies included, `FS_INTEL_MAX_LOCATION_INTERVALS`); above that the build fails and
names the largest rules. They do not count toward the lists' 300,000 intervals or the 2^26 IPv4
union cap of 6.4. Those caps bound what a tampered or hostile download can block; a location set is
computed here from signed data and a choice the user made by name, and blocking all of a large
country is a legitimate choice. For scale, the 2022-10-29 database gives 44,469 prefixes for US,
19,757 for DE, 14,454 for RU and 8,362 for CN (both families), and 6,269 networks flagged anycast.

### 13.7 Enforcement on Linux

- Location sets go into the same table and the same transaction as the lists (section 7), with the
  same rules, log prefix (`STOCKFW-TI <id>`), counters and directions. Their set names show their
  kind: `s_country_<slug>_4` / `_6` and `s_asn_<slug>_4` / `_6`, beside `s_<feed>_4` and
  `s_local_<slug>_4`. `fs_intel_source_kind (id)` tells the kinds apart for counters and the page.
- **Reading the digest without the elements.** nft 1.0.9 fetches every set element before it lists
  tables: `nft -j list tables` took 11 to 13 s with 600,000 elements loaded (measured in a
  namespace), past the 10 s listing timeout, so a big country would have turned the state into
  "unknown" and made every apply unprovable. The digest is now also the comment of the three
  chains, and `intel_live` reads `nft -j list chains inet`, which took 4 ms with the same table: the
  table is present when a chain of `inet stockfw_intel` is listed, and the digest is the one every
  one of its chains carries (the rule the Round 3 branch built independently; see 13.15). Only when
  no chain of ours is listed, or the chains carry no common digest (an older StockFW's table, or one
  changed by hand), does it fall back to `nft -j list tables`: to tell "no table" (cheap, the common
  case) from "a table without chains", which blocks nothing and so is present without a digest
  ("differs") whatever its own comment says. The table keeps its own comment too.
- Loading: elements stay at 1,000 a statement. Measured in a namespace with nft 1.0.9: 150,000
  intervals load in 1.2 s, 600,000 in 5 s, and replacing a 600,000-element table with another
  takes 16.6 s, inside section 7's 60 s. No further batching is needed; the limit of 13.6 keeps the
  worst case (800,000 with the lists) near 25 s. The end-to-end test measures it through the whole
  engine every run: a country of 400,000 networks is applied in about 3.6 s, the state is read in
  under 30 ms with it loaded (6.4 s when the same check read `list tables`), and the replace that
  drops it takes about 10 s.

### 13.8 Lookup and enrichment

- `fs_intel_lookup` now also answers, while the database is on and present: the registered country
  (code and name), the AS (number and name), the network and its flags (anycast among them), and
  the ids of the enabled location rules that hold the address (`locations`, beside `sources` for
  lists). `dir` and `blocked` cover both, and the sentence names both ("Blocked by threat intel:
  Spamhaus DROP, High-risk countries"). A NAT64 address is looked up by the IPv4 address it
  carries: rule membership for outbound rules only, as the build maps it; the country, AS, network
  and flags shown are those of the IPv4 address whenever the database has no network for the NAT64
  address itself, marked `geo_via_nat64` (review GEO-3).
- When the copy in use is missing or no longer verifies, the lookup cannot say which rules hold an
  address, yet the kernel may still hold their sets (a build fails closed and keeps what was
  applied, 13.6). The lookup then names every enabled location rule that `applied.state` says is in
  the kernel (not after Stop) in `locations_unknown`, sets `geo_unknown`, and the sentence says "May
  be blocked by threat intel: High-risk countries (the location database in use cannot be read)."
  It never says "not blocked" for what it cannot read. Exceptions, protected space and this
  computer's addresses still read as not blocked, as the build keeps them out of every set (review
  GEO-1). `fs_intel_geo_lookup` already fails with the error in that case; it never evaluates
  rules.
- `fs_intel_lookup_live` (from Round 3's branch) adds what the kernel does. A location rule's set
  is never a stored list: `applied.state` records for it, in place of a list's digest, the SHA-256
  of the database copy it was built from (its signed creation time and size) and the rule's kind
  and values. The live lookup asks the copy in use for the address only while that digest still
  matches; otherwise the answer is `uncertain` and `pending`, never a plain "not blocked". A rule
  turned on, off or redirected since the apply makes the answer `pending`, as for lists.
- `fs_intel_geo_lookup` is the cheap call for events and connections: one address to its country,
  AS and flags, without evaluating rules. The opened database is cached per process and reopened
  only when `location.db` changes (device, inode, size, mtime), so a busy event list does not
  verify 55 MB for every row.

### 13.9 Lifecycle and state

Nothing new: location sets live in the one table, so Stop (`fs_intel_suspend`) removes them with
the lists, Start (`fs_intel_resume`) brings them back through the gate, a hold (audit-only, Policy
Lock) keeps them out of the kernel, counters carry across re-applies, and the digest and rules checks
of 6.6 cover them. An enabled location rule counts as "something to enforce" only while the
database is on. The state sentence names rules as well as lists ("1 list and 1 location rule are
enforced: ...").

### 13.10 Windows

Windows enforces blocklists (section 11) but not location rules: `fs_intel_geo_supported()` is
FALSE there, so a surface can leave the controls out instead of offering something that cannot
work, and every engine call that would turn the database or a rule on, or download it, fails with
`fs_intel_geo_unsupported_text()`, "Blocking by country or network owner is not supported on
Windows in this version. Blocklists are.", a platform limit and not a promise. A location
rule copied into a Windows `intel.conf` counts as nothing to enforce, so it never reaches the
Windows Firewall rules. A platform with neither (no store, or a backend without the threat-intel
slots) reports "Blocklists and country or network-owner blocking are not available on this
platform yet." The Windows build still compiles and links the reader (`fs-geodb.c`, with xz and
OpenSSL from MSYS2); it is never called there.

### 13.15 The merge with Round 3 (blocklists on Windows)

Rounds 2 and 3 were built on separate branches from the same Round 1 base. Their merge keeps both,
and changes these points:

- **Section numbers.** Round 3's chapter, already merged, keeps 11; the location database reader
  became 12 and the engine part 13. Every reference in the location code, tests and README moved
  with it.
- **The live read.** Both branches put the digest on the chains to avoid `list tables` (13.7). The
  merged reader is Round 3's (`fs_intelset_nft_parse_live_chains`: one digest on every chain of the
  table, `nft -j list chains inet`, a fall-back to `list tables` for a table whose chains carry no
  common digest), plus Round 2's rule that a table found with no chain of ours is present without a
  digest, so it reads "differs". The comment sits before the chain's `type` line, as Round 3 wrote
  it.
- **The live lookup.** Round 3's `fs_intel_lookup_live` read every applied set as a stored list,
  so a location set would have read as "uncertain" forever, and every enabled location rule as a
  pending change. A location set now records, as its input, the digest of the database copy and the
  rule's values (13.8), and is asked through the copy in use while that digest matches.
- **Unsupported text.** Windows now enforces blocklists, so the location calls on Windows say only
  that country and network-owner blocking is unavailable there (13.10). A platform with neither
  says so for both.
- **The engine lock** (11.12) covers what changes the live rules or `applied.state`, which includes
  location sets through the same apply, Stop, Start and clear. The location database's own
  download and install are not under it, as a feed's download is not. The install has its own
  lock (12.6) and judges, under it, against the larger of the floor and the copy in use, so two
  updates at the same time (cron and the app) cannot put an older copy over a newer one. The
  engine lock and the install lock are never held together.
- **Help** kept its one "Not in this build" callout for country and ASN blocking until 13.16
  built the page and the command; the callout is gone since.

Tests added for the merge: fs-intel-geo-test `live: an address in the country set is blocked now,
by it, and nothing is pending`, `live: an address of another country is not blocked, and that is
certain`, `live: the rule's countries changed since the apply: pending and uncertain, never a plain
no`, `live: a rule turned off but not applied still blocks, and the change is pending`; fs-intelset-test
keeps both branches' chain-listing cases, under Round 3's rule.

- **The CLI.** `stockfw intel geo` `status | terms | on [--accept-terms] | off | update
  [--no-apply] | search TEXT [--max N] | add country|asn VALUE... [--dir D] [--name NAME] | remove
  ID | list`, each with `--json`. Refusals and read-only commands never create the store. Exit
  codes: 0; 1 a failed or refused download, or no database to search; 2 usage, an unknown id, terms
  not accepted, or the database turned off for `geo update`; 3 needs root. `intel update --feed
  location` is the same download; `intel update` alone takes it when due (24 h). `intel
  enable`/`disable` take a rule's id. `intel lookup` adds "Registered in", the network and AS,
  anycast, NAT64, "unknown" when the copy cannot be read, and the attribution; it says "MAYBE
  BLOCKED" when a location rule cannot be judged. `intel status --json` and `/api/intel` carry a
  read-only `location` object.
- **Events** gain nothing: no lookup on the event path.

  supported in this version; no topic keeps a "Not in this build" callout (`fs-help-smoke` H8
  requires zero).
