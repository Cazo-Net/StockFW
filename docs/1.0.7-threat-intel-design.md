# StockFW 1.0.7 design: IPv6 on Linux, threat-intel blocklists, country/ASN blocking

Status: section 1 (IPv6) is built. Sections 2-9 are revision 2 of the threat-intel design: the first
draft was reviewed adversarially through three lenses (netfilter: N, security: S, product: P; 47
findings), and every decision below that answers a finding names it, e.g. [N0] or [S5]. Section 10
maps every finding to its answer.
Chosen by LEPL on 2026-11-02 ("IPv6 + threat-intel blocking").
Context: `docs/ARCHITECTURE-AND-SECURITY.md` Chapter 13.9 (Linux IPv6 gap) and the IPFire gap analysis.

## 0. Goals and non-goals

Goals

1. **IPv6 is filtered on Linux** with the same policy as IPv4, without breaking IPv6 itself
   (neighbour discovery, router advertisements, PMTU, DHCPv6 replies).
2. **IP blocklists ("threat-intel feeds")**: the user opts in to well-known feeds; StockFW downloads,
   validates, normalizes and stores them, and blocks listed addresses inbound and outbound.
3. **Country and network-owner (ASN) blocking** from an offline location database built from a
   public-domain / open source.
4. **Enrichment**: every event and connection can show the remote country, network owner (ASN + name),
   and which blocklists contain the remote address.
5. Every one of these is visible and controllable in the desktop app, the `stockfw` CLI (JSON), and
   (read-only) the local dashboard.

Non-goals for 1.0.7: DNS/domain filtering, IDS, gateway features, a native nftables backend for the
*policy* (that is 1.0.8; 1.0.7 uses nftables only for the threat-intel sets), signed feeds (no feed
offers signatures; see the integrity section for what we do instead).

House rules that apply to all of it: local-first and **no network traffic unless the user enabled a
feed** (StockFW is otherwise offline); WYSIWYG (never claim protection that is not in the kernel);
argv-only process spawning (no shell); every security claim has a test with teeth.

## 1. IPv6 on Linux (iptables backend)

- `fs-script.c` gains a family dimension: `fs_script_generate_inbound_family()` /
  `fs_script_generate_outbound_family()` with `FS_SCRIPT_V4` / `FS_SCRIPT_V6`. The existing
  `fs_script_generate_inbound/outbound()` stay and mean IPv4 (no behaviour change for callers).
  The v6 script uses the token `$IP6T` (mapped to `ip6tables`), the v4 script keeps `$IPT`.
- Rule targets are classified: IPv4 literal/CIDR → v4 only; IPv6 literal/CIDR → v6 only;
  "anyone"/empty → both; hostnames → both (iptables/ip6tables resolve A/AAAA themselves at insert time;
  a name with no AAAA makes ip6tables fail → that one rule is skipped with a warning, not a failed apply).
- v6 ICMP (`-p ipv6-icmp --icmpv6-type ...`), placed in the ICMP section, i.e. **before** the
  `ctstate INVALID` drop:
  - always (whatever the ICMP page says): `packet-too-big`, `time-exceeded`, `parameter-problem`,
    `neighbour-solicitation`, `neighbour-advertisement`, `router-solicitation` (all with `-m hl --hl-eq 255`
    for the NDP ones), `router-advertisement` (`-s fe80::/10 -m hl --hl-eq 255`), MLD
    (130,131,132,143 from `fe80::/10`). Without these the host loses IPv6 connectivity.
  - per Preferences: echo-request/echo-reply (limited like v4), destination-unreachable
    (mapped from `icmp_unreachable`/`icmp_mstraceroute`), traceroute UDP 33434 as v4.
  - v4-only types (timestamp, address-mask, source-quench, redirect) have no v6 rule.
  - "ICMP filtering off" → allow all ICMPv6 (rate-limited like v4).
- DHCPv6 client replies: `-p udp -s fe80::/10 --sport 547 --dport 546 -j ACCEPT` (replies to a
  multicast solicit are not matched by conntrack).
- Reserved sources on the external interface (v6 analogue of the RFC1918 block): `::1/128`,
  `::ffff:0:0/96`, `2001:db8::/32`. ULA and link-local are **not** blocked (both are legitimate on a LAN).
- Broadcast rules: none in v6 (no broadcast). NAT/MASQUERADE: v4 only (documented).
  Port-forward DNAT is emitted in the family of its `to` address only.
- Default action: v6 LOG with the same `STOCKFW-DROP`/`STOCKFW-REJECT` prefix; REJECT uses
  `--reject-with icmp6-addr-unreachable`.
- Backend: `apply_lines()` accepts `iptables` and `ip6tables` argv; apply runs v4 then v6;
  stop/clear detach+flush+delete both families; `get_state` is driven by the v4 chain as before.
- New vtable slot `ipv6_state(&detail)` → `FILTERED` (v6 INBOUND exists and is hooked from INPUT),
  `UNFILTERED` (v4 running, v6 not; detail says why), `ABSENT` (kernel has no IPv6:
  no `/proc/net/if_inet6`), `UNKNOWN` (not root / cannot tell). Windows returns `FILTERED`
  (Windows Firewall rules cover both families). Shown on the Status page, `stockfw status`, dashboard.
- If `ip6tables` is missing or the v6 apply fails while the kernel *has* IPv6, the apply result is
  `FS_APPLY_PARTIAL` with a message naming IPv6; when the kernel has no IPv6 at all it is `FS_APPLY_OK`.
- The kernel log parser names `PROTO=ICMPv6` events "ICMPv6".

## 2. Rounds

Threat intel ships in three rounds inside 1.0.7, each one complete and tested on its own:

1. **Round 1 (this revision): blocklists on Linux.** The kernel rules, feed downloads, consent,
   local list files, exceptions, the engine, the `stockfw intel` commands, the Threat Intel page,
   events attributed to a list, and What-If/Copilot that know about lists.
2. **Round 2: country and network-owner (ASN) blocking**, with the location data question settled
   first ([P3]: the iptoasn country column is the AS owner's registration, not where an address is).
3. **Round 3: Windows** (section 11). Blocklists are enforced with Windows Firewall rules of
   their own. Its enforcement cannot be run in the development container: the pure parts are
   tested on Linux, and a test against the real firewall runs on the CI's Windows runner.
   Country and network-owner blocking stay unavailable on Windows.

Everything below is Round 1 unless it says otherwise.

## 3. Address ranges (`core/fs-iprange.[ch]`, built)

Sorted, merged, inclusive intervals per family; strict parsing; union, subtract, membership, text
form. Built and tested in 7e5afd7. Round 1 adds to the **protected ranges** (never blocked by
anything): `192.0.0.0/24`, `192.88.99.0/24`, `198.18.0.0/15` [P7] and the NAT64 prefixes
`64:ff9b::/96`, `64:ff9b:1::/48` [S7.3]. TEST-NETs stay unprotected (the tests use them).

## 4. Feeds (`core/fs-feed.[ch]`)

### 4.1 Catalog

Every feed is **off** until the user turns it on and accepts its terms. No mirrors in 1.0.7
[S12, P6]: a feed is fetched from its own publisher or not at all. Each entry carries: id, name,
category, one-sentence description, URL, the host contacted, an info page, a terms page, the licence
name *only where it has been verified* (otherwise the UI says "See the provider's terms"), a
non-commercial flag, format, default direction, update interval, `recommended`, `includes` (ids of
feeds it already contains) and whether it publishes IPv6.

| id | publisher | format | default dir | interval | recommended |
|---|---|---|---|---|---|
| spamhaus-drop | Spamhaus DROP (IPv4) | spamhaus-json | both | 12 h | yes |
| spamhaus-dropv6 | Spamhaus DROP (IPv6) | spamhaus-json | both | 12 h | yes |
| feodo | abuse.ch Feodo Tracker (botnet C2) | plain | both | 6 h | yes |
| dshield | DShield top attackers | dshield | in | 24 h | no (non-commercial terms) [P9] |
| firehol-level1 | FireHOL level 1 (aggregate; includes the three above and DShield) | plain | in | 24 h | no |
| blocklist-de | blocklist.de (fail2ban reports) | plain | in | 24 h | no |
| et-compromised | Emerging Threats compromised hosts | plain | in | 24 h | no |
| cins-army | CINS Army | plain | in | 24 h | no |
| tor-exits | Tor exit relays (a policy choice, not a threat list) | plain | in | 6 h | no |

Turning on a feed whose `includes` names one that is already on adds a note ("FireHOL level 1
already contains Spamhaus DROP"); both stay on if the user wants. Custom feeds: any URL that passes
the URL rule (4.4), with a name, a format and a direction; the user typed the URL, which is consent
for that host.

### 4.2 Formats

- **plain**: one address, CIDR or `a-b` range per line; `#` and `;` start comments; anything after
  the first whitespace, `;` or `,` is ignored.
- **spamhaus-json**: NDJSON. Lines that are objects with a `"cidr"` string give entries; the
  object with `"type":"metadata"` gives the content date (`"timestamp"`, unix seconds) and the
  advertised `"records"` count (recorded, not enforced: format from documentation).
- **dshield**: `start<TAB>end<TAB>prefix...` rows, `#` comments, a `Start` header row; the range is
  `start-end`.

Content dates are read where a format has one [S12.2]: FireHOL `# This File Date`, abuse.ch
`# Last updated`, DShield's header date, Spamhaus metadata. Unknown dates are 0, and staleness then
falls back to the download time.

### 4.3 Parse guards (pure, in `fs_feed_parse`)

- At most **32 MiB**, at most **200,000** entries [S8.1], lines over 4096 bytes are invalid, a NUL
  byte refuses the body, a UTF-8 BOM and CRLF are accepted.
- Each entry is first reduced by the protected ranges, then **every remaining piece is measured by
  size, never by prefix length** [S1.1, S4]: an IPv4 piece wider than 2^22 addresses (a /10) or an
  IPv6 piece wider than 2^99 (a /29) drops the entry as *too broad*. This catches
  `::ffff:0.0.0.0/96`, `0.0.0.0-255.255.255.255` and `2000::-3fff:...` as well as plain wide CIDRs.
  Aggregates whose wide entries are all protected space (FireHOL's `224.0.0.0/3`) lose nothing and
  report nothing [P7].
- **Coverage caps** on the whole list after subtraction [S1.2]: IPv4 at most 2^25 addresses, IPv6
  at most 2^42 /64 networks. Over the cap, the download is refused.
- Nothing parsed while lines were invalid, or more invalid data lines than valid ones (an HTML
  error page), refuses the body.

### 4.4 URL rule

`https://` only, at most 2048 bytes, printable ASCII without spaces, no `user@` part, a non-empty
host, and never starting with `-`. Query strings are allowed (paid feeds use keys there) but are
shown as `?…` everywhere except the feed editor [S18].

### 4.5 Accepting an update (`fs_feed_judge`, pure)

Compared against the feed's history (the last 7 accepted copies) [S15]:

- **empty**: a list that parses to nothing replaces a non-empty one only with *accept shrink*;
- **shrank**: fewer than a quarter of the largest recent entry count (when that was 8 or more), or
  less than a quarter of the largest recent IPv4 coverage (when that was 2^16 or more);
- **grew**: IPv4 coverage more than doubled *and* grew by more than 2^22 addresses [S1.3]; needs
  *accept coverage*;
- **rollback**: an older content date than the copy we have [S12.4]; needs *accept shrink*.

A refused update keeps the previous copy, sets `refused` in the feed's state with the reason, and
writes an audit line. `--now` (ignore the schedule) and `--accept-shrink` / `--accept-coverage`
(override a guard) are separate flags [S15.2].

## 5. Downloads (`core/fs-fetch.[ch]`)

curl, spawned with an argv, hardened against everything a root process inherits [S0, S2, S9, P14]:

- `argv[0]` is absolute: `/usr/bin/curl`, else `/bin/curl`; missing curl is a clear error.
- `-q` first (no curlrc), then `--proto =https --proto-redir =https --proto-default https
  --tlsv1.2 --fail --silent --show-error --location --max-redirs 3 --globoff
  --max-filesize <cap> --max-time <t> --connect-timeout 20 --user-agent StockFW/<version>
  --output -`, then either `--noproxy *` or `--proxy <url>` (only from `intel.conf`, validated),
  then `--url <url>`. `--globoff`: one URL is one transfer; curl would otherwise expand `[..]`
  and `{..}` into many requests, even to hosts the URL does not name.
- An **explicit environment**: `PATH=/usr/sbin:/usr/bin:/sbin:/bin` and `LC_ALL=C`, nothing else:
  no HOME, no `CURL_CA_BUNDLE`, `SSL_CERT_*`, `SSLKEYLOGFILE` or `*_proxy`.
- As root, curl runs as **nobody** (uid/gid looked up before the fork, supplementary groups
  cleared in the child); if that account does not exist the download is refused [S2.5].
- The body arrives on a **pipe**, never a file; StockFW counts bytes itself and kills curl at
  cap + 1 [S9]. No `--compressed`. A whole-transfer timeout kills it too.
- Errors are classified (no curl, refused URL, too large, timed out, TLS, HTTP status, network)
  with curl's first stderr line.
- Test builds only (`FS_FETCH_TESTING`) read `STOCKFW_TEST_CURL` and `STOCKFW_TEST_CACERT`; release
  builds have no such hook.

Every download goes through one engine function that refuses unless that feed is enabled *and* its
terms were accepted [S14.1]. With the default configuration StockFW makes no network request at
all, and a test with teeth proves it [S14.4].

## 6. The engine (`core/fs-intel.[ch]`)

### 6.1 Store

- Linux, root: `/var/lib/stockfw/intel`, mode 0700, owned by root (parent 0755).
  `STOCKFW_INTEL_DIR` overrides it only when that directory and every parent are owned by the
  current user or root and not writable by group or others (OpenSSH's StrictModes) [S2.1-2]; a
  user-owned directory under `sudo -E` is refused, not used. Non-root without an override: the
  engine says it needs root.
- Every file operation goes through a directory descriptor opened `O_DIRECTORY|O_NOFOLLOW`, files
  are opened `O_NOFOLLOW|O_CLOEXEC`, must be regular files, are read with a size cap, and are
  written to a fresh temp name (`O_EXCL`), fsynced and renamed [S2.3]. All files are 0600.
- Files: `intel.conf` (config), `<id>.list` (normalized ranges), `<id>.state` (key file: dates,
  counts, history, last error, refusal, carried counters), `applied.state` (what the kernel was last
  given: digest, set ids and counts, suspended flag).
- Loading a stored list re-applies the strict syntax, the entry count and the coverage caps,
  counted exactly as the parser counts them [S2.7, S4.4]: a tampered list is an error, not a block.
  The per-entry size floor is not re-applied: a stored list is normalized, so adjacent entries
  that each passed it are merged into wider intervals (eight adjacent /10s are stored as one /7);
  the coverage caps bound what a tampered list can block to what an accepted feed may.
- An existing store directory that group or others can read is tightened to 0700 when it is
  opened (its files are 0600, but a readable directory lists the feeds and local lists in use).
- Windows: `%ProgramData%\StockFW\intel` with an admin-only protected DACL [S3]; see 11.5.

### 6.2 Configuration (`intel.conf`)

Master switch (default on, which does nothing until something is enabled), optional proxy, one
group per feed (enabled, direction, terms accepted at), custom feeds (name, URL, format), local lists
(name, direction, enabled) and exceptions (addresses, CIDRs or ranges). Unknown keys are ignored;
invalid values fail the load naming the key. Ids are `^[a-z0-9][a-z0-9-]{0,39}$` [N7].

### 6.3 Local list files

`stockfw intel import <file> --name <name>` (and Import on the page) read a CSV or plain file with
the rules of `fs_blocklist_parse_csv` (first field; a header line; quoted fields), apply the parse
guards of 4.3, and store it as list `local-<slug>`. Importing the same name again (in any case or
spacing) replaces it; a different name whose slug is already another list's id ("Office VPN" and
"office-vpn") is refused, never written over that list. No network is involved.

### 6.4 Building the rule set (`fs_intel_build`)

One set per enabled feed or local list with a stored copy (never fetched: a note, not an error).
From each set the engine subtracts, and lists in the notes what it subtracted:

- the protected ranges and the user's exceptions;
- this computer's own addresses, its connected prefixes and its default gateways [N4b, S5.2];
- the DNS servers in use: `/etc/resolv.conf`, and when every server there is loopback,
  `/run/systemd/resolve/resolv.conf` and `/run/NetworkManager/no-stub-resolv.conf` [N5, S7.1];
- the peers to keep reachable: the client in `$SSH_CONNECTION`/`$SSH_CLIENT` and every established
  inbound TCP connection to the local SSH port [N4c, S5.3];
- the addresses of the enabled feeds' own hosts, so a list cannot block its own updates [S7.2], and,
  while any feed is enabled, the configured proxy's host, which every download connects to instead
  (`fs_intel_update_hosts`).

Then, for sets that block outbound (out or both), each IPv4 interval is also added to the IPv6 set
inside `64:ff9b::/96`, so NAT64 does not bypass an outbound list [N9, S7.3, P15].

Limits [S8.2, S1.2]: at most **300,000 intervals** over all sets (v4 and v6 together), and at most
2^26 IPv4 addresses in the union of all sets; above either the build fails naming the largest sets.

### 6.5 The gate (`fs_intel_apply_safe`) and the lifecycle

- Audit-only mode and the Policy Lock hold the apply exactly like the policy gate
  (`FS_APPLY_DRY_RUN`, nothing reaches the kernel). A backend without the intel slots answers
  "not available on this platform".
- The live counters are read before the kernel's sets are replaced and added to each source's
  carried total once the replacement is proven, so "blocked N" survives updates and is labelled
  "since <date>" [N8, P8]. Proof is a new digest where another one (or none) was live, or a counter
  lower than before. A re-apply of the same digest that the tool fails is exactly what a refused
  transaction leaves behind, so it is a failure with a note that the same rules are still in force,
  and nothing is carried: the old table still counts, and is never counted twice.
- Success records `applied.state`; every attempt is one audit line.
- **The policy never touches the threat-intel table** [N6, S10.2, P4a]: `linux_stop`, which the
  policy apply, reload and clear all call, never runs nft. The user-facing **Stop** (Status page,
  `stockfw stop`) calls stop and then `fs_intel_suspend`, which removes the table and marks it
  suspended; the user-facing **Start** (Status page, `stockfw start`, start-on-open) calls start and
  then `fs_intel_resume`, which re-applies through the gate under the same hold as any apply. Resume
  first clears "suspended", so a Start whose apply is held, refused or fails reads not-loaded, never
  suspended. Where no list was ever turned on (no store directory), Stop and Start do nothing and
  create nothing. Without nft, a Stop is not an error when StockFW's record says it left no table;
  when the record says it left one, the Stop fails and says why.
- Nothing survives a reboot on Linux, policy or lists, until Start is pressed; the docs and the page
  say so [P4b]. Unattended re-applies (the app's hourly check, `stockfw intel update`) happen only
  when the firewall is running, the table is enforced or differs, and no hold is active [P4].

### 6.6 State: what the kernel is actually doing [S10, P4]

The table carries `comment "sfw:<digest>"`, where the digest is the first 32 hex digits of the
SHA-256 of the canonical rule set (each set's id, direction and stored text form, in order).
`fs_intel_state` compares the live table (`nft -j list tables`, fast: no elements) with
`applied.state`:

| state | meaning |
|---|---|
| off | master switch off, or nothing enabled (also when the kernel cannot be read, e.g. no nft, as long as StockFW's record says it left nothing loaded) |
| enforced | the live table's digest is the one StockFW last applied, and every applied list that has addresses still has its rules (the counter rules, listed per chain) |
| not-loaded | something should be enforced but the table is missing (a reboot, `flush ruleset`) |
| differs | a table is there but not the one StockFW applied |
| suspended | the firewall was stopped by the user, so the lists are off on purpose |
| not-in-force | Round 3 (Windows): rules are there, or cannot be read, and the firewall does not enforce them on a network in use (11.6) |
| unsupported / needs-root / unknown | cannot enforce here / cannot read the kernel / cannot tell |

A table whose chains were flushed (`nft flush table`) keeps its comment, so the digest alone would
still read enforced; the rules check makes it differs. Not seen: elements removed from a set, or some
of a list's rules removed while others remain.

Every surface shows this state, never just the configuration.

### 6.7 Updates and scheduling

`fs_intel_update` takes the enabled, consented feeds that are due (or one feed, or `--now`), fetches,
parses, judges, stores and reports one result per feed: updated, unchanged (same SHA-256), not due,
needs consent, refused (with why) or failed (with why). A failed or refused update never removes
the previous copy. The desktop app checks hourly in a worker thread [P13]; `stockfw intel update`
does the same for cron or a timer. Staleness: older than 7 update intervals, measured from the
content date when known [S12.3].

### 6.8 Lookup

`fs_intel_lookup` answers, for one address: the enabled sets that list it, whether it is protected,
an exception, or kept reachable as this computer's own network, and whether the current
configuration blocks it and in which direction. What-If and Copilot use it [P2]: an address the
policy allows but a list blocks is answered "Blocked by threat intel: <list>".

## 7. Enforcement on Linux (`core/fs-intelset.[ch]`, backend slots)

One table, `inet stockfw_intel`, owned by StockFW and replaced in one `nft -f -` transaction
(create-if-missing, delete, re-create), so it applies whole or not at all and a failed apply leaves
the previous table in force. Set names are `s_<id with - as _>_4` and `_6`; a family with no
addresses has no set and no rules [N7]. Every statement ends with a newline [N7]. Elements are
added 1000 to a statement. nft gets 60 seconds [S8.4].

Three base chains at `priority filter - 10` (before the iptables policy at 0), always present:

```
chain input   { type filter hook input   priority filter - 10; policy accept;  iif "lo" accept ... }
chain output  { type filter hook output  priority filter - 10; policy accept;  oif "lo" accept ... }
chain forward { type filter hook forward priority filter - 10; policy accept;  ... }
```

Directions [N0, S6, P1] — the same meaning as Windows' stateful rules:

| direction | input | output | forward |
|---|---|---|---|
| in ("stops them connecting to you") | `saddr @set ct direction original` drop | — | `saddr @set ct direction original` drop |
| out ("stops you connecting to them") | — | `daddr @set ct direction original` reject | `daddr @set ct direction original` reject |
| both | `saddr @set` drop | `daddr @set` reject | both of the above |

Drops are silent to the outside; outbound blocks are `reject with icmpx type admin-prohibited` so a
local program fails at once instead of hanging [P11]. Each blocking rule is preceded by the same
match with `limit rate 10/second burst 20 packets log prefix "STOCKFW-TI <id> " level info`, and
carries `counter` and `comment "<id>"`. Counters are read with `nft list chain` per chain, never by
listing the table or sets [S8.3].

Backend slots: `intel_apply`, `intel_clear`, `intel_counters`, `intel_live` (table present, and its
digest). The standalone CSV-to-set helper written earlier (`fs_nftset_load_csv`) keeps its API and
now uses its own table, `inet stockfw_blocklist`, so the two never collide.

Events: a kernel log line with `STOCKFW-TI <id>` becomes a blocked event whose rule is
"Threat intel: <list name>", accepted only when `<id>` is a set in the applied rule set [S17.3].

## 8. Surfaces (Round 1)

- **Threat Intel page**: the state (6.6) in words, the master switch, the feeds (switch, name,
  licence or "See terms", direction, entries, content age, status, blocked since), Update now and
  Apply (worker thread, with progress), a consent dialog the first time a feed is turned on (the
  host contacted, how often, what it learns: this computer's public address and "StockFW/<version>",
  the licence and terms link, and that lists contain mistakes and how to make an exception) [P11,
  S14.3], local lists (Import, remove), exceptions (add, remove), a lookup box, and the notes from
  the last build. Linux needs root to change anything; on Windows the page says blocklists are not
  available there yet.
- **Events**: list blocks show the list's name; for an address a list blocks, the Allow action
  becomes "Add exception" [P2].
- **Overview**: one line with the threat-intel state and how many lists are enforced.
- **CLI**: `stockfw intel status|feeds|enable|disable|update|apply|clear|import|remove|except|
  unexcept|exceptions|lookup|on|off`, each with `--json`; `stockfw status` gains an `intel` object;
  `stockfw stop`/`start` suspend and resume the lists; `stockfw simulate` reports list blocks.
- **Dashboard** (read-only): the state and the enforced lists.
- **Audit lines** escape `\`, newlines and `|`, and keep tool output to its first line, capped at
  1 KiB [S17.1].

## 9. Test plan (teeth)

Every check below has a re-injected bug that turns it red; tests/README.md lists them. Where a check
cannot run in the container, it says so [P12].

- **nft rendering** (pure): golden layout, empty families, empty rule set, ids that would inject
  statements are refused (`a";flush ruleset;#`), counters and digest parsing.
- **nft live** (private namespaces, two of them joined by a veth pair): `nft -c` on every fixture;
  apply and replace; a rejected transaction changes nothing; all six direction cells (in/out/both ×
  started here / started there) with a real TCP connection each way; loopback is never blocked;
  counters move; the digest round-trips; clear removes only our table. IPv6 rules are checked as text
  and with `nft -c` only: the container cannot send IPv6.
- **policy vs lists**: apply the policy twice, stop, clear, apply, reload: the table and its counters
  are untouched (test-intel-backend.sh); user Stop removes it and Start brings it back, through the
  engine and through `stockfw stop`/`start` (test-intel-e2e.sh).
- **feeds** (pure): each format, hostile input (size, NUL, 200,001 entries, every too-broad form
  above, BOM, CRLF, HTML), coverage caps, every verdict of `fs_feed_judge`, content dates.
- **fetch** (local HTTPS server with a test CA): success; a curlrc with `insecure`, `CURL_CA_BUNDLE`
  and a proxy in the environment change nothing (TLS still fails without the test CA, no proxy is
  contacted); an endless chunked body is cut at the cap; a silent server times out; redirects to
  http and long redirect chains are refused; HTTP errors; curl runs as nobody; missing curl.
- **engine** (fake backend, fake fetcher): no network with the default config; consent gating;
  updates and guards across history; the store refuses unsafe directories and symlinks; a tampered
  list is an error; every subtraction in 6.4 (the proxy too); NAT64 mapping; limits; hold; state
  transitions (flushed chains, no nft, a Start that fails); counters carried across re-applies,
  and never for a same-digest re-apply the tool failed; lookup.

## 11. Round 3: blocklists on Windows

Round 3 enforces the same rule set (section 6.4) with Windows Firewall rules. The engine, the
store's file formats, the build and every subtraction are shared with Linux; what differs is
below. The shape of the rules and every verdict on what is read back are decided in pure code
(`core/fs-intelwin.[ch]`), which the core suite checks on Linux; the backend
(`platform/windows/fs-backend-windows.c`) only moves them across COM.

### 11.1 The rules

Every rule is written in-process through `INetFwPolicy2`, `INetFwRules` and `INetFwRule`. No
netsh and no PowerShell: a spawned console would flash, and its output would have to be parsed.
The vtable slots StockFW calls are pinned to their documented positions at compile time
(`netfw-compat.h`), so a header that disagreed stops the build instead of calling the wrong method.
(The old note that MinGW's `INetFwRules` was wrong was itself wrong: Microsoft documents
`Add(INetFwRule *)`, `Remove(BSTR name)` and `Item(BSTR name, ...)`, as MinGW declares them.)

- Every rule is in the rule group `StockFW Threat Intel` and nothing else of StockFW's is. The
  policy's rules are named `StockFW-...`, live outside the group, and the policy's clear keeps to
  that prefix, so applying or clearing either never touches the other [N6, P0].
- One rule per chunk: `SFW-TI <id> <in|out> IPv<4|6> <i>/<n> g<8 hex>`. A list in both directions
  gets an inbound and an outbound copy. Every rule blocks, applies to every profile, protocol,
  port, local address, program and interface type, and names its addresses in `RemoteAddresses`.
- The last part of the name is the generation: a random value per apply that no rule on the
  firewall already carries.
- One manifest rule per generation, `SFW-TI manifest g<8 hex>`, disabled, with `RemoteAddresses`
  192.0.2.1 (TEST-NET-1, so enabling it by hand still blocks nothing that exists). Its description
  ends `sfw:<digest> plan:<plan hash> rules:<n>`. The plan hash is the SHA-256 (first 32 hex
  digits) of `sfw:<digest>` followed by, for every address rule in name order, its name, its
  direction and its addresses in the stored text form. The manifest also keeps a rule set whose
  lists were emptied by subtraction visible, as the nft table without sets is on Linux.
- Descriptions name the list (control characters and `|` replaced, at most 80 characters).
- The empty rule set leaves no rule at all.

### 11.2 How many addresses a rule takes

Microsoft documents no limit on `RemoteAddresses` (the `put_RemoteAddresses` reference says only
that it is a list of addresses, ranges and keywords). Reports from tools that write blocklists into
Windows Firewall rules agree on: at most 1000 addresses per rule on Windows 7, 10,000 on later
versions; the WaGi Mass IP Blacklister, for one, splits at 10,000 and at 1000 for Windows 7. StockFW
writes at most **1000 tokens** per rule, the value every supported Windows takes, and at most
**32,000 characters**: a `UNICODE_STRING` holds 32,767 UTF-16 units, and 1000 IPv6 ranges written
as `a-b` can reach about 79,000 characters, so the character cap keeps every string inside what any
layer between the API and the filter engine could store. A token (an address, a CIDR block or
`a-b`, as the stored text form prints it) is never split; a single token longer than the cap would
get a rule of its own.

At the 300,000-interval build cap (6.4) that is 300 rules per direction, which the firewall
handles; Linux uses sets instead because nft has them.

### 11.3 Apply and clear

- **Apply** reads our rules first. Exactly the asked-for rules, whole (11.6), is a no-op: no
  rule is rewritten on every hourly re-apply, and there are no counters a replacement could reset.
- Otherwise the new generation is written first, its manifest last, so until the manifest exists
  the new rules read as incomplete, never as a rule set. A rule the firewall refuses takes the new
  generation out again and leaves the old one untouched and in force.
- Then every rule of ours that is not the new generation is removed (for the empty rule set,
  all of them). A rule that will not go blocks more than asked, never less, and the apply says so.
- `INetFwRules::Remove` goes by name, and Windows lets two rules share one. A rule whose name any
  other rule also has is first renamed, on the rule object itself, to a name nothing else has, so
  a removal can only take that rule, never a user's rule that happens to share the name.
- What the firewall holds afterwards, read back whole, decides success [S10]: the asked-for
  digest, PRESENT; for the empty rule set, nothing of ours.
- **Clear** removes every rule in the group and nothing else, then lists the firewall again: only
  none left is success. A rule someone else put in the group is removed too; the group is
  StockFW's.

### 11.4 Exceptions and what is kept reachable

Windows Firewall has no rule order: a block rule beats every allow rule (the one exception is an
allow rule with "override block rules", which needs authenticated IPsec, below). An exception is
therefore never written as an allow rule. It holds because the build subtracts it, with the
protected ranges and everything in 6.4, before any rule is written; the Windows rules are made
from the same rule set as the nft sets, and `fs-intel-test` checks that no rule they would write
names a subtracted address.

What the build keeps reachable is read on Windows by `fs_hostnet_read`:
`GetAdaptersAddresses` for every adapter that is up (its addresses, the block each lies in from
`OnLinkPrefixLength`, its gateways and its DNS servers), the SSH variables and
`GetExtendedTcpTable` for established connections to local ports 22 (SSH) and 3389 (Remote
Desktop), and `getaddrinfo` for the update hosts. A prefix length of 0, or wider than the family,
keeps the address alone; it never keeps everything (which would empty every list without a word).

### 11.5 Store

`%ProgramData%\StockFW\intel`, from `SHGetFolderPathW`, never from the environment [S3]. Applying
needs StockFW to run as administrator (`FS_INTEL_ERR_NEEDS_ROOT` otherwise).

- `%ProgramData%\StockFW` is created with a protected DACL: SYSTEM and Administrators full,
  Users read. `intel` inside it: SYSTEM and Administrators only. Nothing is inherited from
  `%ProgramData%`, which lets every user create folders.
- An existing folder must be owned by Administrators, SYSTEM or TrustedInstaller, grant no other
  account a right to change it and be no link; otherwise it is refused (`FS_INTEL_ERR_UNSAFE_DIR`).
  A folder another account made first is never used. An `intel` folder others can read is set
  back to SYSTEM and Administrators.
- Win32 has no `openat`, so the store is pinned: a handle on the directory opened without
  `FILE_SHARE_DELETE`, so nobody can rename or delete it, or a parent of it, while StockFW works in
  it. Files are opened with `FILE_FLAG_OPEN_REPARSE_POINT` and refused when they are links, read
  with a size cap, written to a fresh name and moved over the old one with
  `MOVEFILE_WRITE_THROUGH`.
- `STOCKFW_INTEL_DIR` (absolute) gets the same checks, with the current user trusted too, and is
  created with SYSTEM, Administrators and the current user.

### 11.6 Live state and "in force"

`intel_live` lists every rule on the firewall and judges ours (`fs_intelwin_read`):

| live | when |
|---|---|
| ABSENT | no rule in our group |
| PRESENT (with the digest) | one generation, one manifest, and its rules all there and unaltered: the plan hash recomputed from what was read (names, directions, addresses) is the manifest's, the count matches, and every rule is enabled, blocks, has its direction, covers every profile (the three bits; Windows reports `NET_FW_PROFILE2_ALL`), every protocol (256), every local address and port, no program or service, interface types `All`, no named interface and no `INetFwRule3` condition (app package, users, machines, IPsec flags) |
| PARTIAL | anything else: a rule missing, added, edited, disabled or narrowed, a second generation (a removal that failed), a rule in the group StockFW did not write |
| INACTIVE | rules of ours are there, but the firewall does not enforce them on a network in use |
| UNKNOWN | the rules cannot be read |

Addresses are compared as sets: Windows hands IPv4 back with dotted masks
(`10.0.0.0/255.0.0.0`) and may reorder them. Keywords (`*`, `LocalSubnet`, `DNS`,
`DefaultGateway`, ...) and masks with holes are refused, so they read PARTIAL.

"Not in force" (`intel_not_in_force`, `fs_intelwin_not_in_force`) is one sentence, or nothing:

- the Windows Firewall service (MpsSvc) is not running (asked of the service manager, which a
  standard user may ask);
- Group Policy manages the firewall and does not apply local rules
  (`LocalPolicyModifyState` is `GP_OVERRIDE`);
- the firewall is off for a profile a network in use has (`CurrentProfileTypes`,
  `FirewallEnabled`);
- adapters are excluded from such a profile (`ExcludedInterfaces`).

What cannot be read is never reported as off. The engine (6.6) gains one state, **not-in-force**,
which wins over enforced: INACTIVE reads not-in-force with that sentence (and says when the rules
there are not the ones last applied either); UNKNOWN with a sentence (the service stopped, so the
rules cannot even be read) reads not-in-force too; PARTIAL reads **differs** ("Some of the
blocklist rules are missing or were changed outside StockFW; apply to restore them."). An apply
whose rules are written but not enforced is a success with a note: "The rules are in place, but
not in force: ...". Stop removes rules that are PARTIAL or INACTIVE as well.

### 11.7 Counts

Windows Firewall keeps no count of what each rule blocks, so `intel_counters` stays NULL. The
engine says so in words, `fs_intel_counts_unavailable()`: "Windows Firewall does not count what
each rule blocks, so StockFW cannot show blocked counts here." Surfaces show that sentence instead
of a number; `fs_intel_counters()` on Windows holds no entry, so no list is ever shown as "0
blocked". The firewall log (`pfirewall.log`) does not name the rule that dropped a packet either,
so Events on Windows cannot say which list blocked an address.

### 11.8 Downloads on Windows

`fs-fetch.c` spawns the curl that ships with Windows by its absolute path
(`<system folder>\curl.exe`, from `GetSystemDirectoryW`, never `PATH`), with the same argv as
Linux, an explicit environment (`SystemRoot`, which Winsock needs, and
`NoDefaultCurrentDirectoryInExePath=1`, nothing from StockFW's own environment) and the system
folder as working folder. Missing curl (Windows before 10 1803) is a clear error. Known gaps, not closed in Round 3:

- No privilege drop: curl runs with StockFW's rights, which on Windows are an administrator's.
  Windows has no `nobody`; a restricted token is possible but not done.
- GLib starts a console program through its spawn helper, so a console window may flash for the
  length of a download. Not seen in the container; unverified.
- Windows' curl uses Schannel and the Windows certificate store, not a CA file. The test hooks
  (`STOCKFW_TEST_CACERT`) are Linux only.

### 11.9 What blocklists do not cover on Windows

- Routed traffic: the "out" direction on Linux also stops connections a routed LAN host starts.
  Windows Firewall rules filter this computer's own traffic; Internet Connection Sharing is not
  filtered by them.
- An allow rule with "override block rules" (authenticated bypass) wins over a block rule. It
  only matches traffic authenticated with IPsec, which a listed address cannot provide unless the
  administrator set that up.
- Country and network-owner (ASN) blocking (Round 2) are not available on Windows.
